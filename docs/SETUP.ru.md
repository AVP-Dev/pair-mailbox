# Установка

> Язык: русское зеркало, оригинал — SETUP.md.

## Предпосылки

- `python3` 3.8 или новее в `PATH` (у сервера нет сторонних зависимостей)
- Два CLI агентов. В `cli-profiles.json` 6 профилей (opencode, agy,
  codex, claude, pi, omp); тот же сервер работает с любым другим клиентом, говорящим по MCP — см. *Другой CLI* ниже. `pairup --swap` переключает критика на любой из них.
- Оба агента работают в одном репозитории, в одном каталоге проекта, чтобы разрешать один и тот же
  каталог состояния `.pair`.

Проверьте, что сервер запускается, прежде чем подключать к нему что-либо:

```sh
bin/pairctl status
./scripts/verify-project.sh          # сам гейт; см. scripts/verification-profile.tsv
```

## 1. Инициализация спаривания

```sh
bin/pairctl task "fix the retry storm: clients re-send on 502 instead of on 503"
bin/pairctl assign <роль>        # роль = имя CLI: opencode, agy, codex, claude
bin/pairctl status
```

Подставляйте свои два имени CLI везде ниже. Роль — это то, что `install.sh` записал в
конфиг каждого CLI, поэтому `--list` установщика показывает, что у вас реально есть.

`assign` — единственный способ перемещения полномочий. Если пропустить его, состояние останется `UNASSIGNED`, в котором
ни один агент не может редактировать — это безопасное умолчание, а не баг.

## 2. Запуск обоих агентов

Из каталога проекта — `pairup` поднимает сверхвизора (если мёртв) и обоих агентов
из стоящей расстановки, в tmux:

```sh
pairup --install   # один раз: шим в ~/.local/bin
cd ~/work/<проект> && pairup
```

Ручная форма, в **agterm**, по одной панели на агента, один и тот же рабочий каталог. Никогда голый `opencode`:
запуск всегда `opencode --standalone --auto` (см. `cli-profiles.json`),
так каждая панель получает свой локальный инстанс и MCP-конфиг:

```
opencode --standalone --auto          # pane 1
agy                                   # pane 2
```

Любые два разных CLI, в любом порядке. Роли берутся из постоянной договорённости, если вы её
задали, и только иначе — из клейма. Для двух копий ОДНОГО CLI в одном проекте
используй `bin/pair-duo <cli>` — он выводит роли `<cli>-writer` и `<cli>-critic`:

```sh
bin/pairctl roles --writer opencode --global   # set it once (writer-pin: critic is any second live role)
```

При заданной договорённости порядок панелей ничего не решает, и ни одному агенту
не нужно рассказывать о другом: они находят друг друга через общий каталог
состояния. Без неё писателем становится тот, кто первым прочитал задачу.

`pair_deliver` требует, чтобы оба агента были внутри панелей tmux. Вне tmux `pair_send`, `pair_read`
и `pair_note` по-прежнему работают — теряется только живое пробуждение.

### Antigravity: разрешите MCP-инструменты

Antigravity запускает ненастроенные MCP-инструменты в режиме **Ask**, поэтому первый вызов `pair_*` остановится на
подтверждении. Разрешите весь сервер один раз:

```
/permissions
```

и добавьте `mcp(pair/*)`. Без этого спаривание технически работает, а практически — нет.
Убедитесь, что сервер подключён и все его 22 инструмента перечислены.

Три агента — `pair-writer`, `pair-critic`, `pair-explorer` — видны в `/agents`.

### OpenCode

`opencode.jsonc` и плагин `pair-guard` подхватываются автоматически из `.opencode/`. Если
плагин был добавлен, пока сервис работал:

```sh
opencode service restart
```

Затем, в сессии:

```text
/pair-status      # who holds authority, the task, the phase, unread messages
/pair-handoff     # leave a handoff note and report what is still open
```

`pair-guard` подмешивает живое состояние полномочий в каждый запрос агентского цикла, поэтому сессия, работающая
уже часы, всё ещё знает, по какую сторону границы она находится.

## 3. Дымовой тест

Две минуты, и он доказывает всю цепочку, включая отказы.

Спросите писателя: *«Ты писатель? Ответь одним предложением.»* — ожидайте да.

Спросите критика: *«Попробуй отредактировать README.md.»* — ожидайте отказ, а не правку.

Спросите писателя: *«Попробуй `pair_patch_reserve`.»* — ожидайте отказ: писатель не предлагает
патчи.

Из другой панели выполните:

```sh
bin/pairctl log --limit 20
```

Отказы есть в логе. Видеть их — значит, граница реальна, а не рекомендательна.

## 4. Работа

Обычная совместная работа дальше. То, что стоит делать осознанно:

- **Заговорите рано.** Два агента, которые никогда не разговаривают, дают мнение одного агента с лишними шагами.
- **Пусть критик атакует план**, а не только дифф. Самое дешёвое разногласие — до того, как кто-то
  написал код.
- **Передавайте, а не зависайте.** `bin/pairctl release`, затем `bin/pairctl assign <роль соседа>`, затем скажите
  новому писателю, что он писатель, а старый — только для чтения. Сделать это в обеих сессиях — не
  факультативная бухгалтерия; именно так каждый агент узнаёт об изменении.

## Несколько проектов, один движок

Запись MCP указывает на дерево pair-mailbox, из которого запускали `install.sh`. Это дерево —
**движок**; проект, в котором запускали `pairup`, — **цель**. Это разные репозитории по замыслу,
и сервер работает между ними: `galatour` запускает
`/mnt/storage/work/umputum/mcp/pair_mailbox/serve.sh` против `/mnt/storage/work/galatour/.pair`,
по одному серверу на проект, каждый со своими состоянием и блокировками ролей. В цель ничего не
копируется, поэтому один движок обслуживает каждый установленный проект.

Origin guard в `serve.sh` делает это явным, а не доверяя вслепую. Целевой проект записывает,
какой движок ему разрешён, в `.pair/engine` (и `engine_root` в `state.json`); `bin/pairup` пишет
эту запись при первом создании состояния и обновляет её, когда дерево движка переезжает. Дальше
guard отказывается работать, когда корень кода:

- в рабочее пространство (`/tmp`, `/var/tmp`, `/dev/shm`) — дефект 108-го раунда: конфиг,
оставленный указывающим на скрэтч-клон, обслуживал роль устаревшим кодом, пока всё выглядело
правильно;
- не тот движок, который санкционировал этот проект — устаревшая запись или неверная запись,
но никогда не тихое смешивание;
- попадает в проект, у которого есть собственный `mcp/pair_mailbox/` — там запись должна
указывать на собственную копию проекта, а чужой корень — та самая форма скрэтч-клона.

Отказ называет оба дерева и лекарство, поэтому починка — команда, а не расследование.
Эмпирика: `mcp/pair_mailbox/test_origin_guard.py` поднимает настоящий `serve.sh` в настоящих
деревьях — санкционированный движок работает; скрэтч, несанкционированный и собственный-пакет
отказаны.

## Другой CLI

Мост — это MCP, поэтому ничего в нём не специфично для этих двух. Добавьте запись сервера, указывающую на
ту же обёртку с новым именем роли:

```jsonc
{ "mcpServers": { "pair": { "command": "sh",
    "args": ["mcp/pair_mailbox/serve.sh", "<role-name>"] } } }
```

Затем `bin/pairctl assign <role-name>`. Добавьте имя пира в `pair_send(to=...)` и зарегистрируйте
роль, чтобы она появилась в ростере. Скопируйте существующий markdown агента и поправьте имена инструментов, если
MCP-префикс CLI отличается.

Две сессии OpenCode на разных моделях работают так же: скопируйте блок `opencode.jsonc`,
дайте второй роль `opencode2`.

## Формы конфигов, стоившие нам по багу каждая

**`timeout` выше должен превышать потолочное ожидание протокола.** `pair_read` может ждать
60 секунд, и это ожидание — часть протокола: агент, который не умеет ждать, никогда
не замечает входящее сообщение, и человек начинает ретранслировать вручную. Клиент, который
сдаётся первым, рвёт вызов посреди ожидания, и агент не может отличить «никто
не ответил» от «меня отключили» — поэтому он делает вывод о своём пире вместо
вывода о себе. Отсюда 65000 против потолка в 60 с. Сервер также урезает ожидание до
того, что клиент способен пережить, и сообщает об этом в ответе (`wait_capped_by_client_timeout`),
а тест роняет сюиту, если какой-либо профиль в `cli-profiles.json` настроен ниже
`opencode` и Antigravity **не** делят одну форму MCP-конфига. Написание одного в формате другого
молча проваливается: сервер просто никогда не регистрируется, и симптом — «инструментов `pair_*`
не существует», а не ошибка конфига.

**OpenCode** — `mcp` отображает имя сервера прямо на его конфиг. Уровня `servers` нет.
Ключ обязан быть `type: "local"`, `command` обязан быть **массивом строк**, а `args` не существует.
Схема: `#/$defs/McpLocalConfig`, `additionalProperties: false`.

```jsonc
"mcp": {
  "pair": {
    "type": "local",
    "command": ["sh", "mcp/pair_mailbox/serve.sh", "opencode"],
    "enabled": true,
    "timeout": 65000
  }
}
```

**Antigravity** — `mcpServers`, `command` — строка, а `args` — отдельный массив.

```json
{ "mcpServers": { "pair": { "command": "sh", "args": ["mcp/pair_mailbox/serve.sh", "agy"] } } }
```

Третья ловушка того же семейства: ключ разрешений OpenCode — это **`bash`**, а не `shell`. `"shell": "ask"`
проходит валидацию схемы (неизвестные ключи проваливаются через `additionalProperties`) и ничего не делает
вообще, поэтому команды shell тихо переставали запрашивать подтверждение. Валидные ключи включают `read`, `edit`,
`glob`, `grep`, `list`, `bash`, `task`, `webfetch`, `websearch`, `skill`, `external_directory`.

Проверяйте, а не доверяйте, особенно после обновления OpenCode:

```sh
# editor validation: $schema is already in the file
# or check by hand (jsonc allows comments, so plain json.load is not enough):
./install.sh --check
```

Живая форма любого поля — в `https://opencode.ai/config.json` под `$defs`. Если изменение конфига
кажется ни на что не влияющим, ответ — в этом файле.

## ROLE-BUG 2026-10-07: чужие CLI читают наши конфиги

`omp`/`pi` (один движок `pi-coding-agent`, разные дома `~/.omp/` против `~/.pi/`)
подтягивают чужой MCP через discovery-провайдеры: OpenCode (`~/.config/opencode/opencode.json[c]`
+ проектный `opencode.json[c]` + `.opencode/`, проектный сливается поверх пользовательского),
Claude (`.claude.json`), Codex (`config.toml [mcp_servers.*]`), Cursor, Gemini,
VSCode, Windsurf.

Ключ сервера один — `pair`. Какой конфиг последний в слиянии, тот и побеждает.
Замерено вживую 2026-10-07: процесс `omp` (PID 207528), запущенный из корня репозитория,
подхватил `server.py --role opencode` из проектного
`.opencode/opencode.jsonc` — и `pair_state` вернул `you_are_writer=false`,
поэтому агент послушно отказался писать и редактировать. Никакого переключения модели/провайдера
не было: роль — это аргумент `serve.sh <role>`, а не API.

Отсюда три правила, все уже применены:

1. **Проектный конфиг не несёт идентичности.** В `.opencode/opencode.jsonc` нет
   блока `mcp` (только комментарий, объясняющий почему). Роли раздаёт только пользовательский конфиг, записанный
   install.sh. То же для любого проектного файла, который читает чужой движок.
2. **У каждого движка свой дом.** Профиль `omp` в `cli-profiles.json`
   указывает на `~/.omp/agent/mcp.json` с ключом `pair-omp`, а не на
   `~/.pi/agent/mcp.json`. Это сторожит тест `test_no_two_profiles_share_one_config_home`.
3. **Чужой discovery приглушён внутри самого CLI.** Для `omp`:
   `omp config set disabledProviders '["opencode"]'` +
   `omp config set commands.enableOpencodeProject false`.
   Без этого даже без проектного конфига `pair => opencode` подхватывается
   из пользовательского `~/.config/opencode/opencode.jsonc`.

Дополнительно `serve.sh` отказывается стартовать, когда `PAIR_ROLE` из окружения
противоречит роли из argv (выход 3): роль берётся из конфига, никогда из
env — теперь это отказ, а не комментарий.

## Руководство по плагинам тоже не согласуется с этой сборкой

Стоит знать, прежде чем доверять тому или другому. Руководство в `/v2/docs/build/plugins` документирует гораздо
более богатый `PluginContext`, чем реально поставляет OpenCode **2.0.22**: `ctx.session.hook(...)`,
`ctx.location`, `ctx.tool`, `ctx.permission`, `ctx.worktree`, `ctx.event`, `ctx.storage`. На этой
сборке реальный набор такой:

```ts
interface PluginContext {
  options; agent; aisdk; catalog; command; integration; plugin; reference; skill
}
```

А у `CommandDraft` есть только `list` / `get` / `update` / `remove` — он не умеет `add`. Поэтому кастомные
команды нельзя зарегистрировать из плагина здесь, и `/pair-status` с `/pair-handoff` —
это markdown-файлы в `.opencode/commands/`. Этот путь — настоящая фича, а не
обходной путь, и он перезагружается при сохранении.

Два следствия, которые стоит усвоить:

- **Пакет — `@opencode-ai/plugin`, а не `@opencode/plugin`**, как показывают примеры руководства,
  и он резолвится только из собственного каталога установки OpenCode. Проектно-локальный плагин не может
  его импортировать. Поэтому `pair-guard.ts` вообще ничего из него не импортирует: `define()` в этом пакете —
  тождественная функция, так что `export default { id, setup }` в точности эквивалентно и убирает целый
  класс ошибок резолва. Этот импорт был причиной первой
  ошибки *«Cannot find package '@opencode/plugin'»*.
- **Когда что-то выглядит не так, читайте установленные типы**, а не доки:

```sh
cat ~/.opencode/node_modules/@opencode-ai/plugin/dist/v2/promise/context.d.ts
cat ~/.opencode/node_modules/@opencode-ai/plugin/dist/v2/effect/agent.d.ts
opencode --version
```

## То, что вас удивит

**MCP-инструменты Antigravity по умолчанию — Ask.** Разобрано выше; это самая частая причина, по которой
корректная конфигурация выглядит сломанной.

**Роли запечены в конфиг, а не в окружение.** Это намеренно: сервер должен знать, какой
процесс есть какой, а роль, которую процесс может назначить себе сам, — не идентичность.

**Оба агента должны работать из одного каталога.** `--state .pair` разрешается относительно рабочего
каталога процесса. Два разных каталога — это два пустых почтовых ящика и молчаливый отказ.

**Мёртвый агент держит запись в ростере, пока кто-то её не вычистит.** `bin/pairctl roster`
показывает, что зарегистрировано; `--prune` убирает роль, только когда её процесс мёртв **и**
её панель либо исчезла, либо принадлежит другой живой роли. Одного факта недостаточно: после
краша живая панель может оказаться открытым вами shell. Если оставить как есть, две мёртвые записи с общей
живой панелью заставят супервизора пропустить живого пира.

**Оба CLI поставляются по нескольку раз в неделю.** Перепроверяйте части, которые скорее всего уедут:

| если это изменилось | перепроверьте |
|---|---|
| определения агентов | `.opencode/agents/*.md`, `.agents/agents/*/agent.md` frontmatter |
| MCP-конфиг | `mcp` в `opencode.jsonc`, `mcpServers` в `.agents/mcp_config.json` |
| разрешения | `permission.edit: deny` у `verifier`; `mcp(pair/*)` в Antigravity |
| API плагина | `pair-guard.ts` против `node_modules/@opencode-ai/plugin/dist/v2/promise/context.d.ts` |

Ничего в протоколе ни от чего из этого не зависит. Принуждение живёт в `server.py`, который
есть plain MCP поверх stdio и не имеет мнения о том, какой агент его вызывает.

## Откат
```sh
bin/pairctl release        # stop anyone from editing
bin/pairctl reset --yes    # wipe state, mailboxes, notes, transcript, patches
```

Чтобы убрать спаривание целиком: удалите запись `pair` из обоих MCP-конфигов, удалите
`.opencode/` и `.agents/`, если добавляли их только ради этого.
