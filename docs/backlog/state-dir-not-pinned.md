## Где

`mcp/pair_mailbox/serve.sh:19` — `state="${2:-.pair}"`
`install.sh:61` — в конфиг пишутся ровно два аргумента, состояние не передаётся
`.opencode/plugins/pair-guard.ts:89-95` — поиск `.pair` вверх по дереву
`bin/pairctl:31` — читает `PAIR_STATE`, который сервер не читает вовсе

## Что сломается

Три правила разрешения пути состояния на три компонента:

- **сервер**: `serve.sh` берёт `.pair` относительно текущего каталога, `install.sh`
  не передаёт путь, поэтому MCP-сервер всегда стартует с `.pair` от cwd агента;
- **плагин** ищет `.pair/state.json` вверх по дереву от cwd;
- **утилиты человека** (`pairctl`, `pairchat`, `pairdoctor`, `pairwatch`) читают
  `PAIR_STATE`, который сервер не читает вообще.

Воспроизведено: запуск сервера из вложенного каталога создаёт
`nested/deep/.pair/state.json` — **второе независимое состояние в одном проекте**.
Плагин покажет писателя из корневого `.pair`, сервер ответит из вложенного. То
есть плагин, который существует именно чтобы агенты не сошлись во мнении о
писателе, сам может стать источником расхождения.

`PAIR_STATE` при этом выглядит как рабочая настройка: её печатает подсказка
`server.py:1419`, и по ней работают утилиты, — но не сервер.

## Почему отложили

Раунд был в режиме `audit` (`bin/pairctl mode audit`): работа раунда — evidence, а не diff, поэтому правка кода в нём не делалась. Находка подтверждена соседом и ждёт отдельного раунда `fix`.

## Что сделать

1. Один резолвер пути состояния, используемый всеми: сервер, плагин и утилиты.
2. `serve.sh` должен принимать путь из `PAIR_STATE` при отсутствии `$2`, иначе
   переменная половина работающей идеи.
3. `install.sh` писать в конфиг явный `--state`, а не полагаться на cwd.
4. Тест: запуск из вложенного каталога не создаёт второго `.pair`.
