## Где

`mcp/pair_mailbox/server.py:154-164` (`Store._load` уходит в `default_state()`)
`mcp/pair_mailbox/server.py:574` — имя файла `{seq:06d}-{stamp}-{role}.json`
`mcp/pair_mailbox/server.py:226-236` (`atomic_write_json` → `os.replace`)

## Что сломается

`Store._load` при `JSONDecodeError` молча возвращает `default_state()` — только строка
в stderr. `seq` и `seen` при этом откатываются в ноль.

Имя файла сообщения строится из `seq`, а запись идёт через `os.replace`, то есть
**перезаписывает**. Воспроизведено:

- два сообщения отправлены и прочитаны, затем состояние испорчено, отправлено
  третье — `pair_read` вернул `seq=1` (новое) **раньше** `seq=2` (старое), в ящике
  два файла `000001` одновременно;
- в варианте с той же секундой файл перезатирается целиком, и предыдущее
  сообщение **исчезает безвозвратно**.

Заодно молча теряются `writer` (человеческое `assign` забыто), фаза (откат в
`scoping`) и `round`. В транскрипте следов нет: §11 называет транскрипт землёй
для восстановления прогона, а восстанавливать тут нечего.

## Почему отложили

Раунд был в режиме `audit` (`bin/pairctl mode audit`): работа раунда — evidence, а не diff, поэтому правка кода в нём не делалась. Находка подтверждена соседом и ждёт отдельного раунда `fix`.

## Что сделать

1. Не откатывать `seq`/`seen` при порче: сохранять последнее прочитанное значение
   отдельным файлом или монотонной счётчиковой меткой, не зависящей от `state.json`.
2. Имя файла не должно совпадать при откате счётчика — добавить в имя счётчик,
   растущий независимо, либо uuid.
3. Порча состояния — событие аудита: писать в транскрипт `state_corrupt` с содержанием
   файла, а не только в stderr.
