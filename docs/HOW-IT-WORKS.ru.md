# Как это работает

Простое описание, без деталей. Если нужно «почему так» — см.
[`PROTOCOL.md`](./PROTOCOL.md); этот файл — про «что делать».

> Язык: это русское зеркало. Английский оригинал —
> [`HOW-IT-WORKS.md`](./HOW-IT-WORKS.md).

## Что это

Два агента в одном проекте, на разных программах, с одним сервером между
ними. Сервер не просто передаёт сообщения: он ещё следит за правилами и
не даёт их нарушить.

Правил три, и они настоящие, а не пожелания:

1. **Код правит ровно один агент.** Не «договорились между собой» — второй
   получит отказ от сервера.
2. **Правки приходят запечатанными.** Второй не может править файлы; он предлагает
   патч файлом, а писатель проверяет хеш и применяет его.
3. **Каждый отказ попадает в журнал.** Включая попытку обойти правило.

## Зачем два агента, если хватит одного

Один агент принимает собственные решения за правильные. У него нет повода искать
в своём коде то, о проверке чего он не подумал. Второй агент — это другой контекст
и часто другая модель. Он читает то же самое и думает независимо.

Отсюда правило: **двое вежливо соглашаются — это ничего не стоит.** Стоит
чего-то найденная конкретная ошибка или проверенный факт. Молчаливое согласие —
не результат.

## Три слова

| слово | значение |
|---|---|
| **писатель** | тот, кто правит код. Ровно один. |
| **критик** | тот, кто не правит. Читает, ломает, предлагает. |
| **человек** | тот, кто даёт задачу и решает. Агенты не решают за него. |

Роль — это имя программы, а не выбор агента. У вас две программы,
поэтому одна пишет, а другая ломает. Кто есть кто — решает действующая
договорённость (`bin/pairctl roles`) или, если её нет, заявка — и агент обязан
назвать причину («я уже нашёл, где чинить»), а не «потому что я первый».

```sh
bin/pairctl           # власть человека: задача, режим, автономность, ok, статус
pairup                 # быстрый старт из папки проекта: сверхвизор-если-мёртв + пара
bin/pair-duo --swap-critic <cli>  # заменить панель критика, писатель не тронут
bin/pairpilot         # супервизор: перезапускает умершего агента, подтверждает
                      # разрешения по списку, будит роль с непрочитанной почтой, пишет отчёт
bin/pairchat          # переписка этой пары, вживую
bin/pairboard         # самодостаточный HTML-снимок состояния, без сервера
bin/pairctl all       # все проекты сразу: кто пишет, кто молчит
bin/pairwatch         # ловит зависшего агента
bin/pairdoctor        # проверяет, что всё на месте
```

Стоящая расстановка пинит только писателя (`bin/pairctl roles --writer X`);
критик — любой второй живой, CLI с кончившимися лимитами меняется через
`pairup --swap <cli>` без бумажек. `finish.sh` — тяжёлый путь первого раза
(установка + полные тесты); `pairup` — на каждый день (секунды).

Команды запуска живут в `cli-profiles.json`: шесть профилей (`opencode`, `agy`,
`codex`, `claude`, `pi`, `omp`).
Сервер предоставляет 22 MCP-инструмента `pair_*`. Состояние пары живёт в `.pair`:
`state.json`, `transcript.jsonl` и хранилища `mailbox/`, `notes/`, `patches/`,
`obligations/`, `notifications/`.

`bin/pairpilot` не может двигать фазы, давать или отбирать право записи, коммитить
или трогать файлы проекта. Он наблюдает и докладывает.

`.pair/tasks.md` — журнал сессии, собранный из состояния, поэтому он не может
разойтись с фактами: что просили, что сделано, что доказано, что осталось.

## Две оси работы

`mode` говорит, зачем этот раунд. `autonomy` — как далеко он идёт без вас. Это
разные вещи, и смешивать их было бы ошибкой.

```sh
bin/pairctl mode fix          # по умолчанию: код меняется
bin/pairctl mode audit        # код не меняется, только находки

bin/pairctl autonomy auto     # по умолчанию: работает сам, закрывает раунд при наличии доказательств
bin/pairctl autonomy semi     # работает сам, но закрывает только по вашему слову
bin/pairctl autonomy observe  # только сообщает; человек за рулём
```

Вас спрашивают **не больше одного раза**, а по умолчанию не спрашивают вовсе:
уровень выбирается при старте пары, а не пересматривается посреди раунда.

```sh
pairup --task "autonomy: semi сделать дело"   # или pairctl autonomy semi
```

Без флага запускалка решает в таком порядке, от сильного к слабому: флаг, затем
`autonomy: semi` в первой строке задачи, затем `.pair/autonomy`, затем `auto`.
Источник записывается в журнал как `via=flag|task|file|default`, поэтому уровень,
за который никто не может отчитаться, потом никогда не становится загадкой.

Режим агенты читают сами при первом `pair_state`. О том, что вы его
переключили, они **не** узнают, поэтому после команды **скажите одну строку в их окна**.

Заметьте: `observe` — это не «проверки выключены»: доказательства для закрытия
раунда требуются в любом режиме. `observe` означает лишь, что супервизор не станет
перезапускать агентов и ваше слово не требуется.

### fix — чиним

```sh
bin/pairctl task "починить ретраи при 502"
```

Работают вдвоём: **один пишет код, второй ломает.** Не оба сразу. Второй не может
править файлы — для этого у него есть механизм патчей, который предлагает, а не
применяет.

Список задач — только дописываемый. Вторая задача не перезаписывает первую:

```sh
bin/pairctl tasks                        # что открыто, что закрыто
bin/pairctl task --done 2                # готово
bin/pairctl task --drop 3 --reason "покрыто PR #5"
```

Раунд не может закрыться, пока открыта задача, а брошенной задаче нужна причина.
Это намеренно: агент, который переключился на новую задачу и забыл старую, —
обычный вид отказа, и здесь он не проходит молча.

Кто пишет:

```sh
bin/pairctl why
```

Пишущему в окно:

```
режим fix, ты пишешь. Начни с задачи, которую я записал.
```

Второму в окно:

```
режим fix, ты критик. Не правишь — предлагай патчи.
```

### audit — смотрим

```sh
bin/pairctl task "найти гонки в store"
bin/pairctl mode audit
```

Работают вдвоём: **оба ищут дефекты, оба пробуют сломать находку другого.**
Код не меняет никто. Патчи сервер отвергает — в раунде, где ничего не меняется,
предлагать нечего.

Находка считается найденной, только если её подтвердили оба. Не смог сломать —
`confirmed`; смог — `refuted`, с причиной.

Подтверждённые находки кладутся в `docs/backlog/`. Это единственные файлы, которые
такой раунд создаёт, и это же готовый вход для следующего раунда починки.

### Если переключили режим, скажите соседям

```sh
bin/pairctl mode fix
```

Состояние изменилось, но агенты не узнают об этом, пока вы не скажете. По одной
строке в каждое окно. Что именно писать — зависит от того, кто сейчас пишет:

```sh
bin/pairctl why
```

## Типовые сеансы

**Просто починить.** `pairctl task "..."` → по строке в оба окна → они работают →
смотрите `pairchat`.

**Сначала посмотреть, потом чинить.** `pairctl mode audit` → работа → находки в
`docs/backlog/` → `pairctl mode fix` → строка в окна «берём из docs/backlog/» →
работа.

**Починка разрослась, нужен шаг назад.** `pairctl mode audit`. Сделанное остаётся
сделанным.

**Новый раунд.** Задача отображается в обоих окнах (баннер, раунд 53), а критик получает толчок, если писатель молчит. Переход из `scoping → plan` требует `.pair/intent.md` (Проблема, Границы, Ожидаемый результат). Писатель создаёт `.pair/plan.md` — `round: N`, Цель, Инварианты, Критерии приёмки — и отправляет соседу на визу. Переход `plan → implement` отклоняется сервером до получения визы (или истечения окна ожидания); шаги назад и повторное открытие раунда не блокируются никогда (docs/PROTOCOL.md §6). В ходе выполнения потолок бюджета (`budget ceiling`, §10d) защищает от бесконечных циклов раунда по машинным метрикам (сообщения, продвижения фаз, астрономическое время, перезапуски); продвижение вперёд блокируется при превышении, тогда как `done` и шаги назад всегда остаются доступными. При переходе в `done` автоматически создаётся машинная квитанция (`Task Receipt`, `.pair/RECEIPT-<round>.md`) с задачами, доказательствами и финальными метриками бюджета.
При обнаружении регрессий или негативных доказательств (`ok=false`) в фазе `done` петля самовосстановления `pair-heal` (§10f) автоматически возвращает раунд в `implement` (не более 3 попыток).
В `mode=fix` раунд не закрывается без доказательств обоих видов от писателя: `test` и `ground-truth` (PROTOCOL §5a, §5d) — заявления сверяются с деревом (факты дерева, вердикт `anti-mock`, `verify-ground-truth`), а не с памятью.
Сброс лимитов: `bin/pairctl budget --reset`.

## Что видите вы

```sh
bin/pairchat                 # живая переписка
bin/pairchat --once          # разово, и выход
bin/pairctl all              # все проекты, кто молчит, что за задача
bin/pairctl log --limit 50   # что делали, включая каждый отказ
bin/pairctl status           # этот проект и что мешает закрыть раунд
bin/pairctl roster           # кто зарегистрирован
```

Человек вмешивается только в шести вещах: секреты и токены, цели и порты деплоя,
деплои, миграции баз данных, удаление данных, удаление истории git. Всё остальное
агенты решают между собой.

Агентам запрещено просить вас пересылать сообщения между окнами: они будят друг
друга напрямую через `pair_deliver`.

## Что не сработает

**Агент просит вас передать текст в соседнее окно (ручная пересылка через человека).**
Это ошибка поведения агента: для активной передачи сообщений и передачи эстафеты
существует `pair_deliver`. Человек дал задачу и ждёт результат (PR), а не работает
ручным роутером.

**В CLI всплыл запрос подтверждения.**
Если агент заблокировался на интерактивном вопросе, сосед может вызвать
`pair_unblock`, либо фоновый `bin/pairwatch --unblock` нажмёт его — но только для
того, что разрешает список (§13b протокола). Отвечают не на каждый запрос: `curl`
или `rm -rf /` остаются без ответа намеренно, и это не ошибка, которую нужно
обходить. Обрабатываются обе формы: вопрос `[y/N]` и меню TUI, где нажимается
только `Enter`.

**Агент молчит.** Значит, он ушёл. Проверьте `bin/pairctl all` — там видно, кто
давно не отвечал. `bin/pairwatch` ловит это раньше, чем заметите вы.

**Завис один агент.** Обычно он ждёт ответа, которого не будет.
Помогают `bin/pairdoctor` и перезапуск панели.

**Раунд закрыли, а потом нашли дефект.** Фазу можно отвести на шаг назад, это
делает кто угодно, без права записи: агент сам вернёт раунд, если нашёл что-то
после закрытия.

**Один агент работает второй час.** Никто не мешает ему закончить.
`pairwatch` покажет тишину, решение — ваше.

## Git Worktrees (S5)

Для изоляции файловой системы и параллельной работы нескольких пар:
- `pairup --worktree <ветка>` (или `-w <ветка>`) создаёт `.worktrees/<ветка>` и изолирует сессию.
- `pairctl worktree list` выводит все активные деревья.
- `pairctl worktree prune` очищает удалённые деревья.

## Машинный гейт слияния PR и Feature Freeze (раунд 60)

Слияние PR защищено машинными проверками до того, как мастер получит код:
- `bin/pairctl pr merge [pr_id]` — гейт проверяет:
  1. Фаза раунда строго `verify`.
  2. В раунде есть успешное свидетельство тестов (`kind="test"`, `ok=True`), и это свидетельство называет head, который сливается (раунд 138).
  3. head PR'а равен локальному HEAD — слияние везёт head PR'а, поэтому гейт, смотревший на другой коммит, заверял бы код, который никто не проверял (раунд 138).
  4. Есть одобрительный вердикт от независимого критика (self-approval писателем запрещён).
  5. Вердикт свеж на текущем HEAD (нет новых коммитов или незакоммиченных правок после ревью).
- Обход: `--force` требует обязательный аргумент `--reason <причина>` и фиксируется в журнале (`pr_merge_forced`).
- Feature Freeze: Любой коммит на фазе `verify` делает вердикт stale, блокируя и слияние PR, и закрытие раунда.
- **Никогда не сливайте прямым `gh pr merge`.** Он выполняется вне сервера, поэтому ни одно правило этого репозитория не может его отклонить, а журнал не узнаёт о слиянии (PROTOCOL §10g). В раунде 115 слили так, и слияние пришлось чинить руками.
- **Режьте ветку следующего раунда от свежего `origin/master`**, а не от ветки предыдущего раунда. Squash-мерж выбрасывает ветку раунда из истории master: следующий коммит по ней попадает в add/add конфликт, а CI не запускается вовсе — PR без checks читается как зелёный.
