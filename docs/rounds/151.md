# Round 151 — two borrowings from herdr: the logical line, and waiting for a condition

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-151-herdr-borrowings`
- **Writer**: omp · **Critic**: agy
- **Base**: `dev` (the human's directive: dev only, `master` untouched)
- **Deliverable**: a pane capture that returns the LOGICAL line instead of the
  terminal row, and a reconnect command that waits on predicates instead of
  blind sleeps — the two borrowings from `herdr` that this project actually
  needed — plus the two debts the gate found on the way: a merge trail that
  had lost ten events, and a test that only failed under load.

Source: the human's request to study `https://github.com/herdrdev/herdr` and

## The two defects this round started from

**A pane read in fragments.** `capture` ran `tmux capture-pane -p`, which
returns the terminal's ROWS. A pane narrower than its text split every long
line into several rows, and every consumer of the pane — the permission
detector, the composer recogniser — reads ONE line at a time. A permission
prompt whose marker fell onto the second row was therefore invisible, and the
pilot sat on a question it could not see.

**A reconnect that guessed.** `bin/pairmcprestart` sent `/mcp`, slept 6
seconds, sent the filter, slept 2, toggled, then slept 3 seconds ten times
hoping the server process would appear: 38 seconds of waiting even when the
picker was on screen in 300ms — and still not enough when the handshake took
longer than 30 seconds. The waits were numbers with no condition attached.

## The two slices

### A — the capture returns the logical line (`composer.py`)

`capture` now asks tmux for the LOGICAL line with `-J` (tmux >= 2.3): the
terminal's soft-wrapped rows come back joined into the line the program
actually wrote. The fallback matters as much as the flag: an old tmux without
`-J` errors out, and the capture then runs the plain form — an empty pane must
never read as "busy", because busy hides the delivery bug the flag exists to
fix.

The risk `-J` carries is the FRAME. A TUI's bottom edge is wider than the
pane; the plain capture then shows the corner on the first row and the rest of
the edge on the second, and the corner-led geometry is gone — the pane reads
busy forever. With the joining the edge comes back whole, corner first, and
`composer_line` finds it again. This is measured, not assumed: the live test
writes a `╹▀▀▀…` edge wider than the pane into a real 40-column tmux session
and asks the detector for the input field.

The test file is `mcp/pair_mailbox/test_composer.py` — the live tmux pane is
the only honest subject here; stubbing the capture would prove the flag is
spelled right, not that tmux joins the rows.

### B — waiting is a condition, not a number (`mcp/pair_mailbox/wait_until.py`)

`wait_until.py` holds one duty: poll a predicate until it holds or the
deadline passes. The deadline is monotonic, so a clock jump cannot extend or
shorten the wait. A predicate that raises means "not yet", never a crash — the
condition "the server process exists" raises on some platforms when the
process tree is missing. A timeout returns False; it never raises, because
"the condition did not arrive" is a normal answer.

`bin/pairmcprestart` now waits on three predicates: the `/mcp` picker must
DRAW (its own chrome: a row of MCP servers), the filter must narrow to the
pair row, and the server process must APPEAR. Each deadline is a ceiling, not
a guess — the poll ends the moment the condition holds.

## Two debts the gate found on the way

The full gate is run on the round's own tree, and it found two things that
were not part of the plan. Both are recorded here because a round card that
hides the detours is a card that misleads the next reader.

### The merge trail had lost ten events

`scripts/merge-audit-trail.py` failed: 97 merged PRs, 17 with a merge record,
80 without, and ten of the missing ones (72–75, 77–82) were not named in the
baseline. They were not missing because they escaped the gate — they were
missing because the journal's ROTATION window had moved them out. Measured:
the archives now begin at 2026-10-21T09:03Z, while round 150 measured the
oldest surviving event as 2026-10-20T06:51Z, and the journal's first merge
record was PR 72.

The repair is the one the protocol already names for this exact case
(§10g.6): `pairctl pr merge-record <pr_id>` reads the remote's real merge
state, refuses a PR that is not merged, refuses a `--head` that disagrees with
what GitHub reports, and appends `pr_merge_repaired` naming the real merge
commit. All ten were repaired through it, each verified against the remote
(`f5cb837b0348`, `dc19ae09f442`, `b3babb020860`, `259116c6f799`,
`6a451e0e6f0d`, `8fc167b8bf7a`, `3e15184ddf8d`, `c77d2868878f`,
`eb296139bd99`, `09a227ead821`). The audit then reported PASS: 97 merged, 27
with a record, 70 without, all 70 named in the baseline.

The baseline was NOT extended, and that is the point of the protocol's
distinction: the baseline says "this merge left no trace", and for these ten
that would be false — the trace existed and could be named. An event written
NOW for a merge that happened then is a repair; an event written into the
past would be a forgery.

**What this leaves open.** The rotation window is still four archives, so the
next ten merges will be lost the same way. Widening it trades disk for
memory, and no measurement in this round says which is right; that is the next
round's question, not a change to slip in here.

### A flaky test that only failed under load

`mcp/pair_mailbox/test_watchdog.py` failed inside the gate and passed in
isolation. The cause is a race the test never guarded: `subprocess.Popen`
returns as soon as the FORK succeeds, and the child may not have `execve`'d
yet — until it does, `/proc/<pid>/cmdline` is EMPTY, and the watchdog reads
exactly that file. Measured here: **137 of 300 spawns had an empty cmdline
the moment `Popen` returned.** Under the gate's parallel load the window
widens and the test fails.

One test in the same file already knew about this race and fixed it with a
`time.sleep(0.05)` — a guess that loses under load. The fix here is a
predicate: `_wait_for_exec` polls until the child's argv is readable, and the
five tests that spawn a real process now wait on that condition. Verified: 8
consecutive clean runs, and 6 more with six competing processes loading the
machine — all OK.

The PRODUCTION behaviour is deliberately unchanged: `tool_pids` still reads an
empty argv as "the process is gone". The pilot scans the tree on its own
cadence, and a tool that is still forking has not been running long enough to
be the thing the monologue detector must notice. Making the production path
wait would add a delay to every scan for a window that closes in microseconds.


## The honest limits

- **`-J` needs tmux >= 2.3.** Older tmux takes the fallback path, and the
  wrapped-line defect is then still there — degraded, not fixed. The fallback
  is exercised by the test so the degradation is known, not assumed.
- **The `-J` capture is a plain `capture-pane`, not a live screen.** It reads
  the pane's visible rows; a line the program wrote but the terminal has not
  yet scrolled into view is still not seen. That limit is the same as before
  the flag.
- **The reconnect's handshake signal is the process.** `server_pid` matches
  `server.py --role <role>` on the command line. A server launched under a
  different command line would not be found, and the command would report the
  failure it actually hit rather than claim a reconnect.
- **The live stub test was a throwaway.** It proved the tool's three branches
  against a real tmux pane and a real process; it is not part of the tree,
  because a stub that mimics a CLI's picker is a fixture that rots. The
  permanent coverage is `bin/pairmcprestart_test.py`.

## Rollback

The round is one branch, squashed into one commit by the merge. Reverting THE
MERGE removes the `-J` capture and its fallback, the `wait_until` module, the
predicate waits in `bin/pairmcprestart`, the two gate registrations, the
round card, and the watchdog test's exec-wait. Nothing else in the project
depends on the new module: `wait_until` has one caller —
`bin/pairmcprestart` — and `composer.capture` keeps its signature and its
fallback.

The merge-trail repair is NOT undone by reverting the merge: the ten
`pr_merge_repaired` events live in the pair's journal, not in the repository,
and they record merges that really happened. Reverting the merge would leave
the audit green and the history true.
