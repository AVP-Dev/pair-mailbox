# Round 134 — what the context actually costs: a measured token budget, and the variants that pay

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-134-token-budget`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: analysis only. This round changed no code — the human's directive was
  analysis and calculation, so the output is this document plus the backlog cards it
  names. Every number below was measured, not estimated.

## The question

The round's task: analyse and calculate the variants for optimising tokens and session
memory — compressing plans and checklists, keeping the key context (key facts / memory /
sqlite), cutting context bloat without losing history, and a comparative savings
calculation.

Four hypotheses arrived with the task. Three survive the measurement, one is right about
the symptom and wrong about the cause, and the measurement found a fifth sink that no
hypothesis named.

## How the numbers were taken

- **Tokenizer**: `tiktoken` `cl100k_base`, applied to the exact payload strings.
  Other models tokenize differently; read every figure below as ±5–10 %.
- **Room side**: a real `PairSession` bound to this repository's live `.pair`, so the
  payloads are the ones the tools actually return — not a reconstruction of them.
- **Session side**: the real `~/.omp/agent/sessions/<project>/*.jsonl` files, parsed and
  bucketed by role and by tool.
- Anything that is an estimate says so.

## Part 1 — the room side: what one orientation costs

The live room at round 134: 137 tasks (1 open), `state.json` 161 428 B, `notes/` 3.4 MB.

| call | chars | tokens | what it is |
|---|---:|---:|---|
| `pair_task list` | 77 906 | **29 784** | every task ever opened, with its metadata |
| `pair_note_index` | 21 635 | **8 065** | metadata only — 229 notes, 5 fields each, no content |
| `pair_transcript` (limit 0, whole trail) | 185 077 | **80 832** | the append-only audit trail |
| `pair_transcript` (limit 20, default) | 5 408 | **2 358** | the same trail, windowed |
| `pair_note_read decision` (tail) | 12 047 | **5 122** | 120 lines of a 77 KB note |
| `pair_note_read finding` (tail) | 13 397 | **4 391** | 120 lines of a 63 KB note |
| `pair_note_read handoff` (tail) | 9 962 | **4 373** | 120 lines of a 76 KB note |
| `pair_note_read plan` (tail) | 8 110 | **3 166** | 120 lines of a 64 KB note |
| `pair_state` (full) | 3 848 | **1 181** | roster, authority, done-blockers |
| `pair_state` (cached, unchanged) | 125 | **35** | the same, when nothing moved |
| `pair_digest` | 1 153 | **408** | the orientation slice, under a 500-token cap |

**The one call that costs the most returns the least.** `pair_task list` costs 29 784
tokens to say that exactly one task is open. The growth is linear in the number of
tasks ever opened: 217 tokens per task, and this repository opens roughly one task per
round — so the call crosses 30 000 tokens at round ~138 and reaches ~65 000 by round
300. Nothing about it is a bug; it is the tool doing what it says.

**The metadata call is not free.** `pair_note_index` promises to show the heap "without
reading the contents", and it does not read a single byte of them — but 229 rows of
five fields cost 8 065 tokens. It is the second most expensive call in the room, and
the part of its answer an agent acts on — which notes are worth reading — is a handful
of rows, not 229.

**The state file is the task list wearing another hat.** `state.json` breaks down as
tasks 77 864 B (48.2 %), evidence 31 409 B (19.5 %), patches 9 380 B, verdicts
5 847 B; `.pair/tasks.md` is the rendered 96 862 B twin of the same list. The card
`docs/backlog/state-json-grows-unbounded-because-rotation-needs-a-design-round.md`
already names the growth; the measurement here adds its price.

**What compaction actually keeps.** Seven compactions in that session, method

| before | after |
|---:|---:|

Compaction works — it removes ~90 % of the context — but the floor it leaves is
**39 513–49 131 tokens**, and the compaction row itself is 34 831–39 814 tokens of it.

The context also reached 790 583 tokens before a compaction fired.

**On disk**: `~/.omp/agent/sessions` is 411 MB over 16 project directories; this
project's own is 95 MB.

## Part 3 — the four hypotheses, checked

**1. "The task list returns the whole history" — confirmed, and it is 2.4× worse than
first estimated.** The measured cost is 29 784 tokens per call, not ~12 000. The gap is
the tokenizer: at 2.6 characters per token in Russian, dividing characters by four
undercounts by a factor of 2.4. Any estimate of this kind made on character counts
alone is worth re-measuring.

**2. "Plans and checklists are forwarded in full" — confirmed, on both boards.** The
pair board renders 137 tasks into a 96 862 B `tasks.md`, and the harness board costs
386 tokens per `todo` call (27 401 over 71 calls) because each call returns the whole
board. Neither board is wrong; both are re-read whole on every call.

**3. "Command output is not compressed" — half right, and it points at the wrong
sink.** `bash` output averages 323 tokens per call in the long session, which is
ordinary. The context sink is the *call machinery*: the tool-call records are
915 434 tokens (30.1 %) and the `custom` rows store the same payload a second time
(330 999, 10.9 %) — 41 % of the context. The arguments inside those calls are
394 513 tokens, of which 232 065 are whole files handed to `write` and `edit`. The
fix is "do not pass whole files", not "compress stdout".

**4. "Key facts need a persistent anchor" — confirmed, and the anchor already exists,
but it is prose.** After every compaction the agent carries 39 513–49 131 tokens of
summary text, which is exactly the "key context" the task asks about — except that it
cannot be queried, cannot be diffed, and costs ~40 000 tokens to keep alive. A
structured facts surface of 200–500 tokens carries the same invariants for ~1 % of the
price.

**5. The sink nobody named: the harness stores each tool call twice.** The message
part holds the call; a `custom` row holds the same payload again. In the long session
that duplication is 330 999 tokens (10.9 %); in the live one, 6 557 (12.1 %).

## Part 4 — the variants, with the arithmetic

Savings are per call, on this room, with `cl100k_base`.

| # | variant | where | before | after | saved | effort | the risk |
|---|---|---|---:|---:|---:|---|---|
| A | `pair_task list` returns open tasks + counters; history behind an explicit scope | `mcp/pair_mailbox/server.py:2616` | 29 784 | ~150 | **29 634** | S | a caller that relied on the full list must ask for it; the tool description and the digest must say so |
| B | `pair_note_index` returns the N freshest notes + totals, with paging for the rest | `mcp/pair_mailbox/server.py:3149` | 8 065 | ~300 | **7 765** | S | an agent may not see an old note; the count and total bytes must stay visible |
| C | `pair_note_read` budgets tokens, not lines | `mcp/pair_mailbox/server.py:3176`, `NOTE_READ_DEFAULT = 120` (`server.py:158`) | 3 166–5 122 | ≤ 800 | 2 400–4 300 per note | S | a token cut can split a record; the cut must land on a record edge, as the line cut already does |
| D | a structured facts anchor, carried by the digest, replacing prose as the thing that survives a compaction | `mcp/pair_mailbox/digest.py`, `tool_pair_digest` (`server.py:3351`) | 39 513–49 131 tokens kept alive | 200–500 | **~39 000 per compaction** | M | needs a decision: where facts live (`state.json` vs `.pair/facts.json`) and who writes them |
| E | boards carry open items and deltas; closed items leave the read path | the `todo` board, `.pair/tasks.md` | 386 tokens per call; 96 862 B | ~60 | ~320 per call | M | the same design round the `state.json` card already asks for |
| F | no whole files in call arguments — read by range | agent practice, guided by the skills | 232 065 tokens of whole-file arguments in one session (7.6 % of that session, 59 % of all call arguments) | range reads | 232 065 tokens per session of that shape | S (guidance) | none at the tool level; the tools already accept ranges |
| G | trim finished session files | `~/.omp/agent/sessions` | 411 MB (95 MB this project) | disk | **0 tokens** | S (harness) | not this repository's debt — a disk bill, not a context bill |
| H | compact at a bounded threshold instead of at 790 583 tokens | harness | peak 109 070–790 583 | ~120 000 | peak context | M (harness) | harness-side; the peak is what a window has to hold |

**The sweep arithmetic.** A full orientation sweep today — task list, note index, four
note tails, the windowed transcript, full state — costs
29 784 + 8 065 + 17 052 + 2 358 + 1 181 = **58 440 tokens**.

With A, B and C applied: 150 + 300 + 3 200 + 2 358 + 35 = **6 043** — a saving of
**52 397 tokens per sweep (−89.7 %)**. With the digest used instead of a sweep:
**408** (−99.3 %).

**The routine orientation** — digest, state, one task list, one note index — costs
38 292 tokens today (408 + 35 + 29 784 + 8 065) and **893** after A and B (−97.7 %).

## Part 5 — the order of work

1. **A** — the largest single win, one branch of one function, and it removes a call
   that the digest already answers.
2. **F** — guidance only, no code: 232 065 tokens of one session's context were whole
   files handed to `write` and `edit` — 7.6 % of the session, 59 % of all call
   arguments.
3. **B**, **C** — the same shape as A: a bound on what a listing call may cost.
4. **D** — the one that needs a decision before code: where a fact lives, who writes
   it, and what happens to it when the round closes.
5. **E** — with the design round the existing `state.json` card already asks for;
   the two are the same change seen from the store and from the board.

G and H are not this repository's debt, and are listed here so the human can route
them.

## Part 6 — the limits of this measurement

- One tokenizer. `cl100k_base` is a proxy; a different model's tokenizer moves every
  figure by a few per cent. The *ratios* — 29 784 against 408, 394 513 against
  27 401 — hold regardless.
- One room, one project, one week. The growth rates (217 tokens per task, ~1 task per
  round) are this repository's; another room with fifty rounds a day would grow
  faster.
- The session-side figures count what the harness *stored*. What the model actually
  paid is at most that, and less after compaction.
- The compaction floor was measured on `snapcompact`. Another compaction method keeps a
  different anchor, and the anchor's price is the number that decides variant D.

## What a reader should take away

The expensive part of this system is not the work and not the code. It is the
re-reading: the same 137 tasks, the same 229 note headers, the same 40 000 tokens of
summary prose, paid again and again by an agent that only ever needed the one open
task. Every one of those is a call with no bound on what it may cost, and a bound is
the cheapest fix available — a default that returns 150 tokens instead of 29 784
changes no protocol, breaks no rule, and is worth more than every clever compression
scheme put together.

The other half is what the agent sends: whole files as call arguments, duplicated
once more by the harness's own event log. That half is free to fix and nobody has
fixed it, because it is invisible from the tool side — the tools do exactly what they
were asked.
