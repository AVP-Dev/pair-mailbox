# Round 129 — the protocol stops promising wake adapters the code does not ship, and the changed-file gate stops running nothing

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-129-doc-contract-consistency`
- **Writer**: omp · **Critic**: agy (plan in `pair_note` kind=plan; scope ruling seq 1755)
- **PR**: [#74](https://github.com/AVP-Dev/pair-mailbox/pull/74) · ledger: task #133

## What was wrong

Round 126 audited the whole system and filed 16 cards. Round 127 fixed the
behaviour. Round 129 took the two remaining cards that were about the
CONTRACT ITSELF — the documents that tell a reader what the code does — plus
one more that turned up while the gate was running.

**The protocol promised wake adapters the pilot does not have.** PROTOCOL §7
stated, as fact, which CLI has which wake adapter. The table named OpenCode,
Antigravity, Claude and Codex. The pilot ships exactly one:
`WAKE_ADAPTERS = {"opencode": "wake_opencode"}` (`bin/pairpilot:790`). There is
no agy adapter and no `tmux send-keys` wake path — the one `send-keys` in
`pairpilot` sends `Escape` to dismiss a stuck permission prompt.

The third column ("if unsupported: reminder only") only makes sense if the
second column is sometimes empty. By that reading, three CLIs had one. The
transcript of this room measured the gap: **31 `pilot_wake_no_adapter` rows**,
zero API failures. The adapters that exist did not fail; the ones that do not
exist were never tried.

The `pair-guard` plugin was in the table too, as "plugin + host API". It is
not a wake path: it rewrites the authority brief inside the agent's own system
prompt when the shared state changes, and it pushes nothing into an idle
session. Its own docstring says the plugin API in this build exposes no
`ctx.session`.

**A protocol promise with no test behind it.** §7c says "The MCP `timeout` in
`cli-profiles.json` must therefore exceed `MAX_READ_WAIT_SECONDS`, **and a
test fails the suite if any profile does not**." No test did. The only file
that read a profile timeout checked ONE profile against a hard-coded number.
The state was correct — all six profiles carry `65000`, and 65 s > 60 s — but
the guarantee was unguarded, and the failure mode was silent: a profile added
without a `timeout` gets the conservative 20 000 ms default, and
`effective_read_wait` then caps the wait at **15 s** instead of 60 s, with the
suite staying green and the protocol saying it cannot happen.

**And then the gate turned out to be running nothing.** Running the changed-file
gate on this round's own changes produced a line that should not be possible:

```
verify-changed: files: skills/pair-work/SKILL.md
verify-changed: suites:
```

Empty. The gate ran `--only static` and exited 0. So the changed-file gate
passed having run **no suite at all**, while the map's directory rows read as
if they were covered. Two mistakes in one awk, each fatal alone: `$f` in awk
is FIELD f, not the variable f, so the comparison was between the whole record
and the first field; and `index($f, $1"/")` appended a slash to a prefix that
already ends in one (`skills//`).

Measured on the same tree: **134 tracked files selected an empty suite** — 87
whose only mapping is a directory row, and 47 with no row at all. Every
directory row was dead. The `UNKNOWN` fallback was unreachable too, because the
first awk always found a match (a comment line) and printed an empty suite.

This is the same shape the audit round found elsewhere, and the repo has now
fixed it three times: **a check whose green claims more than it checked.** A
gate that selects nothing and exits 0 is the loudest version of that.

## What was done

**The table names what the code ships.** One adapter, for OpenCode, through
the host API of the recorded session. Every other CLI — agy, Claude, Codex, Pi,
OMP — falls back to the ring: a `tmux display-message` popup, then the mailbox
letter. The `pair-guard` plugin is named in the prose and explicitly not a wake
path. Both language versions changed together, so the promise is the same in
both.

**The guard is the pilot's own map, read back.** `TestWakeAdapterTableMatchesTheCode`
in `bin/pairpilot_test.py` reads the table out of `docs/PROTOCOL.md` **and**
`docs/PROTOCOL.ru.md` and compares it with `Pilot.WAKE_ADAPTERS`: every row
promising an adapter names a role, and the set of those roles equals the
pilot's map; every CLI in `cli-profiles.json` appears in the table, so a new
profile cannot arrive undocumented.

**The timeout promise gets its test, and both halves.** `TestProfileTimeoutBudget`
in `install_test.py` asserts that every profile carries an explicit
`mcp.entry.timeout` — the missing key is the case that halves the wait, so it
fails with its own message — and that it exceeds `MAX_READ_WAIT_SECONDS`. The
constant is read from `read_wait.MAX_READ_WAIT_SECONDS`, not copied: a copy is
a second number to keep in step, and the protocol names the module's constant.

**The selector was fixed and made askable.** `suite_for()` holds the rule, so
the loop and the probe cannot disagree, and `--suite-for PATH` asks the real
script which suite a path selects. That is what makes the guard possible
without a second implementation of the rule:
`TestVerifyChangedRouting` in `mcp/pair_mailbox/test_verify_map.py` asks the
script itself.

## What the human should know

The pattern across all three defects is one pattern, not three: a document or a
gate stated a claim, and nothing checked whether the claim held. The protocol
promised adapters; the transcript collected 31 refusals nobody read. The
protocol promised a test; no test existed. The gate promised coverage; it
selected nothing and exited 0.

The fix in each case is the same shape: the claim is now derived from the code
that implements it, and a test compares them. The adapter table is compared
against `Pilot.WAKE_ADAPTERS`. The timeout promise is compared against
`read_wait.MAX_READ_WAIT_SECONDS`. The gate's selection is compared against
the map — by asking the real script, not by re-implementing its rule.

And the failure of that rule was silent in the worst way: the gate's own
output said "suites:" and nothing else, which reads like "there is nothing
more to run" rather than "nothing was selected". A gate that says it cannot
choose is better than one that chooses nothing and says nothing.
