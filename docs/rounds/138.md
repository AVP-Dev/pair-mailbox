# Round 138 — the merge gate vouches for the commit that gets merged

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-138-merge-gate-evidence-head`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the merge gate's green promise is about the code that is
  actually merged, the freshness gate stops calling a fresh server stale, and
  the merge path's rules sit where the next agent reads them.

## The defect

### 1. The evidence was bound to the round, not to the head

`bin/pairctl pr merge` refuses to merge without passing test evidence, and it
looked the evidence up by round number alone (`review_gate.py:43-49`):

```python
round_ev = [ev for ev in (state.get("evidence") or [])
            if int(ev.get("round", -1)) == cur_round]
has_test_ok = any(ev.get("kind") == "test" and ev.get("ok") for ev in round_ev)
```

The round number does not move when the head does, so a record written for one
commit kept vouching for every commit after it in the same round. The card
that recorded it measured it live: PR #77's head was `b23e7c8` while the
passing evidence named `bf3914f` — two commits behind, and itself a head whose
CI had been red. The merge was allowed, and the gate could not have refused
it: it was reading a record about another commit.

The evidence was a machine's word about *a* run. A green suite run is the only
part of the merge gate that speaks about the code itself, and it spoke about
the wrong commit.

### 2. The gate looked at the local HEAD; the merge ships the PR's head

`check_pr_merge` reads `review.git_head(repo_dir)` and binds the verdict to it.
`gh pr merge <pr_id>` merges the PR's head on GitHub. If the local checkout is
not the PR's head, the gate vouches for one commit and another gets merged.
Nothing compared the two. The critic found this while reviewing the plan; the
writer had missed it.

### 3. The freshness gate called a fresh server stale

The gate compared the runtime sources' **mtimes** with the server's start. A
merge or a checkout rewrites the mtimes of files whose bytes did not change —
and a merge brings the round's own code. Round 137's close was blocked twice
by exactly that, both times right after a merge, and the cost was about
fifteen turns of reading `ps`, `/proc` and the harness docs to work out that
killing the MCP server was the remedy.

## What changed

### A. The evidence names the commit it was measured on

- **`tool_pair_evidence` records the head** (`server.py`): the commit the
  measurement was made on. Outside a git repo there is no head to name, and
  the record says so instead of inventing one.
- **The gate compares it** (`review_gate.py`): a passing evidence whose `head`
  is not the head being merged does not count, and the refusal names both.
- **The head being merged is the PR's head** (`gh pr view --json
  headRefOid`): the gate refuses when it is not the local HEAD, and no answer
  from GitHub means no merge. `check_pr_merge` takes it as an argument;
  `cmd_pr` resolves it and fails closed.

The gate does **not** require CI: CI is the GitHub matrix, and the honest
requirement is *"the suite ran on this commit"*.

### B. The freshness gate compares content

- The gate hashes the runtime sources (the files a server loads, test files
  excluded) when the process starts, and compares that hash with the files on
  disk. Bytes differ → stale; the bytes are the same → fresh, whatever the
  mtimes say.
- The mtime stays as the report, and as the cross-process rule: the doctor
  and `pairrestart` cannot read another process's snapshot and ask the weaker
  question, which over-reports — the harmless direction. The doctor now calls
  `list_newer_than_start` for that, and the name says what it answers.
- The docstring that claimed "one rule, one answer" now says which question
  each rule answers.

### C. The rules where the next agent reads them

- **HOW-IT-WORKS (EN+RU)**: a direct `gh pr merge` is a hard error, and the
  next round's branch is cut from a fresh `origin/master`.
- **PROTOCOL §10g (EN+RU)**: the two new preconditions, and a seventh point
  for the branch rule.
- **PROTOCOL §10h (EN+RU)**: the content rule, and the agent-side restart
  procedure — the protocol had the remedy only as a human's.

### D. A card for the mechanical audit-trail check

`docs/backlog/the-merge-audit-trail-is-not-checked-automatically.md`: nothing
compares the merged PRs with the journal's events, so an escape is found by
hand or not at all. It carries the horizon question.

## The measurements

- **The red-proof, gate side**: with the two new checks disabled, an evidence
  for another head and an evidence for no head both pass the gate, and a PR
  head that differs from the local HEAD is not refused. With them on, all
  three are refused, and the reasons name the heads.
- **The red-proof, freshness side**: the old rule on a merge that changed
  nothing returns `['server.py']` — the server reads stale. The new rule on
  the same tree returns `[]` — fresh.
- **The hole, measured**: the journal (the active file plus the rotated
  archive) holds merge events for PRs 61-84, except PR 76 (closed unmerged).
  PRs 1-60 hold none.

## The honest note about the historical merges

The journal learned to record a merge with **PR #27** (the commit that added
the event, round 60). So:

- **PRs 1-26** predate the trail — debt, not a violation.
- **PRs 28-60** (33 merges) came after the trail existed and are not in it.
- **PR #61** (round 115, a hand-run `gh pr merge`) was repaired with the
  sanctioned command, `pairctl pr merge-record`, and reads
  `pr_merge_repaired` — a distinct kind, so the journal never claims a
  gate-verified merge it cannot prove.

Writing 33 repair events for PRs 28-60 now was considered and **declined**.
The critic's reasons: 33 rows stamped with today's date would land in the tail
of the live journal and distort its chronology; 33 sequential calls to the
remote carry a failure mode of their own; the mechanism exists and the
round-115 incident is already repaired; and the horizon decision belongs to
the card, not to a repair run in passing. The facts are recorded here and in
the card; the repair stays available.

## What did not change

- The merge gate still does not require CI, and still does not check the
  PR's own CI status — the verdict is the peer's, the evidence is the
  machine's, and the head is what ties them to the code.
- The evidence's `head` is an unsigned field, exactly like the `value` it
  sits next to. Nothing in the gate verifies evidence signatures today; the
  envelope is checked by a test, not by the gate.
- The freshness gate cannot see a file edited during the server's own
  startup: the snapshot is taken at import, and the window is the import
  sequence. Measured in the code, not closed.
- The gate still reads the local HEAD, so a PR whose head is not the local
  HEAD is refused rather than merged — the direction is safe, the
  convenience is not.
