# Round 148 — three round disciplines: environment, conflict, strategy

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-148-worktree-bootstrap`
- **Writer**: omp · **Critic**: agy
- **Base**: `dev` (the human's directive: dev only, `master` untouched)
- **Deliverable**: a worktree that shares the project's dependencies instead of
  reinstalling them, a conflict found BEFORE the merge instead of during it,
  and a merge strategy that is a setting instead of a hard-wired flag — with
  a protocol section that says all of it in both languages.

Source: backlog P1 — `.pair/notes/backlog.md:133-148` (the three practices of
the agensi.io skill package: environment bootstrap, pre-flight merge checks,
configurable merge strategy).

## The defect this round started from

Round 147 built the worktree-first discipline: a plan declares its isolation
strategy, the critic signs it, and the worktree dies with the branch. Three
things the discipline needs in order to be usable were still missing — and all
three failed in the same way: **at the moment it was too late**.

- A worktree created from scratch had no `.venv` and no `node_modules`. Every
  worktree meant a full reinstall of the dependencies — the cost of the
  isolation was paid in install time, every time.
- A conflict was discovered AT THE MOMENT OF THE MERGE: after the PR was on
  review, after the critic had written a verdict, after the human had read
  the diff. Round 147 ended with a PR that could not be merged, and the
  conflict was found by the merge itself.
- The merge strategy was hard-wired: `gh pr merge --squash --delete-branch`.
  A project that wanted `rebase` or `merge` had no way to ask for it except
  by editing the engine — which is not a setting.

## The four slices

### A — a worktree shares the project's caches (`02010e6`)

`mcp/pair_mailbox/worktree.py` now links the project's heavy paths into a
fresh worktree. The shared list is CLOSED, never a glob: `.venv`,
`node_modules`, `.pytest_cache`, `__pycache__`, `dist`, `build`. A glob
would share everything under the tree, including the sources.

The links are SYMLINKS into the main worktree, and a path is linked only
when the source exists AND the target does not: a link to a place that is
not there is a broken link, and overwriting somebody's directory is data
loss. The setting follows §19's pattern for `trunk`: `PAIR_WORKTREE_SHARE` →
`.pair/worktree-share` → `.pair-worktree-share` → the closed list.

### B — the conflict is found before the merge (`5b41357`)

`mcp/pair_mailbox/preflight.py` (new) asks the question earlier, and asks it
without touching the repository: `git merge-tree --write-tree` computes the
merge result in memory. The index, the working tree and the history are
exactly as they were.

`review_gate.cmd_pr` runs it before the merge, on BOTH paths — forced or
not. `--force` bypasses the REVIEW gates; a conflict is not a review gate,
it is a fact about the two commits, and it does not become true because a
human wrote a reason next to it.

### C — the merge strategy is a setting (`73e4afc`, `1d439f5`, `5d972dd`)

`mcp/pair_mailbox/merge_strategy.py` (new) follows §19's pattern for
`trunk`: `PAIR_MERGE_STRATEGY` → `.pair/merge-strategy` →
`.pair-merge-strategy` → `squash`. The default is what makes this safe to
land: a project that says nothing keeps the behaviour it had, byte for byte.

An invalid value is REFUSED with the admissible values named. It is never
silently replaced by the default: a project that asked for `rebase` and got
`squash` would learn it from the trunk's history, where nobody was looking.

`--delete-branch` is kept at every strategy: §19 requires the round's branch
to die with the round, whatever strategy brought it to the trunk.

### D — the protocol, the card, the map (`1d439f5`, `5d972dd`)

`docs/PROTOCOL.md` §22 and `docs/PROTOCOL.ru.md` §22 describe all three
practices; `scripts/verify-map.tsv` and `scripts/verification-profile.tsv`
know the new files and suites.

## Five defects my own tests found

### Git's prose is localized, and this host speaks Russian

The first parser looked for `Merge conflict in ` in git's output. The host's
git writes «Конфликт слияния в f.txt». The parser found nothing and
reported a conflict with no files — a gate that fails in the direction of
refusing everything, on a repository where the merge was clean.

The file names are now read from the NUL-separated form
(`--name-only -z`), which is a shape and not a language: a path with a space
or a non-ASCII name survives it unchanged.

### The exit code does not tell a conflict from a broken revision

`git merge-tree` exits **1** both for a conflict AND for a revision it
cannot resolve ("no-such-branch — не является тем, что можно слить"), and
128 for unrelated histories. A parser that read the exit code would call an
unknown branch a conflict, and refuse every merge against a branch that does
not exist yet.

The distinction is made on the OUTPUT: git prints the sha of the merge result
only when it actually computed a merge. The module's own docstring said "exit
> 1 is unknown" before the measurement; the measurement corrected it, and the
docstring was corrected with it.

### The PR's head may not be in this repository

The pre-flight compares the PR's HEAD — what the merge would ship — against
`origin/<trunk>`. But the PR was pushed from another machine, and its head
commit was not here. `merge-tree` against a commit git does not have answers
"unknown", and an unknown is a refusal: the merge would be blocked by a
missing object, not by a conflict.

`preflight.ensure_commit` fetches the commit by SHA. `git fetch origin
<sha>` works even when the SHA is not the tip of any branch — verified on a
single-branch clone that had never seen the feature branch.

### The smoke passed against code that was not there

The end-to-end bootstrap smoke ran in a `git clone` of this repository, and a
clone carries only COMMITS. The fix was uncommitted, so the smoke exercised
the old code — which linked nothing and reported `shared: None`. The same
lesson as round 147, and the same fix: point the smoke at the working tree's
module, not at a clone of it.

### The round grew a second way to read a setting

Slice A created `project_settings.py` — the module that knows WHERE a
project's voice is heard (environment → local ignored file → committed
project file → default). Its own docstring names `merge_strategy` as one of
the settings it serves.

Slice C then wrote its own resolver: the same order, the same four sources,
a second copy of the logic. That is exactly what `project_settings.py`
exists to prevent — "each setting invents its own resolution order, and the
project ends up with three ways to read a setting — three places to look
when a round refuses for the 'wrong' reason, and three chances for two of
them to disagree."

No test caught it, because both copies passed their own tests. What caught
it was reading the two files side by side: the round had invented a
convention (`.<name>` for the committed policy) that the trunk's precedent
(`.pair-trunk`) did not use, and the plan the critic had approved named
`.pair-worktree-share` and `.pair-merge-strategy`. The implementation had
drifted from the agreed plan in a way no gate could see.

`merge_strategy.py` now owns only the WHAT and asks `project_settings` for
the WHERE; the committed policy file is `.pair-<name>`, the trunk's name;
and `test_project_settings.py` proves the ORDER is what it says it is, for
every setting, and that the order is the trunk's.

## The proof

**Live facts, not fixtures:**

- The bootstrap, on a real repository: `.venv` and `node_modules` are real
  symlinks into the main worktree, the content reads through them, the
  source is untouched, and the caches absent from the source are skipped
  without leaving broken links.
- The pre-flight, on a real remote: a conflict between two real commits is
  named with its files (`f.txt`, `имя файла.txt`); the clean merge passes;
  the stale trunk looks clean until the trunk is fetched — and then the same
  comparison says `conflict`.
- The pre-flight leaves the repository alone: HEAD, the branches, the reflog
  and the working tree are byte-identical before and after.
- The strategy on the real project: `squash` by default; `rebase` through
  the environment; `cherry-pick` refused with `squash, merge, rebase` named.

**Suites and gates:**

- `python3 mcp/pair_mailbox/test_worktree.py` — **Ran 22 tests, OK**.
- `python3 mcp/pair_mailbox/test_preflight.py` — **Ran 19 tests, OK**
  (unit + integration against a real remote, in one file: one test file per
  source file).
- `python3 mcp/pair_mailbox/test_merge_strategy.py` — **Ran 14 tests, OK**.
- `python3 mcp/pair_mailbox/test_project_settings.py` — **Ran 14 tests, OK**.
- `python3 mcp/pair_mailbox/test_review_gate.py` — **Ran 34 tests, OK**.
- `python3 mcp/pair_mailbox/test_verify_map.py` — **Ran 7 tests, OK**.

- `./scripts/file-size-gate.sh` — clean (cap 800).

**Red-proofs:**

- The pre-flight refuses a real conflict — and the refusal names the file.
- `--force` does not bypass a conflict.
- An `unknown` answer is a refusal, never a pass: a check that said "no
  conflicts" when git failed would say the thing the reader wants to hear
  without having checked anything.
- The strategy resolver refuses `cherry-pick` and names `squash`, `merge`,
  `rebase`; `gh` is never run with a refused strategy.
- The resolver reading `rebase` correctly while the merge still passed
  `--squash` would satisfy every test of the resolver and ship the old
  behaviour — so the test asserts on the command `gh` receives.

## The honest limits

- **The pre-flight needs GitHub.** The PR's head comes from `gh pr view`.
  Without `gh`, or without authentication, the check cannot know what the
  merge would ship, and the merge is refused. That is the fail-closed
  direction, but it is a refusal, not a success.
- **The check needs the network.** The trunk is fetched before the
  comparison, because a check against a stale trunk is a check against a
  fiction. An offline merge is refused for that reason, and the reason is
  named.
- **The shared list is a list, not a rule.** `.venv` and `node_modules` are
  what this project uses. A project with a different dependency layout edits
  the setting — but a path in the list is shared WHATEVER it contains, and a
  path outside it is not shared at all. The list is not clever enough to
  know which of its entries is a cache.
- **Symlinks are not free.** The worktree and the main worktree share the
  same `node_modules`, so an install in one is visible in the other. That is
  the point; it is also a coupling that a project with two incompatible
  dependency sets would not want.
- **The file-size cap forced a split of the tests, not of the sources.**
  `test_review_gate.py` reached 935 lines and the cap is 800. The pre-flight
  gate tests moved to `test_preflight.py` and the merge-flag tests to
  `test_merge_strategy.py` — each next to the function it exercises. No
  source file was split, and no baseline exception was added.
- **The Russian mirror carries this material.** §22 is in both files, so
  the new material creates no new gap. The OLD gap (§14-16, §17 missing from
  the RU file) is still there; it is a separate piece of work and was
  deliberately not smuggled in here.
- **The pre-flight is not a rebase.** It asks whether the merge would
  succeed. It does not rebase the branch, does not rewrite the PR's
  history, and does not change what the merge would produce.

## Rollback

Five commits on one branch, squashed into one by the merge. Reverting the
merge removes the cache sharing, the pre-flight and the strategy setting;
the pre-flight's refusal then simply does not happen, and the merge fails
at GitHub as it did in round 147. Nothing else in the project depends on
the new modules: the protocol text is the only documentation, and the
pre-flight is opt-in by being inside the merge gate — `pairctl pr merge` is
the only caller.
