# Round 141 — the wake path reaches a live OpenCode peer

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-141-opencode-wake`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the supervisor's API wake finds the opencode server that
  actually holds the pair's connection, and the session it steers is that
  server's own active session — the session of an agent that has never made a
  single pair call.

## The defect

Two independent breaks, both measured on a live room (Prof.Granit, 2026-10-21):

**1. The wake asked the wrong server.** `wake_opencode.service_endpoint()` asked
the CLI for the SHARED background service:

```
opencode service status          -> stopped
wake_opencode.service_endpoint() -> ('', '')
wake_opencode.wake(...)          -> {'woken': False, 'why': 'no running opencode service'}
```

The pair runs OpenCode standalone (`bin/pair-duo`: `opencode --standalone
--auto`), and a standalone instance is a DIFFERENT server with its own port and
its own password. The instance that holds the session answered with ITS
password (HTTP 200) while the shared service's password got HTTP 401.

**2. The session id could only arrive too late.** The id came from the request
metadata of an OpenCode **tool call** (`ai.opencode/sessionID`), and at MCP
initialize the server dropped it on purpose. The opencode client's initialize
carries no `_meta` at all, so the id existed only after the agent had called
something — and the id is what wakes it. The circle closed on the wrong side:
the agent that most needs waking is the one that has never called anything.
The pilot wrote it twice for that live agent:

```
17:42:07  pilot_wake_api target=opencode woken=False why='no recorded OpenCode session id'
18:02:21  pilot_wake_api target=opencode woken=False why='no recorded OpenCode session id'
```

## What changed

- **`mcp/pair_mailbox/opencode_server.py`** (new) — finds the opencode server
  that owns the connection by walking up the process tree from the pair's own
  MCP server: the `opencode serve` ancestor, its `OPENCODE_PASSWORD` from its
  own environment, its port from its own listening socket. The password is
  read at call time and written nowhere. A pid without its start time finds
  nothing: pids are recycled, and a recycled pid would point the discovery at
  somebody else's tree.
- **`mcp/pair_mailbox/wake_opencode.py`** — the endpoint is the owning server,
  and the shared service is the fallback, used only when no such ancestor
  exists. The session comes from that server's `/api/session/active`, with the
  directory check that was always there; the recorded id stays as the fallback
  for the shared service and for a server that does not expose the route.
- **`mcp/pair_mailbox/server.py`** — at MCP initialize the pair binds the
  session id from the server that owns the connection, and drops it when there
  is no binding. The tool-call path is untouched: a host-session change still
  invalidates the old id. The binding happens OUTSIDE the state lock: a lock
  held across a network call would block every other role's state write for as
  long as that call takes.
- **`bin/pairpilot`** — the supervisor hands the adapter the role's own pid and
  its start time, so the adapter can tell WHICH opencode server is ours.
- **The suites stand in the gate's tables** — `opencode-server` in
  `scripts/verification-profile.tsv` (10 cases: the discovery and the binding),
  and the new module, its test, the adapter and its test in
  `scripts/verify-map.tsv`. The adapter's own suite grew five cases (10 in
  all).
- **Cards closed**: `opencode-wake-api-looks-for-the-wrong-server.md` and
  `opencode-session-id-never-arrives-at-initialize.md`.

## The proof

The red-proof runs the old adapter and the new one against the same fake
opencode server — a real process, a real port, a real basic auth:

```
the opencode server holding the pair: http://127.0.0.1:44761

OLD service_endpoint()      -> ('http://127.0.0.1:49374', 'db5zAWeSXpG2...')
OLD wake(project, ses_active)-> {'woken': False, 'why': 'recorded OpenCode session is missing or stale'}
requests that reached the owning server: []

NEW service_endpoint(pid)    -> ('http://127.0.0.1:44761', 'pw-3015726')
NEW wake(project, None, pid) -> {'woken': True, 'why': 'the steer turn accepted'}
requests that reached the owning server: [{'path': '/api/session/ses_active/prompt', ...}]
```

The old code found A server — the shared one, which serves every project on
the box — and still failed, because it was not the server holding the pair.
The new code finds the server that holds the pair and steers its own active
session, with no recorded id at all.

The tests are the same proof, standing up: 8 cases for the discovery (the
owning server is found; the shared service is not mistaken for it; a recycled
pid finds nothing; the active session is bound only when it is ours) and 2
cases for the pair's own server (the role entry carries the session id after
an initialize that carries no metadata; a session of another project is not
bound). The adapter's own suite grew five cases against the same fake server:
the endpoint is the owning server; the wake steers its active session; a
foreign active session is refused with nothing typed into it; the recorded id
is the fallback when the server has no active session; and a server with no
session at all refuses.

## The honest limits

- **The discovery is Linux-only.** It reads `/proc` for the command line, the
  environment and the listening sockets. On another system it finds nothing
  and the wake falls back to the shared service — the old behaviour, not a
  crash.
- **The active session is the server's, not the connection's.** For a
  standalone instance — one TUI, one server — that is the same thing. For a
  shared service it would not be, which is why the shared service is a
  fallback and never the source of an active session: its "active" session
  belongs to whoever typed last, on any project.
- **The recorded id is still cleared by a metadata-less tool call.** That is
  the old fail-closed rule, and it stands: a host-session change invalidates
  the old id. The wake does not depend on it any more — it asks the server.
- **The ring popup is still invisible to a full-screen TUI.** That is the
  third card of this round, and it stays open: the API path is the one that
  works for OpenCode, and the popup is a separate path with a separate policy.

## Rollback

One merge commit. The old wake was not wrong about the rule it stated — the
exact session, never a guess by directory or recency. It was asking the
wrong server, and it had nothing to ask when the agent was silent.
