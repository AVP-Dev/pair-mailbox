# Round 140 — the changed-file gate sees the staged work

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-140-changed-file-gate`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the gate that decides which suites an edit runs no longer
  reports "nothing to check" while the tree holds a change that was already
  staged — and it has a test of its own.

## The defect

`scripts/verify-changed.sh` discovered the changed files with

```
git diff --name-only -- . ':!node_modules'      # the worktree against the INDEX
git ls-files --others --exclude-standard         # the untracked
```

`git diff` with no commit compares the worktree with the **index**. A change
that was already `git add`ed is in neither list: it is not unstaged, and it
is tracked, so it is not "other" either. The gate printed

```
verify-changed: nothing to check, the tree is clean
```

and exited 0 — a green gate that ran nothing.

The second half of the door was the map's own test: `test_verify_map.py`
requires every path the map names to be tracked (`git ls-files` counts
staged files), so a new file the map names had to be staged before the map's
test could pass — and once it was staged, the gate could not see it. There
was no state in which the per-commit gate covered a new file the map names.

Measured in round 139, on this tree: the gate was run after `git add` and
reported a clean tree, and the round's own new files were never covered by
it.

## What changed

- **`scripts/verify-changed.sh`** — the default discovery is now the union
  of the unstaged changes, the staged changes (`git diff --cached`) and the
  untracked files. The `--base` mode was never blind (`git diff "$BASE"`
  compares the commit with the worktree) and is untouched.
- **`scripts/verify-changed_test.sh`** — a behavioural test that runs the
  real gate and the real map in a temp git repository: a clean tree (the
  honest empty case), an unstaged change, a staged change, a staged **new**
  file the map names, an untracked file, and the branch-level run
  (`--base`) covering the branch's new files. No network, nothing written
  outside the temp dir, nothing of the machine.
- **The suite stands in the gate's own tables** — a row in
  `scripts/verification-profile.tsv` (`changed-file-gate`) and two rows in
  `scripts/verify-map.tsv`, so a change to the gate or to its test launches
  the gate's test.
- **Card closed**: `the-changed-file-gate-skips-staged-work.md`.

## The proof

The red-proof is the test itself, run against the old gate: it fails at the
staged-change case with exactly the symptom from the card

```
FAIL: a staged change must be selected, got: verify-changed: nothing to check, the tree is clean
```

and passes after the fix — nine checks, all green. The rest of the evidence
for this round (the full gate on the branch head, the ground truth, the
critic's verdict on the head that was merged) is recorded with the round.

## The honest limits

- **The gate now does more work.** After a `git add` it selects suites it
  used to skip. That is the cost of it not lying, and the reason the change
  is small and the test is behavioural.
- **The `--base` mode keeps its meaning**: the diff against a base commit.
  The untracked files are not in it, so the branch-level run covers the
  committed files of the branch — including the new ones — and not the loose
  ones in the worktree.
- **A file that is staged for deletion and lives again in the worktree** is
  listed by the union (the staged diff names it) even though the worktree
  matches HEAD. Checking one file too many is the safe direction.

## Rollback

One merge commit. The old gate was not wrong about anything — it was
silent about half the work.
