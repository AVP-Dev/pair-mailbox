# Round 137 — the facts anchor and the tree facts stop fighting over one file

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-137-stable-facts-and-gate-coverage`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the facts anchor holds facts again, the fast gate runs both
  supervisor environments, and two gates in one worktree can no longer corrupt
  each other's evidence in silence.

## The defect

Two features of round 135 were given the same path.

- `mcp/pair_mailbox/facts.py` — the **anchor** (`pair_facts`): `FACTS_FILE =
  "facts.json"`, a file of `{"facts": [...], "updated_at": ...}`.
- `mcp/pair_mailbox/session_facts.py` — the **tree-facts collector**:
  `FACTS_FILE = "facts.json"`, a file of `{"version": 1, "head",
  "dirty_hash", "touched", "test_runs", ...}`.

Each write replaces the other's content, and both failures are quiet:

- the anchor reads a collector's file as *no facts* — `read_facts` looks for a
  `facts` list and finds none, so the answer is an empty anchor, not an error;
- an anchor write leaves the collector's file without a `version` key, which
  `load_facts` refuses — `FactsError`, *"a foreign-version facts.json, or not a
  dict"* — so `scripts/verify-ground-truth.py` turns **BLOCKED** (*"input never
  reads"*).

Why it matters more than a file name: the close ritual runs the collector
every round (round 135's own evidence reads *"session_facts + anti-mock +
round-summary + verify-ground-truth"*). So the anchor that was built to survive
a context reset was wiped by the very ritual that closes the round. Measured in
this room on 2026-10-21: `pair_facts list` on a room whose `.pair/facts.json`
had been written by the collector answered `{"facts": [], "count": 0}` — the
headline feature of round 135, holding nothing.

## What changed

### A. Two files, two shapes, one writer each

- **The anchor keeps `.pair/facts.json`.** That path is a public contract:
  `PROTOCOL §9c` names it, the `pair_facts` tool writes it, the digest carries
  it, the budget is 500 tokens.
- **The collector moves to `.pair/tree-facts.json`.** Its path is always an
  argument — `scripts/verify-ground-truth.py`, `mcp/pair_mailbox/
  anti_mock_gate.py`, `mcp/pair_mailbox/round_summary.py` all take it on the
  command line — so the move touches the constant, the CLI default and the
  wording, and no contract.
- The protocol (EN and RU, in parity) and `HOW-IT-WORKS` (EN and RU) now name
  the tree facts, and the open card `merge-gate-does-not-require-ci-for-the-
  head.md` — which pointed at the collector's file — was corrected.

### B. The fast gate now runs the second environment

Round 136 added a second row for the supervisor suite: `supervisor-offline`
runs it with the host's tmux server shadowed. The map names **one** suite per
path (the longest matching row wins), so the new row reached the full gate
only: a change to `bin/pairpilot_test.py` could break the offline run and no
per-commit gate would have said so.

The map's own mechanism covers it — a `follow:` pin adds a suite on top of the
file's own:

```
follow:bin/pairpilot_test.py	supervisor-offline
```

The probe says so: before the pin `supervisor`, after it `supervisor;supervisor-offline`.

### C. Two gates in one worktree can no longer corrupt each other

Every gate run writes the same artifacts — `.pair/verify-<name>.log` per check
and `.pair/verify-results.txt` for the totals — and a run **removes both at its
start**. Two runners in one worktree therefore do not merely race: the second
one deletes the first one's results, and each run's totals count the other's
rows. Round 136 measured it: **83 result rows where 78 checks had run**, and a
"0 required failures" that belonged to neither run.

`scripts/verify-lock.sh` now holds the worktree: a lock directory with the
owner's pid and a token. The loser is told (exit 75, *"another gate is running
in this worktree"*) instead of quietly corrupting both runs. A crashed run
leaves a lock behind, and the next run takes it over — the pid is dead.

The first version of the lock exported a **boolean** and the changed-file gate
caught the leak: every process a suite spawned inherited the flag and believed
it held a lock it never took (the suite's own subprocesses then failed to take
one). The token fixed it — a token matches only the lock it was issued for, so
a leaked value is ignored.

### D. The neighbouring live-pane suites, re-audited

Round 136 audited them; this round checked the verdict again, because the
lesson of that round was that an audit is worth repeating.

- `mcp/pair_mailbox/test_panes.py` creates its **own** pane in a temp project
  (a real tmux call, on a pane it then kills) — it must be live, because
  stubbing the resolver would prove the wrong thing.
- `mcp/pair_mailbox/test_protocol_delivery.py` creates its own pane the same
  way, and skips itself outside tmux.
- `mcp/pair_mailbox/test_protocol_panes.py` stubs the resolver
  (`pane_is_foreign`, `pane_belongs_to_project`).

None of them resolves a **foreign** pane, so the round-136 defect does not
reproduce in them. Their `serial` marks stay, and stay correct: they do share
the host's tmux server, unlike the supervisor suite after round 136.

## The property, pinned

- `test_facts.py` — `test_a_tree_facts_write_does_not_wipe_the_anchor`: a
  collector write into the anchor's state dir leaves the anchor's fact
  readable. Red-proof: with `FACTS_FILE = "facts.json"` restored, the test
  goes red on *"the collector's write wiped the anchor"* (1 ≠ 0).
- `test_session_facts.py` — `test_the_collector_writes_a_file_of_its_own` and
  `test_the_cli_default_path_is_the_tree_facts_file`: the collector's file is
  `tree-facts.json`, and the CLI's default path is the one the close ritual
  gets when nobody names a path. Red-proof: the same restored constant makes
  both go red on the file's name.
- `test_verify_map.py` — `test_the_offline_supervisor_row_runs_with_the_file_
  it_covers`: the probe of the real script must answer with both supervisor
  suites. Red-proof: with the pin commented out, the probe answers
  `supervisor` and the test fails.
- `test_verify_project.py` — seven tests on the lock: the second gate is
  refused with 75, the winner's log survives the refusal, a stale lock is
  taken over, a normal run leaves no lock behind, the helper is re-entrant
  within one process tree and refuses a second process, and a leaked token
  opens nothing. Red-proof: with the lock call disabled, the suite goes red
  (*"the first gate never took the lock"*).

## What did not change

- The anchor's public path, tool, budget and digest: `.pair/facts.json`,
  `pair_facts`, 500 tokens.
- The gates' contracts: the tree facts are still passed as an argument, the
  summary keeps its shape, the receipt keeps its ground-truth refusal.
- The pilot and the supervisor suite: round 136's work is untouched here.

## The limits

- Two files means two readers. A tool that wants both the anchor and the tree
  facts reads both, and must name which it wants.
- The lock is per **worktree**, not per machine: two worktrees may run gates
  at the same time, and they cannot collide — each has its own `.pair/`.
- The lock is a directory, so a killed run leaves one behind; the stale-pid
  takeover cleans it, but a gate that is killed between the takeover and its
  own first write can still be refused once. It is refused, not wrong.
- The map still names one suite per path. The `follow:` pin is how a second
  suite is added, and it is easy to forget — the new test pins this one case,
  not the general rule.

## What a reader should take away

A file name is a contract, and two features that pick the same one do not
argue about it — they overwrite each other, quietly, and each side reads the
other's damage as its own normal state. The anchor did not crash; it answered
"no facts", which is exactly what an empty anchor looks like. Nothing in the
review of either feature would have shown it: each file was correct on its
own. The collision was only visible from the ritual that runs both, which is
why the close ritual is where the card was found — and why the fix is a
property test on each side rather than a comment on the shared name.
