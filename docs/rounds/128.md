## What was wrong

Round 127 shipped and merged 45 files of fixes. The merge itself nearly did not happen, and
the reason was not the code.

The merge gate reads the LAST `## `-section of the verdict note that carries a
**machine-readable marker** — either `verdict-approve <sha>` or a line that is exactly
`**APPROVED**` (`review_gate.py`, `docs/PROTOCOL.md` §10g). The rule was written down. The
critic's verdict said:

```
## Verdict: APPROVED (PR #72, Head 82f54f7)
```

`APPROVED` there is ordinary prose. The heading is not a marker. So that section counted as
unmarked, and the gate fell back to the previous MARKED section — round 124's approval of
PR #71 — and compared that stale head with the live one:

```
PR merge gate REFUSED: marker head '3307ec67a545aac30515878e645a23f900043fd7'
does not match current HEAD '82f54f7e0b9a5afc85a9af2d5c5be145680c2387'
```

`3307ec6` is PR #71. The refusal named a commit from two rounds earlier and said nothing
about the work under review. Round 124 hit the same wall and the round closed by another
route, so the shape was known and still repeated.

The rule lived in `docs/PROTOCOL.md`. What was missing was the place that tells the critic
HOW to give a verdict: `skills/pair-work/SKILL.md`, in both language mirrors. It described
the review round, the finding kinds, the verdict kind — and not the one line the gate reads.

## What was done

**Both mirrors of `skills/pair-work/SKILL.md` now carry the format, with the reason.**

```
## verdict-approve <the head sha being reviewed>

**APPROVED**
```

The sha is not decoration. It is what pins the verdict to a revision, so a verdict written
for an older commit does not approve a newer one — the exact confusion that produced the
refusal above, where a verdict for `3307ec6` was weighed against `82f54f7`.

The skill says what happens without the marker: the gate falls back to an OLDER marked
section, compares that stale head with the live one, and refuses the merge for a reason
that has nothing to do with the work. An agent that does not know this reads the refusal as
a defect in the change and goes looking for one that is not there.

## Red-proof

The failure was reproduced before the fix, not asserted: the merge was refused with the
stale-head message above, and it stopped at exactly the old block. The marker was then
posted in the required form, and `bin/pairctl pr merge 73` merged on the first try — the
same gate, the same note file, the same critic, the same round.
