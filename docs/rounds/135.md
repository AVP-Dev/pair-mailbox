# Round 135 — the context bill, paid: the reads answer with a window, and the anchor survives a reset

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-135-token-budget-impl`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the variants round 134 measured and priced, implemented with tests.
  Every number below was measured on the live room, not estimated.

## The question

Round 134 measured what one orientation costs in this pair and priced the variants
that pay. This round implements them: the task list, the note index and the note tail
answer with the window the reader needs, the budget is in tokens instead of lines,
and the pair grows the structured facts anchor that survives a context reset.

## How the numbers were taken

- **Tokenizer**: `tiktoken` `cl100k_base`, applied to the exact payload strings.
  Other models tokenize differently; read every figure as ±5–10 %.
- **Room side**: a real `PairSession` bound to this repository's live `.pair`, so the
  payloads are the ones the tools actually return.
- **Live room at round 135**: 138 tasks (1 open), 229 notes, `notes/` 3.4 MB.

## Part 1 — the room side: what one orientation costs now

| call | before | after | saved |
|---|---:|---:|---:|
| `pair_task list` | 30 130 | 392 | −98,7 % |
| `pair_note_index` | 8 065 | 719 | −91,1 % |
| four-note tail sweep | 17 518 | 2 927 | −83,3 % |
| `pair_digest` | 495 | 495 | the ceiling is now honest |
| **orientation sweep** | **56 208** | **4 533** | **−91,9 %** |

The sweep is the four calls an agent makes to find out where the round stands: the
task list, the note index, the four working notes and the digest.

### A — the task list answers with the open window

`pair_task(action="list")` returns the open tasks, the counts (`open`, `done`,
`dropped`, `total`), `next_id` and `hidden` — how many tasks the answer left out.
The whole history is behind `scope="history"`, with `limit`/`offset` for paging, and
it comes back with the same ids it had before: no duplication, no loss.

Measured on 138 tasks with one open: **30 130 → 392 tokens**. The card's red-proof
is a test: a room with 1 000 closed tasks answers with a payload under 2 000
characters, and the closed count is still reported.

### B — the note index lists the freshest notes, and the room's totals

`pair_note_index` returns the 12 freshest notes with their size, entry count and
modification time, plus `count`, `total_bytes` and `largest` (which note is the
whale) and `omitted` (how many the window left out). The biggest-first order of the
old listing is still there as `scope="largest"`; the rest is reachable by name.

Measured on 229 notes: **8 065 → 719 tokens**.

One detail the tests caught: the sort key is the raw mtime, not the printed stamp.
The printed stamp has second resolution, and notes written in the same second came
back in name order — the "freshest" window was alphabetical.

### C — the note tail is budgeted in tokens

`pair_note_read` answers with the tail under a **token** budget (800 by default,
capped at 4 000). The line window stays on top of it (120 lines, capped at 400): a
line of Russian prose is not a fixed number of tokens, and the old 120-line budget
cost 3 166 to 5 122 tokens on the very same four notes.

The cut still lands on a record edge — a half record reads as a whole one, and the
reader acts on it. The answer says which ceiling bound it (`budget_applied`):
`tokens`, `lines`, `record` or `none`.

Measured on the four working notes: **17 518 → 2 927 tokens**.

One honest exception: when the newest record alone is bigger than the budget, it
comes back whole and the answer says `budget_applied: "record"`. Cutting inside a
record would save the budget and cost the reader the truth.

## Part 2 — the estimate: why bytes/4 was wrong here

The ceilings above are counted with one estimate, and the estimate had to change
first. The old one divided bytes by four. In English that is about right; in
Russian it is not — 2,6 characters per token, measured — so the digest's 500-token
ceiling was a 650-token ceiling in this room, and every budget built on it promised
less than it delivered.

`token_budget.py` now owns the ceilings and the estimate, and the estimate
over-counts on purpose. Two estimates are computed and the larger one wins:

- the character ratio (ASCII at 3,0 characters per token, everything else at 1,8) —
  measured on this room's own notes at 3,3 and 1,9, so both numbers sit below the
  truth;
- the count of word-like chunks — the shape code, JSON and paths have, where the
  character ratio loses.

A 10 % margin rides on top. Checked against the real tokenizer:

| sample | real tokens | estimate | ratio |
|---|---:|---:|---:|
| note `decision` | 2 883 | 3 368 | 1,17 |
| note `finding` | 2 494 | 3 146 | 1,26 |
| note `handoff` | 3 275 | 3 673 | 1,12 |
| note `plan` | 2 998 | 3 585 | 1,20 |
| English prose | 401 | 661 | 1,65 |
| Russian prose | 1 201 | 1 374 | 1,14 |
| Python code | 960 | 1 174 | 1,22 |
| JSON rows | 1 280 | 1 453 | 1,14 |
| dense call arguments | 1 520 | 1 585 | 1,04 |

Never under: 4 % to 26 % above the truth. Over-counting costs a little room;
under-counting costs the ceiling, and the ceiling is the promise.

The digest had to be repaired with it: its line cut sliced BYTES at four per token
while the estimate counted characters, so a cut line came out over budget and the
final cleanup dropped it whole — the task start, the one line the digest exists for,
gone with it. The cut now uses the same arithmetic as the estimate.

## Part 3 — the facts anchor

A compaction in the harness removes about 90 % of the context and leaves 39 513 to
49 131 tokens of prose alive — the summary the agent carries for the rest of the
session. It cannot be queried, diffed or dropped. The card asked four questions
before any code; here are the answers this round implements:

1. **Where the facts live** — `.pair/facts.json`, a file of its own. Not
   `state.json`: that one rotates, and a fact that vanishes with a rotation is not
   an anchor.
2. **Who writes them** — any agent, like a note; the critic is often the one who
   knows a new fact. The writer owns the pruning (`drop`, `clear`).
3. **What happens at round close** — they stay. They are the next round's starting
   point, and the human reads them as the state of the work.
4. **Whether the compaction summary can be replaced** — not from this repository:
   the summary belongs to the harness, and the harness is a different project. What
   this round delivers is the half a pair can deliver — a structured, queryable
   anchor that costs a few hundred tokens — plus the guidance to keep it current.

The store holds 500 tokens. A write that would cross the budget is **refused**, not
trimmed: a silently trimmed fact is a fact the writer believes they recorded and
nobody else can find. The facts travel in `pair_digest`, the cheap orientation, and
they survive a new session on the same state — the test says so.

## Part 4 — the guidance, and what stays a card

The pair skills now say what the tools already allowed: **read a file by range,
never hand a whole file back as a call argument.** Measured on this project's
longest session, `write` and `edit` arguments carrying whole files cost 232 065
tokens of that session's context — 7,6 % of the session and 59 % of all call
arguments — and the harness stored every call payload a second time, another 10,9 %.
A `read` with a range cost 5 953 tokens across 212 calls.

The stale `server.py:NNN` citations in both skill files were corrected as well: the
note-read constants moved to `token_budget.py`, and the line numbers the skills
named pointed at blank lines and unrelated code.

## Part 5 — the limits of this round

- The harness-side half of the context bill is **not** this repository: the
  compaction floor (39–49 thousand tokens of prose), the `tool_execution_start`
  duplication in the session log, and the session store's own growth stay cards.
- The token estimate is an estimate. It over-counts by 4–26 % on the samples
  measured here, and it is not a tokenizer: a different model tokenizes
  differently, and a budget tuned for one model is a budget tuned for a room, not
  for every model.
- `pair_note_index`'s default window is 12 notes. An agent that needs an older
  note asks for it by name or widens the window; the answer always says how many
  notes it left out.
- The facts anchor is only as good as what the agents put into it. Nothing writes
  it automatically yet — the writer sets a fact when an invariant changes.

## What a reader should take away

The context bill was not mysterious: one call reported 30 130 tokens to say that
one task was open, and the room paid it on every orientation. The fix is not
compression — it is answering with the window the reader needs, counting the
window in the unit the reader pays in, and keeping the anchor that must survive a
reset in a shape that can be queried, diffed and dropped.
