# Round 136 — the supervisor suite stops asking the machine

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-136-hermetic-supervisor-suite`
- **Writer**: omp · **Critic**: agy
- **Deliverable**: the required `supervisor` gate no longer reads the live tmux
  server, so its colour is a fact about the change and not about the box.

## The defect

`bin/pairpilot_test.py` is a required gate. It read the **live** tmux server:
its fixtures stubbed two of the three pane facts the pilot asks for and let the
third — *does this pane belong to THIS project?* — be answered by whatever
windows the machine happened to have open.

On this box, `%1` is a live pane of another project:

```
$ tmux list-panes -a -F "#{pane_id} #{pane_current_path}"
%0   /mnt/storage/work/nyx-system
%1   /mnt/storage/work/nyx-system
%2   /mnt/storage/work/umputum
%3   /mnt/storage/work/umputum
```

The pilot then did the right thing: it refused to type into a pane owned by
another project, recorded `pilot_pane_foreign`, dropped the queued push — and
four assertions of a required check fell.

```
FAIL: test_live_cli_in_the_pane_gets_the_text
FAIL: test_unread_mail_wakes_a_live_peer_without_an_ask_file
FAIL: test_a_delivered_mail_wake_does_not_spend_the_human_trigger
FAIL: test_a_delivered_report_does_spend_the_human_trigger
Ran 169 tests in 7.234s
FAILED (failures=4)
```

The same tree, about an hour apart, was green at 07:56 and red at 08:0x in
round 134.
The only thing that changed in the world was that another project opened a
window and took the id `%1`. A gate that turns red for a reason unrelated to
the change is how people learn to ignore red.

**The pilot was right. The fixtures were wrong.** `bin/pairpilot` refuses to
type into a foreign pane, and that guard stays exactly as it was.

## Two resolvers reach a tmux

Stubbing the third fact alone would not have been enough. Two independent
resolvers reach a tmux in this codebase:

1. the pilot's own `pilot.tmux` attribute, and
2. `composer._tmux()`, which looks the binary up in `PATH` by itself — the
   delivery path calls it, not the pilot.

Stub the first and the second still asks the live server. So the **binary**
is replaced: the suite installs a fake `tmux` in `PATH`, and every path in the
file — including the ones that resolved through `PATH` — points at it.

## What changed

- **The fixture answers all three facts.** `pane_role_pid`, `pane_alive` and
  `pane_belongs_to_project` are stubbed together, as the class docstring has
  always promised ("the stub answers the facts the pilot needs and nothing
  else, so the test cannot pass by touching a real window").
- **The fake tmux** (`PilotCase._install_fake_tmux`) exits 0 like the
  `/usr/bin/true` the suite used before, answers a pane asked for its screen
  with a shell prompt, and leaves a trace of every command it was given.
  The screen answer matters: the pilot's own question *"is the agent busy?"*
  was read off a real window before, so the gate's colour depended on another
  project's screen content.
- **Pane ids that cannot exist.** `TestPushGates` names `%999999` instead of
  `%1`, so even a missed stub cannot reach a window.
- **Every tmux path in the file points at the fake** — `/usr/bin/tmux` (5
  places), `/usr/bin/true` (9), the PATH-resolved `"tmux"` (12) and the
  `"tmux-fake"` marker (3).

### What else moved

- **`TestRestart` was making a live query of its own.** It stubs
  `pairpilot.subprocess`, but `composer.pane_key` reaches `pane_identity`,
  which uses the composer's own `subprocess` — the real one. With
  `pilot.tmux = "/usr/bin/tmux"`, `composer.pane_key` asked the live server
  about pane `%7`. That is where the historical "TestRestart read the live
  pane %7" finding came from.
- **The `serial` mark left the `supervisor` row.** That mark existed because
  live-tmux suites share the host's tmux state; this suite no longer touches
  it.
- **The other suites were audited, and none of them has the same defect.**
  `test_panes.py`, `test_protocol_panes.py` and `test_protocol_delivery.py`
  create their **own** tmux session (a scratch name, their own panes);
  `test_wake.py` and `test_protocol_tui.py` stub the resolver; the composer
  tests stub `capture`, `type_text` and `pane_alive`. The supervisor suite was
  the outlier: it was the only one asserting a delivery into a pane **the
  machine owns**.
- **The gate grew a second row.** `supervisor-offline` runs the same suite
  with the host's tmux server out of reach (`env -u TMUX -u TMUX_PANE
  TMUX_TMPDIR=$(mktemp -d)`). The two rows together are the property the
  suite never had: green with a live server, green without one. Before this
  round the second was the only green one, and the full gate had to be run
  with the server hidden by hand (round 135's evidence says so).

## The property, pinned

`TestPushGates.test_the_push_path_asks_the_machine_nothing` holds it:

- the pilot holds the fake, never a tmux of this machine;
- the composer's own resolver finds the fake too — otherwise the delivery
  path still has a road to the host;
- the push path never asks for typing: no `send-keys` in the fake's log.

Its red-proof was measured by breaking it: with the `PATH` shim removed, the
test goes red and names the binary that got through —
`the composer resolves its own tmux from PATH: it must find the fake too, not
'/usr/bin/tmux'`. The suite's own red state, on this box, with `%1` live and
foreign: `Ran 169 tests, FAILED (failures=4)` — the four cases above. After
the fix: `Ran 170 tests, OK`, with the live server in reach and with it
shadowed.

## What did not change

- `bin/pairpilot` is untouched. The guard that refuses a foreign pane
  (`bin/pairpilot:1251`) and its regression test stay as they were.
- The delivery contract is untouched: what the pilot decides about a push, a
  wake, a trigger and a composer is still what the suite checks. Only the
  answers the machine gave are now the fixture's.

## The limits

- The fake models one shape of pane: alive, idle, a shell prompt. A suite
  that needs a different screen must say so in its own fixture, which is the
  point — the answer is then visible in the test instead of in another
  project's window.
- The suite still checks the pilot's decisions, not tmux. A real tmux
  integration test is a different thing and is not here.
- The fake answers for every pane at once; the pilot never learned which pane
  it asked about. That is enough for the facts the pilot asks, and it is why
  the pane ids in the suite are synthetic.

## What a reader should take away

A test that asks the machine is a test about the machine. The supervisor suite
asked the live tmux server whether a pane belonged to the project, and the
answer changed when another project opened a window — so a required gate
turned red for a reason that had nothing to do with the code under test. The
fix was not in the pilot, which was right all along; it was in the fixtures,
which now answer every question the pilot asks.
