# Round 146 — the supervisor had no word for a four-hour monologue

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-146-supervisor-watchdog`
- **Writer**: omp · **Critic**: agy
- **Base**: `dev` (the human's directive: dev only, `master` untouched)
- **Deliverable**: a supervisor that cannot be killed by one failure, whose
  notes are provable, and that reports a composer it may not touch — plus the
  monologue watchdog that started the round.

Round 146 ended with three defects found on the live supervisor of this very
project. Each was found by the supervisor failing at its own job, and each is
recorded here with the numbers that exposed it.

## The three defects

### 1. One failing rule killed the whole supervisor (`e2d9a0d`)

`tmux send-keys` into a pane whose CLI had stopped consuming input hung for
the full 5-second timeout and raised `subprocess.TimeoutExpired`. The pilot's
`flush_outbox` caught `ComposerBusy` and nothing else, so the exception
escaped the tick, the whole `pairpilot` died, and **every** rule it carried
went dark with it — the silence check, the stalled-agent check, the monologue
watchdog.

A dead supervisor is the one failure no watchdog can notice. This project's
own `.pair/pairpilot.log` carried the traceback: the supervisor had been dead
since 2026-10-25, on exactly the path the watchdog was built to watch.

Three layers, each at the level that owns the fact:

- **`mcp/pair_mailbox/composer.py`** — a timeout becomes `ComposerBusy`.
  The pane did not answer in time; that is the same fact as "the composer is
  busy", not a new exception class the callers have to remember.
- **`mcp/pair_mailbox/server.py`** — the ring call is best-effort. A missed
  delivery is not a lost letter: the letter is already in the mailbox.
- **`mcp/pair_mailbox/guard.py`** — every rule runs inside its own guard. A
  rule that throws is journalled and skipped; the rules after it still run.
  The supervisor's value is the **sum** of its rules, so one failure must not
  switch the rest off — and must not be silent either.

### 2. The supervisor's own note was called a forgery (`1aee4ac`)

The pilot wrote `notes/fix.md` by hand, with no sha and no attempt. The
notes-consistency gate compared it against the journal, found no matching
row, and named it a forgery — then **blocked the close of the round the note
was about**. The supervisor's own record of its own work was what stopped the
round from closing.

The pilot now writes through the server: the normalised body, the sha, the
attempt taken from the journal, and a `note` row carrying both. The gate is
the point — it is the layer that proves the note is the supervisor's — so the
fix is to satisfy it, not to weaken it.

### 3. A blocked composer was obeyed in silence (`d22b72a`)

The critic's pane sat frozen for **2.8 hours** with the human's unsent line
in its composer — typed by hand, never submitted. Every delivery was
correctly refused (the text is not ours, so it stays untouched), every wake
was raised, every escalation was queued... and the one person who could
unblock it never learned that it was blocked.

The refusal was right. **The silence was the defect.** The supervisor watches
the ROOM, and a room where one role cannot be reached is a fact about the
room. So the pilot says it: on the console, where the human looks, and in the
journal, so the state is provable. Once per role per round — a blocked
composer is a standing fact, and a fact repeated every tick is noise.

The rule never types into the composer and never erases the text: that stays
the human's. It only LOOKS, and it reports.

## The defect that started the round

In round 144 an agent spent **four hours** streaming its reasoning: no tool
call, no code, no handover. The supervisor watched the whole time and did
nothing. The reason was a wrong signal, not a missing feature.

The signal was `ComposerBusy` — "the composer holds text, so the agent is
working, hands off". But the composer is the **input field**, not the
generation. Measured on the live pane `mail:0.0` during generation
(2026-10-26):

```
composer_line() -> '╰─'
is_composer_empty() -> True
```

The composer reads **empty** while the agent thinks out loud. So the pilot saw
"not busy", judged the agent idle, and the four hours passed unwatched — and
worse, a reminder printed into that idle-looking composer was swallowed by the
very stream it was meant to stop.

The other half of the wrongness: `ComposerBusy` is a fact about the *input
field*. A half-typed question makes it busy; a monologue leaves it empty. The
two states are opposites, and the rule read one as the other.

## What changed

- **`mcp/pair_mailbox/watchdog.py`** (new, 311 lines) — the detector, as pure
  functions over facts the caller supplies:
  - `MonologueTracker` — the streak per role. A streak ends when the screen
    stops changing or a tool appears; the verdict is `idle` / `working` /
    `thinking` / `monologue`.
  - `tool_pids` / `is_agent_cli` / `is_role_server` — which processes count as
    **work**. The agent CLI itself and this project's MCP server (`server.py
    --role <role>`, matched by argv shape) are exempt; everything else under
    the pane is a tool. The CLI may be launched through a runtime, so
    `bun …/omp` is recognised as `omp` — and the agent's own daemon
    (`bun …/pi-coding-agent/dist/cli.js __omp_worker_daemon_broker`) is
    recognised too, by the package marker in its path. Without that the role
    would be exempt forever (see "The daemon the live pane proved").
  - `descendants` — the pane's process tree, read from `/proc`.
  - `screen_signature` — the pane's **content** fingerprint, with the
    volatile parts normalised away: the braille spinner (it rotates while the
    agent waits for the network — a wait is not output), the elapsed timer of
    a running tool, and the wall clock.
- **`bin/pairpilot`** — `check_monologue()` runs the rule; `cut_monologue()`
  acts on it: `tmux send-keys C-c` first (the agent is mid-generation, and a
  reminder typed into a busy composer would be lost in it), then the hard
  reminder through the **outbox queue**, so it survives a busy composer
  instead of dying in it. The journal row is `pilot_monologue_cut`. New flag
  `--max-busy-seconds` (default 300).
- **`mcp/pair_mailbox/test_watchdog.py`** (new, 25 cases) — the streak
  arithmetic and the process rules, against **real** processes: the suite
  starts a throwaway `python3 -` and checks the detector sees it as a tool.
  The runtime cases use the **argv measured on the live pane**, because the
  live shape is the one that matters and a hand-written guess is not proof.
  The reminder's own tests live here too, beside the function.
- **`bin/pairpilot_test.py`** — `TestMonologueDetector` (8 cases): a monologue
  is cut and recorded; a live tool process is never cut; a rotating spinner is
  never cut; a frozen screen is never cut; a sealed patch stops the cut; a
  foreign pane stops the cut; the streak resets after a cut.
- **`mcp/pair_mailbox/composer.py`** — a tmux timeout is a `ComposerBusy`.
- **`mcp/pair_mailbox/server.py`** — the ring call is best-effort; the
  mailbox is the guarantee.
- **`mcp/pair_mailbox/guard.py`** — the guard, the rule order, and the
  blocked-composer rule. It lives here beside the other shared rules so that
  `bin/pairpilot` stays under its frozen ceiling.
- **`mcp/pair_mailbox/test_guard.py`** (11 cases), **`test_pilot_guard.py`**
  (12 cases), **`test_composer.py`** (31 cases),
  **`test_pair_notes_consistency.py`** (13 cases).

## The critic found a test that was not a test

The critic's independent run of `./scripts/verify-changed.sh --base origin/dev`
failed on `test_a_busy_composer_is_reported_to_the_human`. The cause was mine,
and it was the same class of mistake the round is about.

That test asked the **real** tmux about the **live** pane `%8`. `pane_alive`
answered `False` for a pane that was not the one it expected, the rule never
reached the composer check, and the assertion saw an empty log. The test had
been passing only because the human's unsent draft happened to sit in that
pane — and it failed the moment that draft was submitted. A test whose verdict
depends on what the operator is typing is not a test.

Fixed by making the room fake and keeping it fake: `pane_alive` and `capture`
are mocked in the module the rule imports them from, so the rule is exercised
on a pane that does not exist anywhere. Proven both ways:

- **The test no longer touches the live room**: with the pane reference changed
  to `%999999` — a pane that cannot exist — the suite still passes.
- **The test bites**: with the rule's report mutated away, the suite FAILS with
  `AssertionError: False is not true : the block must be reported; got ['']`.

Two cases that had been collapsed were split apart: a **free** composer is not
reported (with the room mocked, not with tmux switched off), and **no tmux at
all** is not a block. The old "free composer" case passed because the rule
returned early on a missing tmux — which proved nothing about the composer.


## The daemon the live pane proved

The first version of `is_agent_cli` knew two shapes: the CLI's name as
argv[0], and a runtime followed by the CLI's name as argv[1]. It was wrong,
and the **live pane** is what proved it — not a test, not a guess.

Reading the real process tree of the watching pane on 2026-10-26:

```
3072402 | bun /home/alexios/.bun/bin/omp --resume 01a17204-…
100305  | /home/alexios/.bun/bin/bun …/pi-coding-agent/dist/cli.js __omp_worker_daemon_broker
229136  | /home/alexios/.bun/bin/bun …/pi-coding-agent/dist/cli.js __omp_worker_daemon_broker
```

The second and third lines are the agent's **own daemon**. Its argv carries no
CLI name at all — only the entry script `cli.js` — so the old rule counted it
as a **tool**. A daemon lives for the whole session, so the role would have
been exempt from the detector **forever**: the watchdog would have been blind
to precisely the role it exists to watch.

The rule now reads the entry script together with the package marker in its
path (`pi-coding-agent`, `opencode`, `@anthropic-ai/claude-code`), so a
stranger's `cli.js` stays a tool and the agent's own daemon does not. The
classification is a pure function over argv (`is_agent_cli_argv`), which is
what makes the measured shape testable without a live daemon.

Verified on the live pane afterwards: the CLI is `CLI`, this project's server
is `SERVER`, and the actual work in flight (`gh pr view`, `python3 -`) is
`TOOL`.

## The reminder must not invent a duration

The first version of the hard reminder said **"5 minutes"** in a fixed
string. The threshold is configurable (`--max-busy-seconds`), so at a
10-second threshold the message told the agent a number the supervisor never
measured — a false statement, typed straight into the agent's composer.

The reminder is now built from the measured streak
(`monologue_reminder(seconds)`), and the test pins it: a 10-second threshold
produces "1 minute", and the text may not contain "5 minutes".

**Red-proof**: the old fixed string claims "5 minutes" regardless of the
measured 60 seconds.

The reminder builder lives in `watchdog.py`, beside the rule that decides when
to send it — not in `bin/pairpilot`. The **file-size gate** caught that
placement: the first version put the function in the supervisor, and the gate
refused the growth of a frozen file (`bin/pairpilot`, frozen at 2814 lines).
Moving the function and its tests to the module that owns the rule brought
both files back under their ceilings — `bin/pairpilot` 2810, its test 3726 —
without touching the baseline.

## The honest limits

- **The screen is the evidence, so a TUI that redraws without content would
  be invisible.** The normalisation covers the spinner, the elapsed timer and
  the wall clock — the three volatile parts measured here — but a CLI with a
  fourth volatile element would read as streaming. The tool exemption still
  holds it back: the cut needs *both* a moving screen and no tool.
- **A tool that never exits exempts the role forever.** A daemon started by
  the agent (a dev server, a watcher) lives under the pane and looks exactly
  like work. The detector would then never fire for that role. The rule
  "no tool alive" is deliberately the conservative direction: it cannot cut a
  working agent, it can only miss a stuck one. The agent CLI's **own** daemon
  is carved out by argv shape; a *third-party* daemon started by the agent
  is not, and it remains a known blind spot.
- **The cut is a keystroke, not a kill.** `C-c` interrupts the current
  generation; the agent may ignore it and keep going. The streak resets after
  a cut, so a second monologue is cut again.
- **The supervisor needs the pane's process tree**, so it needs the pane's
  shell to be an ancestor of the agent's processes. Where the agent runs
  outside its pane's tree, the detector sees no tool and no CLI — it stays
  silent rather than guessing.
- **The five-minute threshold is a measured compromise, not a proof.** It is
  longer than any legitimate thought observed here and shorter than the four
  hours that were lost. A slower agent that thinks for six minutes without a
  tool would still be cut.
- **The blocked-composer rule reports; it does not unblock.** The text in the
  composer belongs to whoever typed it, and only that person may send or
  clear it. The rule makes the block visible; it cannot remove it. A human
  who never looks at the console sees nothing.
