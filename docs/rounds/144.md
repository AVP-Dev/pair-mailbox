# Round 144 — a runner that starts an agent without tmux

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-144-tmux-free-runner`
- **Writer**: omp · **Critic**: agy
- **Base**: `dev` (the human's directive: dev only, `master` untouched)
- **Deliverable**: `bin/pair-runner` starts one agent as a plain subprocess and
  injects the pair MCP server per launch, so the role and the room are named in
  the config the child reads. No pane, no composer, no tmux anywhere on its
  path. The mailbox is the channel.

## The problem

Every way into a pair went through tmux: `pairup`, `bin/pair-duo`, the panes
the roles are recorded in `.pair/state.json`, and the composer that
`pair_deliver` types a pointer into. On a host with no terminal multiplexer
there was no way in at all — and the tmux stack is the reason the pair cannot
be run in a container, a CI job, or a plain SSH session without tmux.

The mailbox itself never needed tmux. It is a directory of JSON files, and
`pair_send` → `pair_read` → ack is a pure file exchange. What needed tmux was
only the WAKE-UP: the pointer typed into the peer's composer.

So the runner is the narrow thing that was actually missing: a second way to
start an agent, with the wake-up path honestly renamed rather than faked.

## What changed

- **`bin/pair-runner`** (new, 249 lines, stdlib only) — starts one agent CLI
  as a child process and injects a per-launch MCP configuration:
  `{"mcp": {"pair": {"command": ["sh", "mcp/pair_mailbox/serve.sh", <role>,
  "--state", <room>]}}}`. The role is the one the caller named; the room is
  the one the caller named. No second rule for the room: the shared
  `state_resolve` decides, exactly as `serve.sh` does.
  - The child's environment is stripped of the pane variables (`TMUX`,
    `TMUX_PANE`, `PAIR_PANE`, `PAIR_PANE_SOCKET`, `PAIR_PILOT_PANE`), of the
    inherited `PAIR_STATE` and `PAIR_ROLE`, and the server's ancestry
    discovery is switched off with `PAIR_DISABLE_ANCESTRY_PANE=1` — otherwise
    the child would find the launching terminal's pane by walking the process
    tree and claim it.
  - The engine and the room must agree: a project that carries its own
    `mcp/pair_mailbox/serve.sh` is refused by name, and an engine the room
    does not sanction is refused before a child is started.
  - `--model` is a first-class flag: the model is named, not inherited. The
    host's default (`opencode-go/*`) answered `Go usage limit exceeded` on
    this host, and a launch that cannot say which model answers it fails for
    reasons the operator cannot see.
  - Any CLI other than OpenCode is refused by name, with the reason. One CLI
    measured is one CLI supported; the rest are not half-supported.
- **`bin/pair-runner_test.py`** (new, 257 lines) — six cases:
  the injected config names the exact role and the explicit `--state`; an
  unsupported CLI is refused by name; a room carrying its own server is
  refused; the child is a subprocess whose environment carries no pane
  variable and no inherited room; a named model reaches the command line; and
  **passive delivery without tmux** — two real roles on the real `serve.sh`
  in a real git project with `TMUX`/`TMUX_PANE` out of the environment, where
  `pair_send` lands the letter, `pair_read` serves the batch, and the
  `ack_token` closes it.
- **`skills/pair-chat/SKILL.md`** — a new section, "Without a tmux pane":
  `pair_send` is the whole channel; `pair_deliver` still delivers the body
  but answers `in_pane: false` and wakes nobody; the wait rule (one read per
  turn, ACK with the `ack_token`) does not change.
- **`skills/pair-work/SKILL.md`** / **`SKILL.ru.md`** — the same in §2a-1:
  what a tmux-less run does, and what it does not change.
- **`README.md`** / **`README.ru.md`** — the runner under "Launching a Pair
  Session", with the honest note that OpenCode is the only CLI it supports.
- **`scripts/verify-map.tsv`** and **`scripts/verification-profile.tsv`** —
  the two new files are mapped to a new `pair-runner` suite, which the
  changed-file gate now runs for them.

## The honest limits

- **One CLI.** OpenCode only. The other five profiles are refused by name.
  Their per-launch config injection is a separate slice with its own
  measurements.
- **No wake-up.** A subprocess has no composer to type into, so
  `pair_deliver` answers `in_pane: false` and nobody is woken. The mailbox is
  the channel; the peer reads on its own next turn. The skills now say so
  instead of leaving an agent to expect a wake that cannot come.
- **The supervisor is not replaced.** `bin/pairpilot` keeps its tmux wake
  path. The runner is a second way in, not a replacement.
- **The model must be named.** The runner does not pick a model: the host's
  default refused the request on this host, and a runner that guessed would
  fail for reasons the operator cannot see.
- **The `dev` branch is an accumulator** — §20 calls it an antipattern — but
  the human ordered dev-only work, so the deviation is recorded here rather
  than silently taken.
- **The launch is not supervised.** `bin/pair-runner` starts one child and
  waits for it; it does not restart a dead agent, does not answer permission
  prompts, and does not report. A long unattended run still wants the tmux
  stack.

## Rollback

One commit on one branch: `git branch -D round-144-tmux-free-runner` and the
PR closes. Nothing in the running system depends on the runner — the tmux
stack is untouched, and the skills changed by adding a section, not by
changing the tmux path.
