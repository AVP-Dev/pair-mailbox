# Round 145 — the guard that guarded the trunk and let `master` through

- **Mode**: fix · **Autonomy**: auto · **Branch**: `round-145-guard-master-too`
- **Writer**: omp · **Critic**: agy
- **Base**: `dev` (the human's directive: dev only, `master` untouched)
- **Deliverable**: `bin/git-hooks/pre-push` refuses a direct push to the
  project's trunk **and to `master`, always** — the hole round 144's
  configurable-trunk slice opened in the only guard that refuses the
  direction bypassing the PR gate.

## The defect

Round 144's second slice made the trunk a project setting: `PAIR_TRUNK` →
`.pair/trunk` → `.pair-trunk` → `master`. The close-side gates asked the
resolver (`mcp/pair_mailbox/trunk.py`) instead of naming a branch, and the
local pre-push guard was moved to the resolved trunk with it.

That was half right. The hook's rule is §19/§20's: **a protected branch
receives code ONLY by PR merge**. The slice implemented "the trunk" as the
protected branch and dropped the second one. In this very workspace
`.pair/trunk` says `dev`, so after the merge the hook:

- **refused** a direct push to `refs/heads/dev` — correct;
- **allowed** a direct push to `refs/heads/master` — a hole in the one guard
  whose whole job is to refuse that direction.

The branch-class table was left right on purpose: `master` stays in the trunk
class in a project whose trunk is `dev` (§20 — the class is the one no robot
may ever delete). The hook was not left right, and the two disagreed: the
engine called `master` untouchable while the guard let bytes travel to it.

This was found by the writer, after the merge, by running the installed hook
against a `master` refspec instead of trusting that the guard had followed the
resolver. The fix is small; the miss is the point of this card.

## What changed

- **`bin/git-hooks/pre-push`** — the hook resolves the trunk as before, and
  refuses a direct push to **two** protected branches: the resolved trunk, and
  `master` unconditionally. Naming another trunk does not hand `master` over.
  The refusal message names the branch it actually refused, so a hook that
  says `dev` can no longer hide a hole at `master`. The human override stays
  `PAIR_ALLOW_TRUNK_PUSH=1` and is still echoed on stderr.
- **`bin/pre_push_guard_test.py`** — one new case, the sixth:
  `test_master_stays_guarded_when_the_project_trunk_is_another_branch`. With
  `.pair-trunk` set to `dev`, a direct `master` push must be refused **and**
  `master` must not appear on origin. Red-proof: the case was run against the
  previous hook and **fails** there (`rc=0`, the push travels), and passes
  against the fixed one.
- **`docs/PROTOCOL.md` §19 / `docs/PROTOCOL.ru.md` §19** — the text said the
  pre-push guard was one of the gates that asks the resolver, which read as
  "the trunk is the only protected branch". It now says plainly: two protected
  branches, the project's trunk and `master`, always.
- **`docs/rounds/144.md`** — the card for round 144 claimed the hook "refuses
  a direct push to *the trunk*, not to a literal `master`". That sentence was
  true of the code and wrong as a rule; it now carries the correction and
  points at this round.

## The honest limits

- **The guard is local.** `bin/git-hooks/pre-push` runs on the machine that
  pushes, and only if `core.hooksPath` points at it. A client that does not
  install the hook is not protected by it — the hook refuses bytes before
  they leave, but it cannot refuse a client that never runs it. The remote
  protection is a branch-protection rule, which this round does not touch.
- **The override still exists.** `PAIR_ALLOW_TRUNK_PUSH=1` opens both
  protected branches for one push, and prints what it did. It is loud on
  purpose; it is still a hole a human can walk through.
- **`master` is protected by name here.** A project that renamed its default
  trunk to something else *and* wanted that name unguarded would have to edit
  the hook. The hardcoded `master` in the CI trigger, the GitHub branch
  protection and the `autoperms` deny-list is the same policy, untouched —
  a separate slice, recorded in the round-144 card.
- **The round card landed in its own PR.** The sanctioned merge deletes the
  round's branch by construction, so the card for round 144 could not travel
  in PR #92; round 143 set the precedent and this round follows it.
