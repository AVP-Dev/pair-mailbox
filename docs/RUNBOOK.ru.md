# Рабочие команды

[English](RUNBOOK.md) · [Установка](SETUP.ru.md) · [Протокол](PROTOCOL.ru.md)

## Пути и режимы запуска

В примерах движок расположен здесь; замените путь, если ваш клон в другом месте:

```bash
PAIR_HOME="$HOME/pair-mailbox"
cd "$HOME/work/my-project"
```

`PAIR_HOME` — удобная переменная оболочки, а не настройка движка. Текущий каталог —
целевой проект. В `PATH` устанавливается только `pairup`, остальные инструменты
вызываются по пути к движку. Доступные опции показывает их `--help`.

| Что нужно | Команда из целевого проекта |
|---|---|
| Самостоятельный агент | `codex` или `agy` |
| Пара с задачей | `pairup --writer codex "Исправь повторные запросы"` |
| Подключение к существующей паре | `pairup` |
| Заменить критика | `pairup --swap agy` |
| Имя ветки worktree | `pairup --worktree feature/retry "Исправь повторные запросы"` |
| Два экземпляра одного CLI | `"$PAIR_HOME/bin/pair-duo" codex "Исправь повторные запросы"` |

Если ссылки ещё нет, один раз выполните `"$PAIR_HOME/bin/pairup" --install` и
добавьте `$HOME/.local/bin` в PATH. После перемещения клона повторите установку ссылки.

Новая пара создаёт `.pair`, записывает движок, копирует отсутствующий `anti-mock.json`
и выбирает доступные профили. Существующая политика писателя приоритетнее
автоматического выбора. Новый каталог явного `--state` должен заканчиваться на `.pair`;
существующие нестандартные каталоги состояния поддерживаются. Опции состояния и
worktree показаны в `pairup --help`.

По умолчанию запуск создаёт или использует отдельный worktree. Состояние остаётся
в основном каталоге. `pairup --in-place` выбирает текущий checkout. Совместное
использование изменяемых зависимостей, build- и cache-каталогов включается явно
через `worktree-share`; см. [протокол](PROTOCOL.ru.md).

## Состояние, сообщения и доска

```bash
"$PAIR_HOME/bin/pairctl" status
"$PAIR_HOME/bin/pairctl" tasks
"$PAIR_HOME/bin/pairctl" budget
"$PAIR_HOME/bin/pairctl" all
"$PAIR_HOME/bin/pairchat" --once
"$PAIR_HOME/bin/pairchat" --all --once
"$PAIR_HOME/bin/pairboard"
"$PAIR_HOME/bin/pairboard" --print-json
```

`pairchat --all --once` печатает один снимок известных проектов; без `--once`
идёт поток. `pairboard` записывает `board.html` в текущий каталог и не запускает
веб-сервер. Откройте файл командой `open board.html` на macOS или
`xdg-open board.html` на Linux с графической средой. Доска показывает записанное
состояние, а не независимое доказательство выполнения задачи или теста.

У проекта отдельный tmux-сокет. Для подключения используйте `pairup`:
обычный `tmux attach` может попасть в другой сервер. Отключение от tmux —
Ctrl+B, затем D; агенты продолжают работать.

## Задачи и право записи

```bash
"$PAIR_HOME/bin/pairctl" task "Также проверь экспоненциальную задержку"
"$PAIR_HOME/bin/pairctl" why
"$PAIR_HOME/bin/pairctl" roles
```

`task` добавляет работу. Агенты закрывают её через общий список задач.
В парном сеансе `pair_state`, `pair_claim`, `pair_send` и похожие имена —
MCP-инструменты, а не исполняемые команды оболочки. Нативные помощники отчитываются родителю.

Чтобы задать предпочитаемого писателя для следующих запусков:

```bash
"$PAIR_HOME/bin/pairctl" roles --writer codex --global
```

Для явной передачи текущих прав человек может выполнить `pairctl release`, затем
`pairctl assign ROLE`. Держатель также может отказаться от прав через MCP-инструмент
`pair_release`; сообщение соседа само по себе ничего не передаёт.
Исходники правит только писатель. Потеря MCP не превращает критика в писателя.

## Автономность и цель раунда

```bash
"$PAIR_HOME/bin/pairctl" autonomy auto
"$PAIR_HOME/bin/pairctl" mode audit
```

`auto` разрешает действия супервизора в рамках списка разрешений; `semi` дополнительно
требует человеческого `pairctl ok` в контрольной точке; `observe` отключает
автоперезапуски и подтверждение разрешений. Доказательства нужны во всех режимах.
В `mode fix` писатель реализует изменения, в `mode audit` обе роли только читают.
Смена режима влияет на текущий раунд: сообщите агентам его цель.

Для выбора автономности при запуске укажите её первой строкой задачи:

```bash
pairup --task $'autonomy: semi
Проверь повторные запросы'
```

У `pairup` нет флага `--autonomy`. Порядок выбора: директива задачи, затем файл
`.pair/autonomy`, затем `auto`. `pair-duo` также принимает `--autonomy`.
Сама CLI может продолжать требовать подтверждение по собственной политике разрешений.

## Диагностика запуска и MCP

```bash
"$PAIR_HOME/bin/pairdoctor"
"$PAIR_HOME/bin/pairmcpdoctor" --role codex
"$PAIR_HOME/bin/pairrelaunch" --role codex --check
"$PAIR_HOME/bin/pairrestart" --role codex --dry-run
```

Начните с режимов отчёта и плана. `pairrestart` обновляет серверы с устаревшим кодом;
`pairrelaunch` без `--check` перезапускает CLI роли и теряет её контекст в памяти.
Срок жизни демона и границы переподключения описаны в [socket-транспорте](socket-transport-flip.md).

Если обычный CLI называет себя критиком, перезапустите его для загрузки актуальных
инструкций и проверьте интеграцию из клона движка: `./install.sh codex --check`.
Ноль инструментов у самостоятельного MCP — ожидаемый результат. Если ноль у явно
парного запуска, проверьте команду запуска, происхождение процесса, путь движка
и передачу `env_vars` для Codex. Экспорт старых `PAIR_*` не заменяет запуск пары.

Если `pairup` открыл две панели, но работа не начинается, проверьте, передана ли задача.
Пустой список означает «сообщить готовность». Codex и agy получают начальный промпт;
остальные профили зависят от обработки инструкций своим клиентом.

## Запуск без tmux: только OpenCode

Есть отдельный запуск CLI дочерним процессом. Просмотр сгенерированной MCP-конфигурации
без запуска модели:

```bash
"$PAIR_HOME/bin/pair-runner" --role opencode --state "$PWD/.pair" --print-config
```

Для запуска OpenCode укажите `--message "Задача"` вместо `--print-config`.
Остальные профили отклоняются. Панели tmux нет: сообщения попадают в ящик,
но runner не обещает активное пробуждение и не является общим пулом работников.
Перед использованием посмотрите `"$PAIR_HOME/bin/pair-runner" --help`.

## Обслуживание и чистка

`finish.sh` выполняет проверки и переустанавливает интеграции движка. Это не
повседневный запуск целевого проекта. `./finish.sh --no-pair` из клона движка
обслуживает интеграции без запуска модельных сессий. Полный путь — в `./finish.sh --help`.

Не запускайте второй супервизор для проекта с уже работающим. `pairup` поднимает
его при отсутствии. Перед удалением состояния остановите связанные CLI и супервизор,
сохраните нужные сообщения, патчи и доказательства. `pairctl reset --yes` заменяет
состояние; это не обычная команда запуска.

Держите `master` актуальным, а временные ветки удаляйте после слияния или сохранения
их работы в другом месте. [Бэклог](backlog/README.md), записи раундов и архив хранят
историю проекта; само их наличие не делает их мусором.
