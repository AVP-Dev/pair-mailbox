# RUNBOOK: как поднять рабочую парную сессию

> Язык: это русское зеркало. Английский оригинал — [RUNBOOK.md](./RUNBOOK.md).

Короткий путь от чистой машины до пары, где оба агента молчат, потому что
сказать больше нечего, а не потому что что-то сломалось.

## Одна команда

```bash
pairup
```

Запускать **из папки проекта** (`cd ~/work/nyx-os && pairup`) — `.pair`
находится walk-up от cwd (нет — создаётся в корне git), сверхвизор поднимается
если мёртв, пара поднимается. Без тестов и переустановки: секунды, не минуты.
Первый раз: `pairup --install` кладёт шим в `~/.local/bin`, дальше без полных
путей. Писатель не назначен — `pairup` применит твою общую расстановку
(`~/.config/pair-mailbox/roles.json`) и скажет об этом; перебить разово:
`pairup --writer <роль>`.

```bash
pairup --writer omp    # назначить писателя проекта и поднять пару одной командой
pairup --swap agy       # у критика кончились лимиты: новая панель критика, писатель не тронут
pairup --task "..."     # записать задачу перед подъёмом
```
Критик не назначен — `pairup` сам поднимает первый установленный CLI (писатель
не тронут) и запускает писателя в текущей панели: свежая папка работает одной
командой без вопросов. При создании `.pair` в корень проекта также копируется
шаблон ground-truth `anti-mock.json` (существующий файл никогда не затирается).

| флаг `pairup` | эффект |
|---|---|
| `--install` | положить шим в `~/.local/bin`, выйти (один раз) |
| `--writer <роль>` | назначить писателя проекта и поднять пару |
| `--swap <cli>` | заменить панель критика другим CLI; писатель и право не тронуты |
| `--worktree, -w <ветка>` | запустить пару в изолированном git worktree |
| `--task "..."` | записать задачу в общий список перед стартом |
| `--state <dir>` | явный каталог состояния (по умолчанию walk-up, иначе корень git) |

## Запуск pairup из любого каталога

`bin/pairup` — скрипт из клона репо, а не глобальная команда. Чтобы `pairup`
работал отовсюду (Linux или macOS), ставится шим один раз — клон может
жить в любом каталоге:

```bash
./bin/pairup --install        # симлинк ~/.local/bin/pairup -> bin/pairup вашего клона
```

**Примечание для macOS:** `~/.local/bin` обычно **не в PATH по умолчанию**. Проверить:

```bash
echo $PATH | tr ':' '\n' | grep .local/bin
```

Если пусто — добавьте в `~/.zshrc` (zsh) или `~/.bashrc` (bash):

```bash
export PATH="$HOME/.local/bin:$PATH"
```

после — `source ~/.zshrc` (или откройте новый терминал). После этого `pairup`
работает из любого каталога. Linux то же самое, но на большинстве дистрибутивов
`~/.local/bin` уже в PATH.

Если вы переносите или пересоздаёте клон, запустите `--install` ещё раз — шим
это просто симлинк на `bin/pairup` вашего клона. Либо, без всякой установки:

```bash
cd <каталог pair-mailbox> && ./bin/pairup      # полный путь, шим не нужен
```

## Стоящая пара

По умолчанию `pairup`/`finish.sh` читают стоящую расстановку и запускают
**писателя и критика на их собственных CLI**. Пинится только писатель
(writer-pin); критик — любой второй живой, смена CLI при кончившихся лимитах
без бумажек:

```bash
bin/pairctl roles --writer opencode --global   # задать один раз
pairup                                         # её и соблюдает, из папки проекта
```

Право движется только через человека. Пара — всегда два *разных* CLI: две
копии одного дерутся за MCP-лок роли и обе падают, duo-режима нет.

## Пошаговый путь, когда он нужен

### 1. Поставить и проверить

```bash
./install.sh              # каждый найденный CLI
./install.sh opencode     # только один
./install.sh --check      # ничего не менять, только проверить
```

Установщик пишет ваши конфиги. Перед ним:

```bash
cp ~/.config/opencode/opencode.jsonc{,.bak}     # подстраховка, хотя он и сам делает .bak
```

Что он делает и чего не делает:

- **пишет** блок `mcp.pair` в конфиг каждого CLI, с зашитой внутрь ролью;
- **копирует** навыки в `~/.config/<cli>/skills/`;
- **дописывает** парный блок в `AGENTS.md` после маркера `<!-- pair-mailbox -->`,
  сохраняя всё, что вы написали после маркера, и кладёт `.bak` перед
  перезаписью;
- **не трогает** ваши собственные ключи конфигов, ваши прочие MCP-серверы и ваши
  правила `deny`.

Проверить, что ничего не сломалось:

```bash
./scripts/verify-project.sh --list   # что проверяется
./scripts/verify-project.sh          # сам гейт
```

Гейт определён в `scripts/verification-profile.tsv`: сначала статические проверки,
затем по одному набору на модуль, затем установщик. Не цитируйте здесь числа
тестов — они растут вместе с кодом; источник правды — TSV.

### 2. Починить стоящую расстановку

```bash
bin/pairctl roles --writer opencode --global
bin/pairctl roles                                 # показать её (project + effective)
bin/pairctl roster                                # кто зарегистрирован
bin/pairctl roster --prune                        # убрать мёртвых
```

Пинится только писатель. `--critic` принят и проигнорирован с предупреждением
(старые вызовы работают); `--swap` двигает писателя на второго живого из
ростера. Критик — кто угодно второй живой, на swap без бумажек.

`--prune` убирает роль только когда сходятся два независимых факта: её процесс
мёртв, **и** её панель либо исчезла, либо принадлежит другой живой роли. Одного
факта мало — после падения живая панель может оказаться шеллом, который вы сами
открыли. Того, кто держит право записи, удалять отказывается.

### 3. Запустить сверхвизора

Вручную обычно не нужно: `pairup`, `pair-duo --pilot` и `finish.sh` (шаг 5)
поднимают его если мёртв и не трогают живого. Прямая форма, когда нужна:

```bash
bin/pairpilot &                  # в фоне, следит
bin/pairpilot --once             # один проход, посмотреть, что бы он сделал
bin/pairpilot --launch agy=agy   # как поднять роль, чей процесс умер
```

Как далеко пара ходит без вас:

```bash
bin/pairctl autonomy auto      # по умолчанию: работает сама, закрывает раунд по доказательству
bin/pairctl autonomy semi      # работает сама, но закрывает только по вашему слову
bin/pairctl autonomy observe   # только сообщает; человек за рулём
```

### 4. Запустить пару

```bash
cd ~/work/<проект> && pairup --task "..."   # быстро: сверхвизор-если-мёртв + пара
./finish.sh --task "..."                     # тяжело: установка + полные тесты + пара
```

Или вручную, в двух панелях:

```bash
# панель писателя
PAIR_ROLE=opencode PAIR_STATE=.pair opencode --standalone --auto
# панель критика
PAIR_ROLE=agy PAIR_STATE=.pair agy
```

Запуск opencode — это `opencode --standalone --auto`, никогда голый `opencode`:
`--standalone` даёт каждой панели свой локальный инстанс и MCP-конфиг, `--auto`
позволяет подтверждаться самому всему, что протокол и так разрешает. Это совпадает
с `launch: opencode --standalone --auto` в `cli-profiles.json` и с `WRITER_CMD`
в `bin/pair-duo`.

### 4a. Наблюдать без сервера

```bash
bin/pairboard                   # собрать board.html в корне репо, напечатать file:// url
bin/pairboard --watch 5         # пересобирать каждые 5с, страница перезагружается сама
bin/pairboard --out /tmp/b.html # куда-нибудь ещё
bin/pairboard --print-json      # один снимок, для пайпа
```

Один самодостаточный HTML-файл: без веб-сервера, без localhost, без запросов.
Открывается двойным кликом и копируется на другую машину как есть. На странице —
раунд и его фаза, каждая роль с панелью, pid и давностью молчания, сверхвизор
(жив или нет, его лог, его отчёт), журнал задач и хвост транскрипта.

Две вещи стоит знать до того, как открывать:

- **Без `--watch` это фотография, а не живой вид.** Сама страница читать `.pair`
  не умеет — браузеру на `file://` забирать локальные файлы запрещено — поэтому
  свежесть берётся из того, что генератор переписывает файл, а страница сама
  перезагружается. Живым его делает именно `--watch`, это не украшение.
- **В `.pair` он никогда не пишет.** Единственный файл, который он создаёт, — сам
  HTML, и по умолчанию это `board.html` в корне репо (игнорируется гитом,
  одноразовый, как и всё остальное состояние).

Тёмная тема по умолчанию, светлая — в один клик; выбор и пауза запоминаются в
`localStorage`, а кнопка паузы останавливает перезагрузку, пока вы читаете. Если
хотите рядом с терминалом, достаточно `bin/pairboard --watch 5 &` в другой панели.

Заметьте, `observe` — это не «гейты выключены»: доказательство для закрытия раунда
требуется в любом режиме. `observe` означает лишь, что он не будет перезапускать
агентов и ваше слово ему не нужно. См. PROTOCOL §10b.

Уровень выбирается при старте пары, и по умолчанию вас вообще не спрашивают:

```bash
pairup --task "autonomy: semi сделать дело"   # или pairctl autonomy semi
```

Без флага: `autonomy: semi` на первой строке задачи, затем `.pair/autonomy`,
затем `auto`. Источник пишется в транскрипт как `via=flag|task|file|default`.

### 5. Работать

```bash
bin/pairchat          # переписка вживую
bin/pairctl status    # состояние, включая что мешает закрыть раунд
bin/pairctl tasks     # список задач, заодно пересоздаёт .pair/tasks.md
bin/pairctl task --done 3              # закрыть задачу
bin/pairctl task --drop 3 --reason "covered by PR #5 instead"
bin/pairctl ok                       # сказать да на чекпоинте верификации
bin/pairctl ok --revoke              # забрать обратно
```

Раунд не закрывается, пока открыта хоть одна задача, поэтому добавленное
посреди раунда нельзя забыть: либо оно делается, либо снимается с причиной в
записи.

## Правило, которое экономит больше всего времени

**После правки кода в этом репозитории — перезапустите агентов.**

MCP-сервер держит модули в памяти. Правка файла на диске ничего не меняет, пока
процесс жив. Это не теория: сервер, стартовавший в 09:43, держал версию
`composer.py` за 09:43, правка вышла в 12:04 — и одиннадцать отказов доставки
подряд объяснялись этой разницей.

Как проверить, что код свежий:

```bash
ps -o pid,lstart,cmd -p $(pgrep -f 'server.py --role' | head -1)   # когда стартовал сервер
git log -1 --format=%cd                                            # когда лёг последний коммит
```

Если время старта раньше последнего изменения — код протух.

Обходной путь, который предлагают, — `importlib.reload(composer)` на каждый вызов:
не делайте так. В одном процессе останутся две версии модуля, потому что ранние
импорты смотрят на первую. Перезапуск честен и предсказуем.

## Почему вас просили что-то подтверждать

Две отдельные причины, обе исправлены, обе стоит знать.

**Агент шёл со старым конфигом, где не было `--auto`.** Теперь
`~/.config/opencode/opencode.jsonc` несёт блок `permission`, а профиль opencode
в `cli-profiles.json` — `launch: opencode --standalone --auto`. Так что всё, что
протокол и так требует без человека, подтверждается само, а §12, разрушение
системы, история git и сеть отклоняются всегда.

**Файл allowlist сверхвизора никогда не существовал.** `.pair/permissions.json`
отсутствовал, и `load_allow_patterns` превращала путь к недостающему файлу в один
разрешающий паттерн. Он не совпадал ни с каким промптом, поэтому сверхвизор
отказывал в **каждом** разрешении — что снаружи неотличимо от соседа, который
перестал помогать. Теперь отсутствующий файл означает список по умолчанию, и он
пишется в транскрипт (`pilot_default_allowlist`, `unblock_default_allowlist`),
чтобы было видно, какое правило одобрило команду.

Проверьте deny-правила:

```bash
python3 -c "
import re,pathlib
t=(pathlib.Path.home()/'.config/opencode/opencode.jsonc').read_text()
print('deny rules:', len(re.findall(r'\"deny\"', t)))"
```

Если напечатало 0 — установка не дошла дотуда, и агент будет спрашивать обо всём.

## Когда что-то выглядит не так

| симптом | вероятная причина |
|---|---|
| промпты доходят до вас за то, что протокол разрешает | файл allowlist отсутствует или `--auto` у CLI не применился — проверьте оба пункта выше |
| сверхвизор ничего не подтверждает | `bin/pairpilot --once` и читайте `closing_blocked_by` в `pairctl status` |
| мёртвая роль всё ещё сидит в ростере | `bin/pairctl roster --prune` |
| критик перестал получать подталкивания | две мёртвые роли делили его панель; исправлено, а `--prune` не даёт повториться |
| правки ни на что не влияют | протухший MCP-сервер — перезапустите, см. правило выше |
| `pair_read` пуст после ожидания | клиент срезал ожидание; в ответе сказано `wait_capped_by_client_timeout` |

`closing_blocked_by` в `pairctl status` называет причину, по которой раунд нельзя
закрыть прямо сейчас. Читайте его раньше, чем тратить ход на заведомый отказ.
