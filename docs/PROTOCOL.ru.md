# Протокол парной работы

> **Внимание: эта русская версия отстаёт от
> [`PROTOCOL.md`](./PROTOCOL.md) и будет переписана.** Расхождения уже известны и
> перечислены ниже. Между тем оригинал на английском — нормативный; здесь
> правило может быть устаревшим.
>
> Расхождения, которые уже исправлены в английском оригинале:
>
> - §10b: в `observe` доказательства **обязательны**. Раньше здесь было написано,
>   что гейт §5a выключен — это было неверно, код всегда требовал доказательств.
> - §5a: в `mode=fix` прогон тестов должен быть **от писателя**.
> - §5c (новая): список задач `state["tasks"]`, стоппер на закрытии раунда,
>   журнал `.pair/tasks.md`.
> - §5b (уточнение): писатель может снять чужой нерешённый патч.
> - §10b (новое): `pairctl ok --revoke`, привязка `ok` к фазе.
> - §10b (дефолт сменился): **по умолчанию теперь `auto`, а не `semi`**, и
>   `reset` оставляет `auto`. Старое рассуждение «стирание не должно повышать
>   права» было ошибочным: права измеряются относительно дефолта, а дефолтом
>   человек назначил `auto`.
> - §10b.1 (новая подсекция): выбор уровня **один раз при старте**, порядок
>   источников `flag` > `task` (`autonomy: semi` на первой строке) > `file`
>   (`.pair/autonomy`) > `default` (`auto`); источник пишется в транскрипт как
>   `via=flag|task|file|default`. Флаг проверяется до старта tmux, а мусор в файле
>   или флаге не ломает запуск, а переходит к следующему источнику.
> - Неизвестное значение `autonomy` читается как `observe`, но **отсутствующий
>   ключ** — это старый файл состояния, а не просьба осторожничать, и читается как
>   `auto`.
> - §7 (новая редакция в оригинале): **ход заканчивается ограниченным
>   `pair_read`** — это не пожелание, а механизм. Ни в одной реализации MCP нет
>   инструмента, позволяющего серверу вставить ход в клиента: MCP ведёт клиент,
>   сервер отвечает на запросы и не может подтолкнуть хост. Поэтому ящик —
>   единственный универсальный канал, а чтение — единственное универсальное
>   пробуждение. Напоминание сверхвизора — ускоритель, и оно идёт через ту же
>   ненадёжную доставку. Адаптеры пробуждения по CLI перечислены таблицей, и на
>   них ничего не завязано.
> - §13a (новое): `respawn-pane` без `-k`, записка при перезапуске, мёртвая роль
>   не делает панель общей.
> - §13 (новое): `pairctl roster --prune`.
> - §13b (новое): отсутствие файла = список по умолчанию, и это пишется в журнал;
>   запрет `python3 -c`; `OVERSCAN_LINES`.
> - §2 (новое): `bin/pair-duo` больше не двигает авторитет молча.

Два агента, разные CLI, один проект, одна задача. Один пишет, второй ломает.
Документ — контракт между ними. Короткий намеренно: правило либо enforce'ится сервером,
либо заслуживает внимания агента. Всё, чего здесь нет, правилом не является.

Читай также `AGENTS.md` — там форма пары. Этот файл — часть, которая не должна
разъезжаться.

## 1. Писатель ровно один

Одна роль держит право записи. Она правит файлы, гоняет тесты, коммитит. Вторая
read-only: читает, ищет, предлагает патчи.

### Как выбирается

`pair_claim(reason="...")`. Кто захватил — пишет, второй критик. Это гонка, и
остаётся ею: чтобы выбрать роль осмысленно, а не по скорости нажатия, обоим нужно
прочитать задачу и код, а это время, которое никто не ждёт.

Но гонка без аргумента — просто очередь. Поэтому у захвата есть `reason`: одно
предложение, почему именно ты. Он попадает в транскрипт, в `pair_state` и **в отказ
соседу** — сосед видит чужой аргумент и может с ним не согласиться.

Имена ролей в примере — конкретная пара `opencode` + `agy`. В любой другой паре имена
те же по смыслу, но свои: писатель — `<писатель>`, второй — `<критик>`. Роль равна
имени CLI и зашивается при установке.

```
<писатель>: pair_claim(reason="я уже нашёл, где чинить: retry в клиенте")
<критик>:    write authority is held by 'codex',
             which claimed it because: я уже нашёл, где чинить: retry в клиенте
```

Дальше у критика два честных пути, оба без участия человека:

- `pair_send` — назвать, с чем он не согласен, с `file:line`. Держатель может
  передумать и отдать право сам.
- Согласиться и работать критиком.

Ни один из путей не отнимает право у другого. Отнять нельзя вообще.

Enforce'ится сервером:

- `pair_claim` отказ, если авторитет занят
- `pair_patch_reserve` отказ у держателя — он правит напрямую и не нуждается в механизме
- `pair_patch_verify` и `pair_advance` вперёд доступны только держателю

## 2. Авторитет двигает только человек

`bin/pairctl assign` и `bin/pairctl release`, больше нигде.

**Сообщение соседа не передаёт авторитет** — ни выдать, ни забрать, ни взять на
одну правку. Ни один агентский инструмент не пишет в `writer`.

Сменить писателя посреди задачи:

```sh
bin/pairctl release
bin/pairctl assign <роль>      # роль соседа: agy, codex, claude — как у вас в проекте
```

Сказать обоим в их окнах, кто теперь пишет. Прежний писатель остаётся read-only даже
после прерывания и возобновления: отозванный писатель не помнит, что был писателем.

Есть нюанс, который легко спутать с нарушением: **держатель может отдать право сам.**
`pair_release(why="...")` — это его решение, а не передача по сообщению. Агент не может
забрать право у другого, но держатель может его отдать — и это право нельзя отнять
обратно, потому что авторитет после отдачи свободен и достаётся новым `pair_claim`.

Кто пишет и что он заявил:

```sh
bin/pairctl why          # по всем проектам
bin/pairctl status       # в текущем проекте, JSON
```

## 3. Read-only агент предлагает патчи, а не делает их

```
pair_patch_reserve        # пустой файл 0600, точный путь
# пишем unified diff в этот путь
pair_patch_seal(path)      # сервер считает и запоминает SHA-256
# активная доставка прямо в композер писателя для немедленного продолжения:
pair_deliver(to="<writer>", text="patch at <path> sha256 <hash> — что чинит, применяй и продолжай")
# если композер занят — pair_send в ящик
```

Писатель:

```
pair_patch_verify(path)    # пересчёт; не совпало — стоп
```

- **Несовпадение — стоп.** Патч изменился после печати. Не применять, попросить
  перепечатать. Это единственная защита от подмены между предложением и применением.
- Копировать патч **один раз**, работать с копии.
- **Перепроверять непосредственно перед применением**, не в начале ревью.

Оба удаляют свои файлы через `pair_patch_release` **точным путём**. Никогда глобом:
каталог общий, чужой патч не виден и будет удалён вместе со своим.

После прерывания — проверить, остался ли файл, и удалить по точному пути.

## 4. «Сосед согласился» — не одобрение человека

Самая опасная фраза в системе. Её можно процитировать, и она не значит ничего.

- Агент может сказать, что сосед согласился.
- Агент не может сказать, что поэтому действие одобрено человеком (когда речь идёт о передаче
  авторитета или 6 критических триггерах из §12).
- Ни один агент не отвечает за пользователя: не выдаёт права от его имени, не трогает секреты и прод.

**При этом рутинная разработка автономна:** агенты не спрашивают одобрения человека на применение
патча, прогон тестов, коммиты или смену фаз. Если критик опечатал патч — писатель применяет его
и продолжает работу без вопросов человеку.

## 5. Раунд нельзя закрыть поверх непрочитанного

`pair_advance("done")` отказ, если в своём ящике есть непрочитанные сообщения.

Отчёт, который писатель не прочитал, — это не отчёт.

### 5a. Раунд нельзя закрыть без доказательства

`pair_evidence(kind, value, ok)` записывает машинно-проверяемый факт текущего
раунда: тесты с числом тестов и кодом выхода, lint, typecheck, diffstat, коммит,
URL PR. Виды: `test`, `lint`, `typecheck`, `build`, `diff`, `commit`, `pr`, `manual`.

В режимах `semi` и `auto` закрыть раунд нельзя, пока:

- нет ни одного успешного доказательства текущего раунда;
- последний прогон по какому-либо виду провалился.

По каждому виду решает **последний** запись: тесты падали → починили → прогнали
снова, и раунд закрывается. `ok=false` — не признание в ошибке, а запись, которая
держит раунд открытым, пока её не починят или не объяснят в заметке.

Доказательства принадлежат раунду. То, что доказало раунд 3, ничего не говорит о
раунде 7, иначе гейт превращается в наклейку из первого же раунда.

Почему это вообще нужно: у моделей 78–96% заявленных оценок уверенности равны
100. «Критик доволен» — не сигнал, и пустить его в `done` нельзя.

### 5b. Патч без применения держит раунд открытым

`pair_patch_applied(path, ok, note)` — писатель, только после успешного
`pair_patch_verify`, записывает исход применения. Раньше в протоколе не было
такого глагола вообще: `applied` выставлялся при резервировании и больше не
менялся, поэтому «применён» и «лежит с прошлой ночи» выглядели одинаково, и
раунд спокойно закрывался над предложением, которого никто не касался.

`ok=false` (hunk не применился) считается нерешённым. Снять патч осознанно —
`pair_patch_release`, и это тоже попадает в транскрипт как `patch_dropped`:
«сняли» и «забыли» — разные вещи, и от обязан различать.

## 6. Откат фазы доступен обоим

Вперёд фазу двигает писатель. **На шаг назад — кто угодно:**

```
done     → implement   любой
verify   → implement   любой
implement → plan       любой
```

Это право вето критика, и оно не требует правы записи. Ран закрывается на том, что
критик нашёл находку после `done` — а раньше он был заперт в закрытом раунде, и его
находка умирала в почтовом ящике.

Откат из `done` увеличивает `round` и снимает `closed_at`.

## 7. Живой канал: агент ждёт, а не спит

Два способа отправки:
- **`pair_deliver`** — активный: вбивает текст в окно соседа и жмёт Enter, будит сразу.
- **`pair_send`** — пассивный: кладёт в ящик.

`pair_read(wait_seconds=N)` — нормальный способ услышать соседа. Пришёл пустым — зови
снова. Потолок 60 секунд, время вышло — возвращайся к работе.

Обе роли могут ждать. Ограниченное ожидание не создаёт взаимной блокировки: оно всегда
истекает и возвращает агента к задаче.

Раньше писателю запрещалось ждать вовсе, чтобы не было тупика. Это убило канал:
агент без возможности ждать засыпает и не замечает входящих сообщений, и человек
начинает пересылать их руками. Живое ожидание — часть протокола, а не оптимизация.

## 7a. Запрет «голубиной почты»: агенты общаются напрямую

Агентам категорически **запрещено** просить пользователя пересылать сообщения, сигналы или промпты
в соседнее окно терминала (например: *«В окне opencode висит запрос на ваш сигнал, отправьте ему подтверждение...»*).

Такой вывод — грубое нарушение контракта автономной парной работы:
1. Для передачи сигналов и пробуждения соседа есть инструмент **`pair_deliver`**, который вбивает
   команду прямо в активный ввод tmux-панели соседа.
2. Для фонового обмена есть `pair_send` и `pair_read`.
3. Пользователь даёт задачу на старте и принимает готовый PR на финише. Человек не является
   маршрутизатором между окнами.

## 7b. Не беспокоить человека: пара замыкает цикл сама

Дефолт, не украшение промпта. Действует в каждом раунде, пока не сработал §12:

- Человека не звать никогда: ни вопросов, ни «посмотри», ни «подтверди».
  Застрял — пиши в `pair_note`, что заблокировано и чем, делай следующий шаг сам.
- Критик молчит 15+ мин — повторный `pair_send` с `expects_reply`,
  работаешь дальше, пилот его догонит.
- Вердикт открывает obligation писателю автоматом — `done` берёшь сам,
  когда блокеров ноль. Закрыл раунд — бери следующую карточку из
  `docs/backlog/` сам, новый раунд открывает писатель.
- Неопределённость решается между агентами (§12): выбери вариант, запиши
  `decision` с причиной, иди дальше.

Останавливают пару и зовут человека только шесть вещей (§12): секреты, порты,
деплой, миграции, удаление данных или истории. Всё остальное решается без
него — в этом и смысл `auto`.

## 8. На вопрос «как дела?» отвечать фактом

Не «ща проверю». Открыть `pair_state` или `pair_transcript` и сказать, что **правда
сейчас**: фаза, что сделано, что висит. Если ничего не изменилось — так и сказать.

Обещание проверить — это способ занять время, не сообщив ничего.

## 9. Заметки, а не переписка

Переписка не разделяема и не переживает перезапуск. Всё, что сосед должен знать после
сброса контекста, — в заметке:

```
plan      что agreed и в каком порядке
decision  выбор и причина
finding   проверено на коде, с file:line
verdict   итог проверки и чего она НЕ покрыла
handoff   что сделано, что пропущено, что неясно
backlog   реальный дефект вне объёма задачи
```

## 10. Git — часть работы

Ветка от задачи, коммит после каждого зелёного шага, тесты зелёные обязательны,
`push` и PR в конце. **В `main` не пушат никогда.**

Это не «отдельное явное действие пользователя». Агент, считающий пуш и PR чужим
делом, оставляет работу на половине.

### 10a. Режим раунда: `fix` или `audit`

`bin/pairctl mode fix|audit` — человек выбирает, что вообще делает раунд. По умолчанию
`fix`, и всё поведение выше сохраняется.

В `audit` раунде проект не меняется **намеренно**: никто не правит файлы, не создаёт
ветку, не коммитит, не предлагает патчи — сервер отказывает в резервировании патча с
записью в аудит. Работа при этом настоящая: находки, их опровержение соседом,
подтверждённое кладётся в `docs/backlog/`. В раунде `fix` исправленные карточки
удаляются из `docs/backlog/` (с фиксацией в коммите). Отличие от `fix` не в том, что работа
слабее, а в том, что её результат — доказательства, а не diff.

Право записи в `audit` не отменяется — иначе фазой некому двигать, а §5 и §6 остались
бы в силе. Меняется предмет: писатель не коммитит код, а ведёт раунд, держит находки
в заметках и переносит подтверждённые в `docs/backlog/`.

Режим лежит в состоянии, а не в тексте задачи. Причина: агент получает свои инструкции
из состояния и промпта, и эти два не должны противоречить задаче — иначе агент, который
внимательнее прочёл свою инструкцию, сделает не то.

### 10b. Насколько далеко пара идёт сама: `observe`, `semi`, `auto`

`bin/pairctl autonomy observe|semi|auto` (**по умолчанию `auto`**). Это **отдельная** ось от
`mode`: `mode` отвечает на вопрос «что делает раунд», `autonomy` — «насколько далеко он
идёт без человека». Сливать их нельзя: `pairctl mode auto` молча превратил бы аудит в
правку кода, потому что каждая проверка аудита смотрит на `mode == "audit"`.

| | перезапуск упавшего | подтверждение разрешений | закрытие раунда |
|---|---|---|---|
| `auto` (по умолчанию) | да | только из белого списка | нужно доказательство, слова не требуется — раунд закрывается сам |
| `semi` | да | только из белого списка | нужно доказательство **и** слово человека: `bin/pairctl ok` |
| `observe` | нет | нет | человек за рулём; доказательство всё равно обязательно |

`pair_state` отдаёт `autonomy` и `autonomy_meaning`, а также `closing_blocked_by` —
список причин, по которым `done` прямо сейчас невозможен. Агент должен видеть причину
до того, как потратит ход на заведомый отказ.

Неизвестное значение `autonomy` (например, из состояния, записанного более новой
сборкой) читается как `observe`: чужое состояние не должно выдавать этой сборке больше
прав, чем человек просил. **Отсутствующий** ключ — другое дело: это старый файл
состояния, а не просьба осторожничать, и он читается как `auto` — дефолт, который задал
человек.

#### 10b.1. Как уровень выбирается один раз, при старте

Пара поднимается один раз и дальше работает без присмотра до готового результата.
Уровень выбирается в этот момент и не пересматривается посреди раунда, поэтому человека
спрашивают **не чаще одного раза**, а в `auto` — не спрашивают вовсе.

`bin/pair-duo` принимает `--autonomy observe|semi|auto`, а `--auto`, `--semi` и
`--observe` — сокращения того же. Значение проверяется **до** старта tmux: опечатка,
молча проигнорированная после запуска, оставила бы пару работать не на том уровне,
который выбрал человек, и узнать об этом можно было бы только по факту.

Без флага `bin/pairctl launch-autonomy` решает так, по убыванию силы:

| источник | как выглядит | сильнее |
|---|---|---|
| `flag` | `pair-duo --semi` | всего |
| `task` | `autonomy: semi` на **первой строке** задачи | файла |
| `file` | `.pair/autonomy`, одно слово | дефолта |
| `default` | `auto` | — |

Источник попадает в транскрипт вместе со значением как `via=flag|task|file|default`.
Уровень, за который нельзя объясниться, потом становится спором: «почему этот раунд
закрыл себя сам?» не имеет ответа, если причина не записана в момент решения.

Строка в задаче должна **начинать** задачу, а не просто встречаться в ней — иначе слова
«перенеси этот текст про autonomy: semi» тихо понизили бы пару. Мусор в файле или флаге
не ломает запуск, а переходит к следующему источнику: отказ подняться хуже, чем
подняться на уровне, который человек видит в `pairctl status`.

§12 не входит ни в одну из этих осей. Секреты, порты, деплой, миграции, удаление данных
и истории git, прод останавливают пару при любом уровне, включая `auto`.

## 11. Аудит

`pair-transcript.jsonl`, append-only, по событию: сообщение, захват, смена фазы,
резервирование патча, печать, проверка хеша, **и каждый отказ**.

Отказы — самое ценное. Сосед, пробующий обойти границу записи, — ровно то событие,
которое надо хранить.

```sh
bin/pairctl log --limit 50
```

Если прогон нельзя восстановить по этому файлу — прогона не было, независимо от
финального отчёта.

## 12. Триггер остановки

Останавливаются и спрашивают пользователя только про шесть вещей:

`.env`, секреты и токены, порты и адреса развёртывания, деплой, миграции БД,
удаление данных или истории git.

Всё остальное, включая неопределённость, решается между агентами. Неопределённость —
не повод будить человека: выбрать вариант, записать `decision` с причиной, идти
дальше.

## 13. Сверхвизор: кто смотрит на пару, пока оба молчат

Агенты по устройству пассивны: отработав шаг, они ждут ввода. Пока оба не пишут
друг другу — пара стоит, и разбудить её может только человек. `bin/pairpilot` —
процесс, который смотрит на пару извне и делает ровно семь вещей: переживающая
доставка отложенного, подталкивание молчащего, подтверждение запроса разрешения **из
белого списка**, перезапуск упавшего агента, сигнал о зависшем патче, дайджест на
чекпоинте и отчёт при закрытии раунда.

И принципиально не умеет: двигать фазу, выдавать или забирать право записи, коммитить,
применять чужие патчи, трогать файлы проекта. Иначе §2 перестаёт быть границей.

### 13a. Перезапуск упавшего агента

Только когда: процесс действительно мёртв (pid не отвечает), панель жива, роль не
делит панель с другой ролью, режим не `observe`, и команда запуска известна.

Команда берётся в порядке «явное раньше угаданного»: `--launch role=cmd`,
`PAIR_LAUNCH_<ROLE>`, `.pair/restart.json`, поле `launch` в `cli-profiles.json`. Нет
команды — перезапуска не будет, а в транскрипт ляжет `pilot_restart_impossible` с
причиной. Выдуманная команда хуже отсутствующей: панель оживает и сразу падает.

Роль возвращается с тем же именем, потому что `install.sh` зашивает роль в MCP-конфиг,
а не в память процесса. **Право записи перезапуск не трогает**: писателем остаётся тот,
кого назначил человек. Это и делает перезапуск безопасным — он чинит процесс, а не
границу доверия.

Молчание и смерть лечатся по-разному, и смешивать их нельзя: молчание — это напоминание,
смерть — это перезапуск. Бить живого процесса нельзя: он не потеряет контекст, если
работает.

Панели, которой нет, сверхвизор не поднимает: окно, закрытое человеком, — это решение,
а не зависание.

### 13b. Белый список разрешений

`resolve_permission_prompt` подтверждает только то, что совпало с белым списком. Список
по умолчанию — не «только чтение»: это работа, которую протокол и так обязан делать без
человека, иначе пара встаёт на каждом шаге.

Разрешено по умолчанию:

- чтение: `Read`, `grep`, `glob`, `ls`, `cat`, `head`, `tail`, `find`;
- правка внутри проекта: `write`, `edit`, `create`, `replace`, `patch`, `apply`, `format`, `lint`;
- проверки и сборки: `pytest`, `unittest`, `ruff`, `mypy`, `tsc`, `make`, `npm run`, `build`,
  а также `python3`/`node` с тестом или линтером в команде;
- локальный git: `status`, `diff`, `log`, `add`, `commit`, `checkout`, `switch`, `branch`, `stash`;
- отправка работы: `git push` в **фиче-ветку** и `gh pr` — §10 требует PR;
- уборка артефактов: `rm -rf build/` с относительной целью.

Запрещено при любом белом списке, проверяется первым:

- **§12 целиком:** секреты (`.env`, `id_rsa`, `/etc/shadow`, `.pem`, `.npmrc`, `.aws`, токены,
  пароли), порты и деплой (`deploy`, `kubectl`, `helm`, `docker`, `terraform`, `ssh`, `sudo`),
  миграции и разрушение БД (`migrate`, `drop table`, `truncate`), прод;
- **разрушение системы:** `rm -rf /`, `rm -rf ~`, `rm -rf .`, `mkfs`, `dd if=`, `> /dev/sda`,
  `killall`;
- **история git:** push в `main`/`master`, `--force`, `reset --hard`, `clean -f`,
  `filter-branch`, `reflog expire` — §10 и §12;
- **сеть и установка пакетов:** `curl`, `wget`, `nc -`, `pip install`, `npm install`,
  `npm publish`. Не потому что сеть опасна сама по себе, а потому что сеть позволяет вынести
  наружу то, что §12 защищает, а установка пакета тянет в проект чужой непроверенный код;
- **труба в шелл:** `| sh`, `| bash`, `$(`, backtick, `xargs`, `find … -exec/-delete` — это
  превращает любое чтение в выполнение.

Расширяет человек: `.pair/permissions.json` с `{"allow": ["Read", "git status"]}`,
`PAIR_PERMISSIONS` или `bin/pairpilot --allow 'Read,git status'`. Пустой или нечитаемый файл
означает «не подтверждать ничего»: сломанная настройка не имеет права расширять права
сверхвизора.

Отказ — не ошибка, а результат: панель остаётся заблокированной, событие
`pilot_unblock_refused` попадает в транскрипт, а причина — в отчёт. Причина обязательна:
необъяснённое «нет» неотличимо от сломанного сверхвизора.

**Ограничение, о котором нужно знать.** Решение принимается по тексту строки, а не по разбору
команды: строка может содержать безобидное слово рядом с опасным. Отсюда три правила: список
по умолчанию ограничен внутренней работой, запреты проверяются первыми и не отменяются
настройкой, а совпадение записывается в транскрипт вместе с самой строкой — по журналу видно,
на что именно было сказано «да».

Тот же список применяет `pair_unblock` агента и `bin/pairwatch --unblock`. Оставляя эту дыру
с другой стороны значило бы оставить её наполовину.

**Две формы вопроса.** Не все агенты спрашивают `[y/N]`. TUI opencode показывает меню:
`Allow once · Always allow · Reject` с подсказкой `⇆ select  enter confirm`. Различия
существенны, и обе обрабатываются:

| | `[y/N]` | меню |
|---|---|---|
| как определяется | `PERMISSION_PATTERNS`, две последние строки | заголовок `Permission required` **и** признаки меню |
| по чему выносится вердикт | по строке вопроса | по тексту всей модалки — команда видна в теле (`$ git status`), а не в заголовке |
| что нажимается | `y`, затем `Enter` | только `Enter` |
| проверка композера | да | нет: в модалке строки ввода не существует |

`y` в меню не значит согласие, поэтому не отправляется. Вердикт по заголовку был бы всегда
отказом — в нём нет ни одного слова из белого списка, — то есть разрешение в меню молча
перестало бы работать. Заголовок `Permission required` в обычном выводе вопросом не
считается: нужны оба признака сразу.

### 13c. Свой deny-список важнее сверхвизора

У каждого CLI есть собственный механизм запретов, и он срабатывает **раньше** любого
нашего. Для OpenCode это `permission` в `opencode.jsonc` и флаг `--auto`: в авто-режиме
запросы, которые не запрещены явно, подтверждаются сами, а правила `"deny"` действуют
всегда.

```jsonc
{
  "permission": {
    "bash": {
      "*": "allow",
      "sudo *": "deny", "curl *": "deny", "wget *": "deny",
      "pip install *": "deny", "npm install *": "deny", "npm publish *": "deny",
      "ssh *": "deny", "docker *": "deny", "kubectl *": "deny",
      "terraform *": "deny", "helm *": "deny", "mkfs*": "deny", "killall *": "deny",
      "git push *main*": "deny", "git push *master*": "deny", "git push --force*": "deny",
      "git reset --hard *": "deny", "git clean -f*": "deny", "git filter-branch*": "deny"
    },
    "read": {
      "*": "allow",
      "*.env": "deny", "*.env.*": "deny", "*.env.example": "allow",
      "**/.ssh/*": "deny", "**/id_rsa*": "deny", "**/*.pem": "deny", "**/*.key": "deny",
      "**/.npmrc": "deny", "**/.aws/*": "deny", "**/.git-credentials": "deny"
    }
  }
}
```

Звёздочки здесь — точный синтаксис opencode, а не наш: правила применяются по порядку,
последнее совпавшее выигрывает, поэтому `"*": "allow"` идёт первым.

Почему это лучше белого списка сверхвизора, а не рядом с ним:

- **срабатывает раньше.** CLI не показывает диалог вообще, поэтому агент не стоит и
  сверхвизору не нужно решать, нажимать ли Enter;
- **обязателен.** `"deny"` действует в том числе в авто-режиме, то есть пережить его нельзя
  опечаткой в белом списке;
- **читает человек.** Правила лежат в его конфиге, рядом с настройкой модели, а не внутри
  инструмента, который мы сопровождаем.

Поэтому `launch` для OpenCode содержит `--auto`: агент перестаёт вставать на каждом шаге, а
граница держится на `deny`, который человек видит и может изменить.
